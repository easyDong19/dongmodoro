# 설계: 조절이 곧 기준이다 — 뽀모 길이 편집의 단일화

> **성격:** 이 문서는 **설계(스펙)** 다. 태스크 단위 구현 계획은 이 문서를 근거로 별도
> 작성한다. 결정의 근거 원장은 [2026-08-13 세션](#부록--이-설계에-이른-과정)에 요약한다.

**Goal:** 뽀모 길이를 바꾸는 경로를 **대기 중인 타이머의 ± 칩 하나**로 단일화한다.
조절한 값은 그 즉시 그 모드의 기준 길이가 되고, 모드 전환·세션 종료·앱 재시작 뒤에도
남는다. "이번 세션만 늘리는 임시 조절"이라는 개념은 폐기한다.

## 문제

사용자가 집중 모드에서 ± 칩으로 30분을 맞추고, 짧은 휴식을 다녀온 뒤 집중으로
돌아오면 25분이었다. 이는 결함이 아니라 설계대로였다 —
[pomo-baseline R2](../features/pomo-baseline/prd.md) 는 ± 조절을 "그날의 예외 대응"으로
정의했고, 모드 전환은 언제나 저장된 기준 길이로 되돌린다
([timer ux-spec §2](../features/timer/ux-spec.md)).

문제는 그 설계가 **사용자가 아는 유일한 길이 조절 수단이 ± 칩**이라는 현실과
어긋났다는 것이다. 기준 길이를 바꾸는 진짜 경로는 주간 정산 패널 안에 접혀 있는
`조정` 폼뿐이고, 타이머 화면에는 그 존재를 알리는 것이 없다. 손에 닿는 수단이 하나뿐인데
그것이 "저장되지 않는 쪽"이라, 사용자는 저장했다고 믿고 사라진 값을 본다.

이는 [ADR-029](../architecture/decisions/adr-029-baseline-immediate-effect.md) 가 고친
1.x 결함과 **같은 종류의 문제**다. 그때는 저장이 다음 주까지 효력이 없어 "저장이 안
된다"로 읽혔고, 지금은 조절이 애초에 저장이 아니라서 같게 읽힌다.

## 결정

**조절이 곧 기준이다.** 별도의 저장 동작을 두지 않는다.

### R1. 길이를 바꾸는 경로는 하나다

대기 중인 타이머의 ± 칩이 뽀모 길이를 바꾸는 **유일한 경로**다. 정산 패널의 `조정`
진입점과 그 폼은 폐기한다. 이로써 [pomo-baseline R11](../features/pomo-baseline/prd.md)
의 "편집 진입점 2개"는 1개로 개정된다.

### R2. 조절은 즉시 그 모드의 기준이 된다

모드 탭마다 자기 기준을 갖는다 — `집중` 탭의 조절은 `focus_min` 을, `짧은 휴식` 탭의
조절은 `short_break_min` 을, `긴 휴식` 탭의 조절은 `long_break_min` 을 바꾼다.
저장은 조절 즉시 일어나며, 별도의 확정 버튼이 없다.

기존 R2("± 조절은 저장된 길이를 변경하지 않는다")는 **폐기**한다. 임시 조절과 기준
길이는 하나의 개념으로 합쳐진다.

### R3. 세션이 도는 중에는 조절할 수 없다

실행·일시정지 상태에서 ± 칩은 **비활성**이다. 자리에서 사라지지는 않는다 — 버튼 줄이
상태마다 재배치되면 레이아웃이 흔들리고, 비활성 상태가 "지금은 바꿀 수 없다"는 사실을
그 자체로 말한다.

이로써 "이번 세션만 10분 늘리기"는 없어진다. 이것은 손실이 아니라 **R2 의 필연적
결과**다: 조절이 곧 기준이면 실행 중 조절은 의도치 않은 기준 변경이 된다.

기존 timer R2("실행 중에도 가능")는 이 규칙으로 개정된다.

### R4. 하한은 1분이다

기존 규칙 그대로다. 1분에서 더 줄이려 해도 1분이며, 하한은 IPC 계약과 SQLite CHECK
양쪽에서 거부된다 ([ADR-011 §6](../architecture/decisions/adr-011-schema-final.md) ·
[ADR-019 §3](../architecture/decisions/adr-019-constraint-implementation.md)).

### R5. 진행 중인 세션과 과거 기록은 그대로다

[ADR-029 §1](../architecture/decisions/adr-029-baseline-immediate-effect.md) 의 "적용은
다음 세션 시작부터"와 [pomo-baseline R10](../features/pomo-baseline/prd.md) 의 "길이
변경으로 과거 기록은 재해석되지 않는다"는 그대로 유효하다. R3 이 실행 중 조절 자체를
막으므로, 이 두 규칙은 이제 **구조적으로 위반이 불가능**하다.

`초기화` 버튼의 의미도 그대로다 — 진행 중인 세션을 기록 없이 버리고 대기로 돌아간다.
돌아온 다이얼은 그 모드의 기준 길이를 보여주며, 그 값은 사용자가 마지막에 맞춰 둔
값이므로 놀랄 일이 없다.

### R6. 정산 패널은 길이를 다루지 않는다

`조정` 버튼·편집 폼·보조 문구(`바꾼 길이는 다음 세션부터 적용돼요 · 진행 중인 세션은
그대로예요`)에 더해 **현재 길이 표시 줄도 제거**한다.

표시를 남기지 않는 이유는 정합성이다. 타이머 카드와 정산 패널은 넓은 배치에서 한 화면에
동시에 보인다. 패널을 열어 둔 채 ± 를 누르면 표시가 낡은 값으로 남고, 그것을 맞추려면
"길이가 바뀌었다"를 화면에 알리는 경로를 새로 만들어야 한다. 그 값은 **바로 옆 타이머
다이얼이 이미 보여주고 있다** — 중복 표시를 위해 새 동기화 경로를 만들지 않는다.

## 구조

### 바뀌는 것

**1. 타이머 엔진이 길이 저장을 소유한다.**
`TimerEngineDeps` 에 한 모드의 길이만 쓰는 의존성을 추가하고, 호스트(`timer-host.ts`)가
DB 쓰기를 꽂는다. 엔진은 지금처럼 electron·DB 를 import 하지 않는다.

`adjust()` 는 다음과 같이 재작성된다:

- 대기 중이 아니면 아무 것도 하지 않고 현재 스냅샷을 돌려준다 (예외를 던지지 않는다 —
  IPC 계약의 응답이 스냅샷이고, 비활성 칩을 통과한 요청은 정상적인 무시 대상이다)
- 대기 중이면 새 길이를 계산(하한 1분)하고 → **저장한 뒤** → 엔진 상태를 갱신하고 →
  전이를 발송한다

**2. 모드 → 설정 키 매핑을 한 곳으로 모은다.**
지금 이 매핑은 엔진(`baselineSec`)과 설정 서비스(`globalBaseline`) 두 곳에 흩어져 있다.
쓰기 경로가 추가되면 세 곳이 되므로, 매핑의 소유를 `services/baseline.ts` 로 모은다.

### 사라지는 것

| 대상 | 이유 |
|---|---|
| 엔진의 `idleAdjusted` 플래그와 이를 읽던 3개 분기 (`start`·`startWithTask`·`refreshBaseline`) | 조절값과 기준이 같은 값이 되어 우선순위 판정이 성립하지 않는다 |
| `adjust()` 의 running·paused 분기 (남은 시간 이동 + 시작 앵커 보정) | R3 이 그 상태의 조절을 막는다 |
| `refreshBaseline()` 과 그 호출부 | 화면이 길이를 쓰는 경로가 사라져 호출자가 없다 |
| IPC `settings:getBaseline` · `settings:setBaseline` (채널·계약·preload·핸들러) | 화면 쪽 소비자가 전부 사라진다 |
| `features/baseline/` 3파일 (`BaselineForm`·`BaselineSection`·`useBaseline`) | R1·R6 |
| `baseline-changed` 무효화 | 무효화를 유발하는 화면 동작이 없다 |
| 정산 패널의 `조정` 버튼·보조 문구·길이 표시 줄 | R6 |

### 새로 생기는 것

- `services/baseline.ts` — 한 모드의 길이만 쓰는 함수와 모드 → 설정 키 매핑
- `TimerCard` — 대기 중이 아닐 때 ± 칩 비활성 처리

## 데이터 흐름과 실패 처리

```
칩 클릭 → timer:adjust (IPC)
        → 엔진: 새 길이 계산 (하한 1분)
        → 엔진: 설정에 저장          ← 실패하면 여기서 멈춘다
        → 엔진: durationSec 갱신
        → 스냅샷 반환 + timer:transition 발송
```

**저장을 먼저 하는 것이 이 순서의 요점이다.** 저장이 실패하면 엔진 상태를 건드리지
않으므로 "다이얼은 30분인데 저장은 25분"인 상태가 만들어지지 않는다. `better-sqlite3`
가 동기라 코드 순서가 곧 보장이며, 이는 이미
[ADR-026 §2](../architecture/decisions/adr-026-main-to-renderer-events.md) 가 완료 기록에
쓰는 것과 같은 구도다.

읽는 쪽은 변경이 없다 — 앱 시작·모드 전환·세션 종료 시점에 설정에서 해당 모드 길이를
다시 읽는다 ([timer R1](../features/timer/prd.md)). 달라지는 것은 그 값이 이제 사용자가
마지막에 맞춰 둔 값이라는 사실뿐이다.

## 테스트

**회귀(이번 사건 그대로):** 집중에서 30분으로 조절 → 짧은 휴식으로 전환 → 집중으로 복귀
→ 30분이어야 한다.

**엔진:**

- 대기 중 조절이 해당 모드의 길이 저장을 1회 호출한다 (모드별 3종 각각)
- 실행·일시정지 중 조절은 저장을 호출하지 않고 남은 시간도 바꾸지 않는다
- 하한: 1분에서 더 줄여도 1분이며 저장 값도 1이다
- 저장이 실패(예외)하면 `durationSec` 이 바뀌지 않고 전이도 나가지 않는다

**화면:** 실행·일시정지 중 ± 칩이 비활성이다.

**지우는 테스트:** 실행 중 조절 동작, 조절값 우선순위, `refreshBaseline`, 편집 폼·섹션
관련 전부.

## 비범위

- 첫 실행 온보딩 화면 — 미구현이며 이 변경이 만들지 않는다. 새 설치의 기본값은 시딩이
  계속 담당한다 ([ADR-018 §4](../architecture/decisions/adr-018-first-run-state.md))
- 조절 단위(±1/±5/±10) 변경
- 상시 설정 화면 — R1 이 편집 경로를 타이머로 단일화하므로 필요하지 않다
- 뽀모의 정의·집계 통화 — [ADR-030](../architecture/decisions/adr-030-time-as-progress-currency.md) 그대로다

## 부록 — 이 설계에 이른 과정

1. **관찰:** 집중 30분 조절 후 짧은 휴식을 다녀오니 25분. DB 확인 결과 `focus_min` 은
   25 였다 — 조절값이 저장된 적이 없었다. 스펙대로 동작한 것이었다.
2. **판단:** 정책 위반이 아니라 **정책 자체가 현실과 어긋난** 경우다. 손에 닿는 유일한
   조절 수단이 저장되지 않는 쪽이었다.
3. **방향 선택:** 타이머에서 바로 기준을 바꾸는 쪽으로 결정. 상시 설정 화면 추가·정산
   진입점 강조는 기각 — 전자는 화면을 늘리고, 후자는 "타이머에서 바꾸고 싶다"는 욕구를
   해결하지 않는다.
4. **저장 방식:** 별도 저장 버튼 없이 조절 즉시 기준으로 확정. 저장 버튼은 사용자가
   이미 원하는 값을 만들어 놓은 뒤 한 번 더 확인을 요구하는 단계다.
5. **실행 중 조절:** 막는 쪽으로 결정. 즉시 저장과 임시 조절이 공존하면 "언제 기준이
   바뀌는가"를 사용자가 매번 판단해야 한다.
6. **정산 폼:** 없애는 쪽으로 결정. 편집 경로가 둘이면 어느 쪽이 진짜인지 다시 물어야
   한다.

# 설계: M3a — 주간 계획 (week-plan)

- 날짜: 2026-08-07
- 산출물: `docs/plans/` 의 M3a 구현 계획서 (이 문서 승인 후 작성)
- 지위: 이 문서는 M3a 범위·구조의 승인된 설계 원본이다. **결정을 만들지 않는다** —
  기획 문서(`docs/features/`)·ADR 과 충돌하면 그쪽이 이긴다. 이 문서가 새로 정한 것은
  §6 의 미결 종결 1건뿐이며, 그것도 기획 문서가 "v1 구현 시 재판단"으로 위임한 항목이다.
- 선행: M2 코어 루프 완료 (main `8138982`, [PR #31](https://github.com/easyDong19/dongmodoro/pull/31))

## 결정 요약 (사용자 승인)

1. **M3 을 M3a(주간 계획) / M3b(정산) 로 분할한다.** 통합 시 요구사항 68개·인수 기준
   67개로 M2(계획서 877줄·11 태스크)의 2배가 된다. 분할 근거는 분량이 아니라 **의존
   방향**이다 — 정산은 주간 항목을 대상으로 동작하므로 항목이 없으면 의미 있는 테스트가
   성립하지 않는다. 역방향 의존은 없다.
2. **`weekly_capacity` 는 미설정(NULL) 인 채로 둔다.** 편집 경로를 온보딩·정산 둘로
   한정한 pomo-baseline R25 를 따른다. 기본값 시딩은 R8·R15 가 이미 금지했다.
3. **마일스톤 연결은 M3a 범위 밖.** `milestone_id` 는 항상 NULL 이고 연결 칩 UI 를
   만들지 않는다. week-plan R6 이 미연결을 정상 상태로 정의했으므로 문서 위반이 아니다.
4. **소진 집계 술어는 리포지토리 SQL 한 곳에만 둔다** (§4.1).
5. **기타 행 소진은 차액으로 정의한다** (§4.2).
6. **플래너 확정 요청은 선언형 전체 초안이다** (§5).
7. **week-plan R9 의 미결(항목 est vs 자식 task est 합 어긋남 표시)을 "표시하지 않음"
   으로 닫는다** (§6).

## 1. 문제와 위치

계획의 층위는 셋이다 — 월(이번 달에 뭘 끝낼 건가) · 주(이번 주에 얼마만큼) · 오늘
(지금 뭐부터). 가운데가 비면 두 가지가 무너진다: 큰 목표가 실행 크기로 쪼개지지 않아
매일 즉흥으로 오늘 목록을 짜게 되고(원칙 2 위반), 비교 기준이 없어 기록이 "얼마나 했다"만
남기고 "계획 대비 어땠다"를 말하지 못한다.

M2 는 아래 두 칸(오늘 목록 · 타이머 · 세션 기록)을 세웠다. **가운데 주 레이어가 비어
있어서 `pull` 경로가 죽어 있다** — `TodayRepository.pull` 과 오늘 목록 행의 `출처` 표시
자리는 이미 있으나 가져올 주간 항목이 존재하지 않는다.

M3a 는 그 층을 채워 두 방향의 화살표를 살린다.

```
월: 마일스톤          ← 범위 밖 (milestones 기능)
      ↓
주: 주간 항목 + 예산   ← ★ M3a
      ↓ pull                    ↑ 소진 (세션에서 파생, 저장하지 않음)
오늘: 오늘 목록 → 타이머 → 세션  ← M2 완료
```

## 3. 가용량 미설정은 정상 경로다

`weekly_capacity` 편집 UI 는 pomo-baseline R25 가 **첫 실행 온보딩 / 주간 정산 진입점**
둘로 한정했다. 둘 다 M3a 밖이므로 M3a 에서 이 값은 NULL 이다.

기본값 시딩으로 우회하지 않는다 — R8 이 "미설정은 NULL 이며 오류가 아니다", R15 가
"계획 의사는 사용자가 정한 적 없으면 없는 것이 사실"이라고 정했고, M2 의
`seedSettings` 가 이 키를 의도적으로 제외한 것도 같은 이유다. 0 으로 시딩하면
"예산 0으로 하겠다"는 의사 표시와 "아직 정하지 않았다"가 데이터상 구분 불가해진다.

기획 문서가 이 상태의 화면 동작을 이미 규정해뒀으므로 그대로 따른다:

| 지점 | 미설정일 때 동작 | 근거 |
|---|---|---|
| 예산 입력 | 프리필하지 않고 빈 채로 시작. 비운 채 확정 가능 | pomo-baseline R12, ux-spec §5.2 |
| 총량 과적 경고 | 계산하지 않고 `예산을 정하면 과적을 알려줘요` 만 표시 | ux-spec §5.2 |
| 요일별 부하 그래프 | **막대는 그린다.** 기준선과 초과 판정만 없다 | ux-spec §5.5 |
| 주간 게이지 | 바를 숨기고 소진량만 표시. `소진 / 0` 을 렌더하지 않는다 | week-plan R20 |

부하 막대가 그려지는 이유는 부하값이 `Σ(항목 est / 배정 요일 수)` 로 capacity 없이도
산출되기 때문이다. capacity 는 비교 기준선일 뿐이다.

## 4. 데이터 계층

현재 `WeekItemsRepository` 는 `ensureSystemItem` · `weekOf` 둘뿐이고 `WeeksRepository` 는
`baseline` · `ensure` 둘뿐이다. `MilestonesRepository` 는 없다(M3a 에서 만들지 않는다).

### 4.1 소진 집계 술어 — SQL 한 곳

```sql
count(sessions s JOIN tasks t ON s.task_id = t.id
      WHERE t.week_item_id = <항목>
        AND s.kind = 'focus'
        AND s.local_week = <그 항목의 week>)
```

마지막 줄이 핵심이다. 세션은 기록 시점에 `local_week` 를 1회 계산해 박제하므로
(ADR-009 §2, ADR-011 §3) **모든 focus 세션은 자기 주에서 정확히 한 번만 세어진다.**
일요일 23:50 에 시작해 자정을 넘긴 집중은, 부모 항목이 지난 주 소속이면 지난 주 항목
소진에 들어가지 않고 다음 주의 미분류로 떨어진다.

이 조건이 빠지면 **에러 없이 조용히 틀린 숫자**가 나온다. 그래서 화면·서비스가 각자
조립하지 않고 리포지토리 메서드 하나에만 둔다. week-plan 성공 지표가 "실제 검증 대상은
R8 의 주 조건이 모든 항목 소진 계산 경로에 들어 있는지"라고 명시했다.

**기각:** 항목 목록과 소진을 따로 조회해 도메인 함수에서 결합. 결합 지점이 늘 때마다
조건을 다시 지켜야 한다. M2 의 `today.list`(left join + 서브쿼리 한 방)가 선례다.

### 4.2 기타 행은 차액으로 정의한다

> **정정 (2026-08-07).** 이 절이 인용한 ADR-012 §4 의 수식은 그 자체가 모순을 안고
> 있었다 — 수식은 폐기 항목을 Σ 에 넣는데 바로 다음 문장이 "폐기 항목의 소진은 흡수된다"고
> 약속한다. [ADR-027](../../architecture/decisions/adr-027-other-row-domain.md) 이 이것을
> 정정했고, **정의역·표시 조건의 확정 기준은 이제 그 ADR 이다.** 아래 서술은 그 결론과
> 같지만, 다르게 읽히면 ADR-027 이 이긴다.

```
Σ 의 정의역 = is_system = 0 AND dropped_at IS NULL AND deleted_at IS NULL  (= 목록에 보이는 항목)
기타 행 소진 = 그 주 총 focus 세션 수 − Σ(그 정의역의 항목 소진)
```

표시 조건은 **세 갈래**다 (ADR-027 §3): 미분류 세션이 있다 · 부모 없는 조각이 있다 ·
**기타 행 소진 > 0**. 세 번째를 빠뜨리면 폐기 항목의 소진만 있는 주에서 행이 숨겨져
A24 가 깨진다.

독립 계산하면 두 버그가 열린다 — 시스템 항목이 Σ 에도 기타 행에도 들어가는 **이중
계상**, 그리고 폐기되어 목록에서 사라진 항목의 소진 **누락**. 차액 정의는 둘을
산술적으로 불가능하게 만든다 (ADR-012 §4).

부수 효과: 세션 9개가 달린 항목을 폐기해도 그 9뽀모가 기타 행에 나타나 행방을 추적할
수 있다. "닫히는 게이지" 성공 지표가 검증 대상이 아니라 **정의**가 된다.

표시 조건은 소진이 아니라 존재다 — 미분류 세션이나 부모 없는 조각이 하나라도 있으면
**소진 0 이어도 행을 표시한다** (R17). 그러지 않으면 사용자가 직접 만든 조각이 주간
카드 어디에도 나타나지 않는다.

## 5. 플래너 확정 — 선언형 전체 초안

요청이 초안 목록 전체를 담는다.

```
{ week, budget: number | null,
  items: [{ id: string | null, title, estPomos, days: number[] }] }
```

서버는 그 주의 기존 `is_system = 0` 항목을 조회한 뒤 세 갈래로 판정한다.

| 상황 | 처리 | 근거 |
|---|---|---|
| 요청에 `id` 있음 | **ID 로** 매칭해 update. 자식 task·`origin_week`·`carry_from_id`·`milestone_id` 보존 | R23 |
| 요청에 `id` 없음 | 신규 insert, `origin_week = week` | R6 |
| 기존 ID 가 요청 목록에 없음 | `dropped_at` 기록 (폐기 — 삭제 아님) | R24 |

전체가 `uow.run` 한 번이다 (ADR-015 — 유스케이스 하나 = 트랜잭션 하나). 과적 여부와
무관하게 **항상 성공한다** (R22 — 차단 0건).

**왜 선언형인가:** 플래너에서 기존 항목의 `×` 가 의미하는 바가 곧 "이 목록에서 빠짐 =
폐기"다. 증분 diff 를 클라이언트가 관리하면 "제목이 아니라 ID 로 매칭"(R23) 규칙을
양쪽에서 지켜야 하고, 규칙이 두 곳에 흩어지면 한쪽만 고쳐지는 날이 온다.

**기각:** `{ added, updated, removed }` 증분 페이로드. 페이로드는 작아지나 위 이유로 버린다.

**알려진 약점 (M3a 에서 수용):** 플래너를 열어둔 채 다른 경로로 항목이 생기면 확정 시
"목록에 없음 = 폐기"로 판정된다. M3a 에서 항목 생성 경로는 플래너뿐이라 실제로 발생하지
않지만 구조적으로 열려 있다. 정산은 같은 문제를 확정 요청에 **예외만 담고 나머지는 서버가
재조회**하는 방식으로 닫았다 (weekly-review R29). **M3b 에서 이 충돌이 실제로 발생하면
플래너도 그 방식으로 옮긴다** — 그때 이 문단이 근거가 된다.

`weeks.planned_at` 은 **최초 확정 시각만** 담는다. 주중 재수정으로 다시 확정해도 갱신하지
않는다 (R23) — 이 값이 답하는 질문은 "이 주의 계획을 언제 세웠나"이고 "마지막으로 손댄
시각"이 아니다.

## 6. 미결 종결 — R9 의 est 어긋남은 표시하지 않는다

week-plan R9 의 `⚠️ 가정` 블록이 "드로어에서 항목 est 와 자식 task est 합의 어긋남을
사실로 표시할지"를 미결로 두고 v1 구현 시 재판단하라고 위임했다.

**표시하지 않는 것으로 닫는다.** R9 자체가 두 값을 "서로 다른 질문에 답하는 독립적인 값"
으로 정의했다 — 항목 est 는 "이번 주 이만큼", 조각 est 는 "이 조각 이만큼"이다. 어긋남을
화면에 띄우는 순간 그것이 "맞춰야 할 것"이라는 판단을 주입하게 되고, 앱이 사용자를
판단하지 않는다는 원칙 6과 부딪친다.

이 종결은 **같은 PR 에서 week-plan/prd.md 의 해당 가정 블록을 갱신**해 반영한다
(CLAUDE.md 의 "용어·정의 변경은 같은 PR" 규칙과 같은 취지).

## 7. 이벤트와 무효화

> **정정 (2026-08-07, 3인 리뷰 후).** 이 절의 원래 서술 — "M2 가 주간 키를 이미 넣어뒀으므로
> M3a 가 주간 쿼리를 붙이는 순간 **저절로 동작한다**" — 은 **사실이 아니었다.**
>
> M2 가 무효화하는 키는 `keys.weekItems(w)` = `['week', w, 'items']` 이고, 주간 카드
> 쿼리의 키는 `['week', w]` 다. TanStack Query 의 무효화는 **주어진 키를 접두사로 갖는
> 쿼리**를 잡으므로 **긴 키로 짧은 키를 잡을 수 없다.** 방향이 반대다. 게다가
> `keys.weekItems` 를 실제 쿼리 키로 쓰는 곳은 현재 0건이라, M2 의 주간 무효화 4건은
> **어떤 쿼리에도 걸리지 않는 장식**이었다.
>
> 그대로 두면 타이머로 1뽀모를 태워도 주간 게이지·항목 도트가 오르지 않는다 — 이
> 마일스톤 Goal 의 마지막 화살표가 끊긴다. 구현 계획서 Task 5 가 이것을 정정한다:
> `keys.weekItems` 를 제거하고 `keys.week(w)` 로 대체한 뒤, 기존 4개 사건이 그 키를
> 무효화하게 한다. 죽은 팩토리 항목을 남기지 않는 이유는 나중에 누군가 그것을 쿼리 키로
> 쓰고 "무효화되는 줄" 알게 되기 때문이다.

정정 후의 상태는 이렇다. 기존 4개 사건(`session-recorded`·`capture-recorded`·
`pull-changed`·`task-toggled`)이 `keys.week(w)` 를 무효화하고, `clock-boundary` 는 주가
바뀔 때 `keys.weekAll()` 을 민다. 여기에 추가할 사건은 둘이다.

| 사건 | 무효화 대상 | 비고 |
|---|---|---|
| `plan-confirmed` | 확정한 주 + 그 주가 오늘 주면 오늘 목록 | 신규 |
| `item-completed` | 그 항목의 주 | 신규 |

달력 키는 **이벤트 payload 의 저장값**을 쓴다. renderer 에서 재계산하면 ADR-025 §2 의
"키 속 달력 키는 `useClock()` 또는 payload 저장값만" 규칙을 어긴다.

## 8. UI 구성

- 카드 모드 전환은 **같은 카드 안에서** 일어난다. 새 창·모달이 아니다 (ux-spec §1).
- 항목 드로어는 항목 행 아래 **인라인 펼침**이며 모달이 아니다 (ux-spec §6). 열려 있는
  동안 타이머·오늘 목록이 계속 동작한다.
- `+ 오늘로` 는 **원클릭 pull** 이다. 유자격 조각(미완료·미삭제·오늘 pull 행 없음) 중
  생성순 첫 번째를 바로 가져온다. **유자격 조각이 0개면 드로어가 열린다** — 첫 pull 은
  선택이 아니라 생성이기 때문이다 (R12, ux-spec §3.1·§6.4).
- 앱 레이아웃은 카드 3장이 되지만 **반응형·3컬럼은 만들지 않는다** (app-shell, M4).
  M2 의 임시 배치를 확장한다.
- **주간 카드는 `ClockGate` 안쪽에 둔다.** M2 에서 `useClock()` 캐시가 차기 전 마운트로
  콜드 스타트 크래시가 났고(`7e0d472`), 주간 카드는 주 키에 더 강하게 의존한다.
  이것을 구현 계획서의 명시 항목으로 적는다.

## 9. 시각 규칙 (어기기 쉬운 것)

- 과적 표시에 **`--danger`·경고 아이콘·"초과했습니다" 류 단정 금지.** `--amber` 글로우 +
  `+N` 배지 + 질문형 문구까지만 (R21, principles §1·§2).
- 과적 안내는 **이 화면에서 실제로 가능한 조작만** 제시한다 — est 낮추기 / 항목 덜어내기 /
  예산 올리기. "다음 주로 미루기"는 플래너의 조작이 아니라 정산의 이월이다 (R22).
- 편집 대상 주를 `다음 주` 로 바꾸는 것은 "미루기"가 아니라 **다른 주를 편집하는 것**이므로
  과적 안내에서 권하지 않는다.
- 이모지 금지. 아이콘은 lucide, 뽀모 도트는 토큰 기반 커스텀 (principles §6).

## 10. 함정 (구현 계획서에 그대로 옮길 것)

| 함정 | 결과 | 방어 |
|---|---|---|

## 11. 테스트 전략

- **리포지토리 계약** (인메모리 실 SQLite — ADR-023 §3): 주 경계 넘긴 세션이 지난 주
  항목에 안 세어짐(A10), 폐기 항목 소진이 기타 행에 흡수됨(A24), 소진 0 인 조각만 있어도
  기타 행 표시(A23), 제목 변경 후 자식 조각 유지(A30).
- **서비스**: 확정 원자성(중간 실패 시 전부 롤백), `planned_at` 최초 유지(A31), 세션 9개
  달린 항목 폐기 시 전부 보존(A32).
- **남은 몫 클램프** `max(0, est − 소진)` (R9·A12): 화면에 남은 몫을 그리는 것은 정산
  (M3b)이지만 **규칙의 소유는 week-plan R9** 이므로 순수 함수로 여기서 만들고 테스트한다.
  M3b 가 이 함수를 소비한다 — 두 곳에서 각자 클램프하면 한쪽만 고쳐지는 날이 온다.
- **렌더 계약**: 모드 전환, capacity 미설정 경로(프리필 없음·기준선 없음), 과적 표시에
  `--danger`·경고 아이콘 0건(A28), est 스테퍼 하한 1(A6).

## 12. M3b 로 넘기는 것

정산(weekly-review, 요구사항 40개)은 별도 스펙·계획서를 갖는다. M3a 가 M3b 에 남기는
연결점은 셋이다.

1. 주간 항목이 존재해야 정산의 이월 3택이 대상을 갖는다.
2. `weekly_capacity` 편집 진입점이 정산 패널에 생기는 순간 §3 의 축소분(예산 프리필·
   요일 부하 기준선)이 자동으로 살아난다.
3. §5 의 알려진 약점(선언형 확정의 동시성)이 M3b 에서 실제로 발생하면 재조회 방식으로 옮긴다.

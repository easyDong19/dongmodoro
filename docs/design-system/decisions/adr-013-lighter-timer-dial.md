# ADR-013 (design-system): 타이머 다이얼의 상한을 낮추고, 숫자와 링을 가볍게 한다

- 상태: accepted (2026-09-24)
- Supersedes: [design-system ADR-012](./adr-012-fluid-timer-dial.md) **§2 의 상한값**(400px) ·
  **§3 의 비율**(25.45%) · **§4 의 굵기**(10). §1(크기 기준은 다이얼 한 변, `min(가로, 세로)`)과
  §5(창 세로 하한 640px)는 그대로 유효
- 관련 문서: [tokens.md §2.2·§2.3·§9](../tokens.md)

## Context

ADR-012 로 다이얼이 칸에 비례해 커지게 된 뒤 "타이머가 너무 크다"는 피드백이 나왔다.
빌드 산출물을 임시 프로필로 띄워 실측하면 원인은 두 가지다.

| 무엇 | 값 (기본 창 1280×800) | 비교 |
|---|---|---|
| 다이얼 한 변 | **400px — 이미 상한** | ADR-012 §2 가 "기본 창이 상한에 정확히 닿는 값"으로 정했다. 대부분의 사용자는 늘 최대 크기를 본다 |
| 숫자 | **102px**, 굵기 400 | 바로 아래 세션 라벨(12px)의 8.5배, 카드 제목(14px)의 7배 |
| 링 굵기 | **20px** | 지름의 5% 라 링이 굵은 띠로 읽힌다 |

크기보다 **무게**가 문제다. 화면에서 가장 큰 글자가 굵기까지 갖추고 20px 띠에 둘러싸여,
Milestone·Sprint·오늘 카드를 전부 누른다. 상한만 낮추면(대안 A) 굵은 숫자와 띠는 그대로
남고, 고정 크기로 되돌리면(대안 D) 최대화 시 카드가 비어 ADR-012 가 풀던 문제로 돌아간다.

## Decision

### 1. 상한을 400px → 320px 로 낮춘다

```
--timer-dial-max: 5.71em;   /* ≈320px, was 7.14em */
```

한 변 공식(ADR-012 §1)은 그대로다. 창이 작으면 여전히 세로 여유를 따라 줄고, 기본 창과
그보다 큰 창은 320px 에 멈춘다. 단위가 `em` 인 이유도 ADR-012 §2 그대로다.

### 2. 숫자 비율을 25.45% → 22% 로 내린다

```
.timer-digits { font-size: 22cqmin; }
```

숫자가 한 변에서 파생된다는 ADR-012 §3 의 구조는 유지한다 — 비율만 바꾼다. 곡선이
하나라 링과 숫자가 어긋나는 구간이 여전히 없다.

**대가:** 하한(220px)에서 숫자가 `--text-display`(56px) 가 아니라 ≈49px 이 된다.
ADR-012 §3 이 정한 "하한에서 정확히 `--text-display`" 는 더 성립하지 않는다.
`--text-display` 는 이제 **다이얼 하한(`--timer-dial-min`)을 `em` 으로 풀기 위한 기준값**
으로만 남는다. 49px 도 이 화면의 다른 어떤 글자보다 세 배 이상 크므로, 가장 작은 창에서
숫자가 읽히지 않을 위험은 없다.

### 3. 숫자 굵기를 300 으로 두고, 이를 위해 `--weight-light` 를 추가한다

```
--weight-light: 300;   /* 타이머 숫자 전용 */
```

tokens.md §2.3 은 "3단계 외 굵기 추가 금지" 다. 이 결정은 그 규칙에 **예외 하나**를 낸다.

- 근거: 이 화면에서 가장 큰 글자는 굵기를 낮춰야 비로소 다른 카드와 같은 무게가 된다.
  크기를 더 줄이는 쪽으로 같은 효과를 내면 최대화 창에서 다이얼이 카드 안에서 떠 버린다.
- 범위: **타이머 숫자 전용** 이다. 본문·제목에 쓰지 않는다. 300 이 12~14px 에서 쓰이면
  대비와 판독성이 떨어진다.
- `--weight-bold` 의 용도 칸에 있던 "타이머 숫자" 는 사실과 달라서(구현은 400 이었다)
  함께 고친다.

Azeret Mono 는 가변 폰트(100–900)로 번들되므로 추가 파일이 없다.

### 4. 링 굵기를 viewBox 기준 10 → 6 (지름의 3%)

굵기가 지름에 비례한다는 ADR-012 §4 의 원리는 유지한다 — 비율만 바꾼다. 320px 에서
9.6px, 하한 220px 에서 6.6px 이다.

## 실측 (2026-09-24, 빌드 산출물 · 임시 프로필)

`scrollHeight = clientHeight` 는 타이머 카드가 내용을 잘라내지 않았다는 뜻이다.

| 창 크기 | 다이얼 칸 (가로×세로) | 한 변 | 숫자 | 링 | 크기를 정한 것 | 잘림 |
|---|---|---|---|---|---|---|
| 720×640 (창 하한) | 222×259 | **222px** (was 222) | 48.8px (was 56.5) | 6.7px | 하한 | 없음 (552 = 552) |
| 1280×800 (기본) | 458×419 | **320px** (was 400) | 70.3px (was 101.8) | 9.6px | 상한 | 없음 (712 = 712) |
| 1728×949 (최대화) | 906×568 | **320px** (was 400) | 70.3px (was 101.8) | 9.6px | 상한 | 없음 (861 = 861) |
| 1600×660 (넓고 낮음) | 778×279 | **279px** (was 279) | 61.4px (was 71.1) | 8.4px | 세로 여유 | 없음 (572 = 572) |

## 검토한 대안

비교 목업에서 네 안을 같은 칸 실측값으로 나란히 놓고 골랐다.

| 안 | 내용 | 기본 창 (한 변 / 숫자) | 기각 이유 |
|---|---|---|---|
| A | 상한만 280px | 280 / 71 | 1024px 창부터 곧바로 상한이라 창 크기에 거의 반응하지 않는다. 굵기·띠는 그대로 |
| B | 칸의 70% 만, 최대 340px | 293 / 75 | 작은 창에서 사실상 하한에 붙고, 최대화 시 숫자 87px 로 여전히 크다 |
| **C** | **상한 320px + 숫자 22%·300 + 링 3%** | **320 / 70** | **채택** |
| D | 240px 에 거의 고정 | 240 / 61 | 최대화 시 카드가 비어 ADR-012 이전으로 돌아간다 |

## Consequences

- (+) 기본 창에서 숫자가 102 → 70px, 링이 20 → 9.6px. 크기보다 무게가 더 많이 준다.
- (+) 창에 비례해 커지는 ADR-012 §1 의 구조는 그대로라, 낮은 창에서 잘리는 것은 여전히
  다이얼뿐이다.
- (−) `--text-display` 가 렌더되는 자리가 완전히 사라지고, 다이얼 하한을 푸는 기준값으로만
  남는다. 이 토큰 이름을 보고 "타이머 숫자는 56px" 이라고 읽으면 틀린다 — tokens.md §2.2 의
  용도 칸이 이를 적는다.
- (−) 굵기 3단계 규칙에 예외가 생긴다. "여기도 300 이던데" 를 본문 굵기의 근거로 쓰지 않는다.
- (−) 단위 테스트로는 볼 수 없다(jsdom 에 레이아웃이 없다). 검증은 여전히 실제 창 실측이다.

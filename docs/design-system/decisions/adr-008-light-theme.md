# ADR-008 (design-system): 라이트 모드 도입 — ADR-006 §1 을 뒤집는다

- 상태: **§4 는 superseded by [ADR-010](./adr-010-app-owned-theme.md)** (2026-08-11) — 전환 경로가
  뒤집혔다. OS 추종과 `system` 선택지를 없애고 앱이 테마를 소유하며, 전환은 트레이 서브메뉴가
  아니라 타이틀바의 2택 세그먼트다. **§1·§2·§3·§5 는 계속 유효하다** — 특히 §2 의 라이트
  팔레트 13개와 §5 의 고대비 우선 규칙은 그대로다. 아래 §4 본문은 이력으로 그대로 둔다
  (docs/CLAUDE.md 의 ADR 규칙).
  - §1 의 CSS 두 경로 구조도 살아 있다. 다만 `[data-theme]` 경로의 **용도가 바뀌었다** —
    런타임 전환 채널이 아니라 테스트·문서 전용 진입점이다 (ADR-010 §3).
- 상태(원본): accepted (2026-08-05)
- **supersedes: [ADR-006](./adr-006-theme-scope.md) §1** (v1 다크 전용). §2~§4(고대비 대응·제2 신호)는 그대로 유효하다
- 사용자 결정: 2026-08-05 (라이트 모드 추가 · OS 따라가기 + 트레이 수동 전환 · 유리 유지)

## Context

[ADR-006 §1](./adr-006-theme-scope.md) 이 같은 날 "v1 은 다크 전용이고 `prefers-color-scheme`
분기를 만들지 않는다"를 확정했고, 그 대가로 **"라이트를 도입하면 토큰 체계 전면 재설계가
필요하다"** 를 명시 수용했다. 사용자가 라이트 모드를 요청해 그 결정을 뒤집는다.

**실측 결과 "전면 재설계"는 필요하지 않았다.** 토큰 이름 중 라이트에서 오해를 부르는 것은
`--bg-deep` 하나뿐이고(`--ink`·`--glass`·`--glow-*` 는 이미 의미 기반이다), 이름을 유지하고
**값만 테마별로 재정의**하면 기능 문서 8개는 한 줄도 고치지 않아도 된다. ADR-006 이 예상한
비용은 과대평가였다.

### 다크 액센트는 라이트에서 전멸한다

| 토큰 | 라이트 배경 위 | 판정 |
|---|---|---|
| `--teal` `#6fd4b8` | 1.66:1 | 실패 |
| `--amber` `#f0b671` | 1.69:1 | 실패 |
| `--danger` `#e8907e` | 2.25:1 | 실패 |

어두운 배경용으로 고른 밝은 색이므로 당연한 결과다. 라이트용 액센트를 새로 만들어야 한다.

### 두 가지 규칙이 테마에 따라 뒤집힌다

**① 최악 배경의 방향.** 다크는 글자가 밝으므로 **배경이 밝아질수록** 대비가 나빠져
최악이 `광원 위 --glass-strong` 이었다. 라이트는 글자가 어두우므로 **배경이 어두워질수록**
나빠져 최악이 **`광원 위, 카드 없음`** 이다. 카드 밖에 텍스트가 있는 자리는
**타이틀바(앱 이름·날짜 라벨)** 이며, 그것이 라이트의 판정 지점이다.

**② 유리의 방향.** 다크는 `카드 = 배경 + 흰색 5.5%` 로 카드가 배경보다 밝다. 라이트에서
이 관계를 유지하려면 **페이지 배경이 흰색보다 어두워야** 한다. 페이지를 거의 흰색으로 두면
흰 카드가 배경과 구분되지 않는다.

## Decision

### 1. 토큰 이름을 유지하고 값만 테마별로 재정의한다

```css
:root { /* 다크 = 기본값 */ }

@media (prefers-color-scheme: light) {
  :root:not([data-theme="dark"]) { /* 라이트 값 */ }
}
:root[data-theme="light"] { /* 라이트 값 */ }
```

- **다크가 기본값**이다 — OS 정보가 없거나 판정 실패 시 다크로 렌더된다.
- `data-theme` 속성이 OS 선호를 덮어쓴다(§4 의 수동 전환).
- 기능 문서·ux-spec 은 **토큰 이름만 참조하므로 수정 대상이 아니다.**
- `--bg-deep` 이라는 이름은 라이트에서 부정확하다. **개명하지 않는다** — 기능 문서 8개와
  ADR 여러 건의 참조를 바꾸는 비용이 이름의 정확성보다 크다. 이 부정확을 알려진 부채로
  기록한다.

### 2. 라이트 팔레트 (전수 검증 완료, 실패 0건)

| 토큰 | 다크 | 라이트 | 라이트 대비 |
|---|---|---|---|
| `--bg-deep` | `#0c1a16` | **`#e7eeec`** | — (L 92%, 카드가 떠오르게 흰색보다 어둡다) |
| `--glass` | 흰색 0.055 | **흰색 0.72** | — |
| `--glass-strong` | 흰색 0.09 | **흰색 0.92** | — |
| `--glass-border` | 흰색 0.14 | **잉크 0.14** | 장식용 |
| `--glass-border-soft` | 흰색 0.08 | **잉크 0.08** | 장식용 |
| `--control-border` | 잉크 0.45 | **잉크 0.50** | 3.35:1 |
| `--ink` | `#eef4ef` | **`#0c1a16`** | 13.63:1 (타이틀바) / 16.61:1 (카드) |
| `--ink-dim` | 잉크 0.60 | **잉크 0.65** | 4.97:1 (타이틀바) / 5.40:1 (카드) |
| `--ink-faint` | 잉크 0.32 | **잉크 0.38** | 면제 전용 |
| `--teal` | `#6fd4b8` | **`#216e59`** | 4.66:1 |
| `--amber` | `#f0b671` | **`#8f550f`** | 4.61:1 |
| `--danger` | `#e8907e` | **`#b13820`** | 4.63:1 (아이콘 3:1 요건) |
| 광원 실효 상한 | 0.20 | **0.10** | — |

- 라이트 잉크는 **다크의 배경색(`#0c1a16`)을 그대로 재사용**한다. 두 테마가 같은 두 색을
  뒤집어 쓰는 구조라 색온도가 자동으로 맞는다.
- 액센트는 **색상(hue)·채도를 그대로 두고 명도만 내렸다** — teal 163° / amber 33° /
  danger 13° 가 두 테마에서 같다. 그래서 principles §3 의 상태 → 색 매핑 4행이 테마와
  무관하게 유지된다.
- `--ink-dim` 알파가 라이트에서 0.60 → 0.65 인 이유는 판정 지점이 **타이틀바(카드 밖)** 라서다.
  0.60 은 카드 위에서는 4.58:1 로 통과하지만 타이틀바에서 4.27:1 로 미달한다.
- 라이트 광원 상한 0.10 은 대비가 아니라 **미학** 근거다 — 밝은 배경의 컬러 광원은 탁해진다.
  대비만 보면 0.18 에서도 `--ink` 는 12.45:1 로 여유가 크다.

### 3. 유리를 유지하고 관계만 뒤집는다

라이트에서도 blur·하이라이트·섬도우를 쓴다. 페이지 배경을 L 92% 로 두어 **흰 카드가 위로
떠오르는** 관계를 만들고, 다크의 "카드가 배경보다 밝다"를 그대로 보존한다.

- `--glass-highlight` 는 라이트에서 흰색 알파를 높인다(위 모서리 광택).
- `--glass-shadow` 는 검정 대신 **잉크 기반**으로 두고 알파를 낮춘다 — 라이트에서 순검정
  그림자는 지저분하다.
- `--glass-backdrop`(blur 24px saturate 140%)은 두 테마 공통이다.

### 4. 전환 경로 — OS 따라가기 + 트레이 수동 전환

| 항목 | 규칙 |
|---|---|
| 기본 | `prefers-color-scheme` 로 OS 를 따른다 |
| 수동 | **트레이 메뉴에 `테마` 서브메뉴** — `시스템 따라가기` / `라이트` / `다크` 3택 |
| 저장 | `settings` 테이블의 `theme` 키. 값은 `system` / `light` / `dark`, 기본 `system` |
| 새 화면 | **만들지 않는다** — app-shell PRD R35 의 "탭·컬럼을 늘리지 않는다"를 지킨다 |

트레이 메뉴 그룹이 하나 늘어난다: `창 열기` / `테마 ▸` / `종료`. app-shell ux-spec §6.5 가
"구분선 위 그룹은 미래의 트레이 타이머 조작 자리"로 예약해 두었으므로, 테마는 그 그룹에
넣지 않고 **자기 그룹**을 갖는다.

`settings` 에 `theme` 키가 추가되지만 그 테이블은 key-value 이므로 **마이그레이션이 필요
없다.** ADR-011 §1 의 사용 키 목록에 한 줄이 늘어난다.

이 항목은 pomo-baseline R25("길이·가용량 편집 경로는 온보딩과 정산 진입점 2개뿐")와
충돌하지 않는다 — 그 규칙은 베이스라인 값의 편집 경로에 관한 것이고, 테마는 표시 설정이다.

### 5. 고대비 모드는 테마보다 우선한다

`forced-colors: active` 에서는 두 테마 모두 [ADR-006 §2](./adr-006-theme-scope.md) 를
따른다 — 유리·blur·광원을 포기하고 시스템 색을 쓴다. OS 가 이미 밝고 어두움을 결정하므로
`data-theme` 은 그 환경에서 아무 효과가 없다. ADR-006 의 §2~§4 는 이 ADR 이 뒤집지 않는다.

## Consequences

- (+) 라이트 모드가 실제로 성립한다 — 13개 항목 전수 검증에서 실패 0건.
- (+) **기능 문서 8개를 고치지 않는다.** 토큰 이름 강제(principles §5)가 만든 이득이다.
- (+) 액센트가 색상을 공유하므로 상태 → 색 매핑이 테마와 무관하다.
- (+) 라이트가 대비 여유가 더 크다(본문 16.61:1 대 다크 9.63:1). 접근성 관점에서는 라이트가
  안전한 쪽이다.
- (−) **테마마다 판정 배경이 다르다**(다크: 광원 위 glass-strong / 라이트: 광원 위 카드 밖).
  대비를 검증할 때 테마별로 다른 배경을 써야 하며, 이것을 잊으면 통과한 것처럼 보인다.
  principles §7 에 두 배경을 함께 명시한다.
- (−) `--bg-deep` 이름이 라이트에서 부정확하다(§1 에서 부채로 수용).
- (−) 색 토큰이 12개 × 2테마 = 24개 값이 된다. 값 하나를 바꿀 때 두 테마를 함께 봐야 한다.
- (−) 트레이 메뉴 그룹이 2개 → 3개로 늘어난다. app-shell ux-spec §6.5 를 갱신해야 한다.
- (−) 와이어프레임이 두 테마를 모두 보여줘야 하므로 미리보기 토글이 필요하다(제품 UI 가
  아니라 문서 크롬이다).

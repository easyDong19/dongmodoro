# ADR-006 (design-system): 테마 범위 — 다크 전용과 고대비 모드 최소 대응

- 상태: accepted (2026-08-05)
- 사용자 결정: 2026-08-05 (다크 전용 확정 · 고대비 최소 대응)
- 관련: [ADR-002](./adr-002-glass-surface-tokens.md) (유리 표면), [ADR-003](./adr-003-contrast-baseline.md) (대비 기준)

## Context

`prefers-color-scheme`·라이트 모드·`forced-colors` 가 저장소 문서 전체에 **0건**이었다.
색 토큰은 어두운 배경 하나만 전제하는데, **그것이 결정인지 누락인지 문서가 답하지 못하는
상태**였다.

[PRODUCT.md](../../../PRODUCT.md) 에서 대상 OS 가 **macOS · Windows · Linux 셋 다**로
확정되면서 이 공백이 실제 리스크가 됐다. Windows 고대비 모드(`forced-colors: active`)는
OS 가 색을 강제로 덮어쓴다 — 유리 표면·반투명 텍스트·`backdrop-filter` 가 전부 무력화되고,
최악의 경우 글자와 배경이 같은 색이 되어 화면을 읽을 수 없다.

또한 이 앱에는 **색만으로 구분되는 상태**가 있다. 색이 강제로 교체되면 그 구분이 사라진다.
어디가 그런지 전수 확인했다.

| 상태 표현 | 색 외의 신호 | 판정 |
|---|---|---|
| 뽀모 도트 채움 / 미채움 | 채움 = solid, 미채움 = 윤곽선만 | 모양 차이 있음 |
| 뽀모 도트 초과 | `+N` 배지 + lucide `Flame` 동반 (규정된 필수 요소) | 배지·아이콘이 신호 |
| 캘린더 기본 점 / 진한 점 | 지름 차이 (4px / 6px) | 크기 차이 있음 |
| 캘린더 "오늘" | `--weight-semibold` 동반 | 굵기가 신호 |
| 캘린더 "선택" | 배경 + 보더 | 보더가 남는다 |
| **요일 핍 4상태** | **지난 = 불투명도만, 오늘 = 색만** | **신호 없음** |
| **정산 3택 선택 상태** | **배경 + 색만** | **신호 없음** |

즉 제2 신호가 필요한 곳은 **2군데**다. 나머지는 이미 갖고 있다.

## Decision

### 1. v1 은 다크 전용이다 — 누락이 아니라 결정이다

- 라이트 모드는 **v1 바울로 없다.** OS 가 라이트 모드여도 앱은 다크로 렌더된다.
- `prefers-color-scheme` 분기를 만들지 않는다. 토큰은 단일 값으로 유지한다.
- 토큰 이름을 의미 기반(`surface` / `on-surface` 등) 2생 구조로 미리 바꾸지 않는다 —
  지금 그 작업의 비용(모든 기능 문서의 토큰 이름 교체)이 나중 라이트 모드 추가의 비용보다
  크다고 판단했다. 라이트 모드를 도입하면 **그때 토큰 체계를 2생으로 재설계하는 ADR** 을
  낸다. 이 대가를 명시적으로 수용한다.

### 2. 고대비 모드는 유리를 포기하고 시스템 색을 따른다

`@media (forced-colors: active)` 에서:

- `backdrop-filter` 를 **끈다** — 시스템 색 위의 blur 는 의미가 없고 성능만 쓴다.
- 유리 표면의 반투명 배경 대신 시스템 색(`Canvas`)을 쓰고, 모든 카드·컨트롤 경계에
  `1px solid CanvasText` 를 준다. 반투명 보더는 강제 색 아래에서 사라진다.
- 텍스트는 `CanvasText`, 선택·활성 상태는 `Highlight` / `HighlightText` 를 따른다.
- 배경 라디얼 광원과 별을 **렌더하지 않는다.** 강제 색 환경에서 장식 그라디언트는
  판독을 방해할 뿐이다.
- `forced-color-adjust: none` 을 쓰지 않는다 — OS 의 선택을 덮어쓰는 것이 이 결정의
  반대 방향이다.

### 3. 색만으로 구분되던 2군데에 제2 신호를 넣는다

이것은 고대비 모드만을 위한 것이 아니다. 색각 이상 사용자에게도 같은 문제였다.

**요일 핍 (week-plan ux-spec §3.2)** — 4상태를 모양으로 구분한다.

| 상태 | 기존 | 추가되는 제2 신호 |
|---|---|---|
| 미배정 | `--ink-faint` | 그대로 (부재 표현) |
| 배정 · 지난 요일 | `--teal` 흐리게 | **윤곽선만** (속을 비운다) |
| 배정 · 오늘 | `--amber` + 글로우 | **바깥 링 1겹** (지름이 커진다) |
| 배정 · 다가올 요일 | `--teal` | **solid 채움** |

불투명도만으로 "지난"을 표현하던 것이 문제였다 — 불투명도는 강제 색 아래에서 사라진다.

**정산 3택 세그먼트 (weekly-review ux-spec §5.2)** — 선택 상태에 **보더를 추가**한다.
`--glass-strong` 배경은 강제 색 아래에서 사라지므로, 선택된 세그먼트만 1px 보더를 갖는다.
`aria-pressed` 는 스크린리더용이고 시각 신호를 대체하지 않는다.

### 4. 고대비 모드는 "읽을 수 있음" 까지만 보장한다

브랜드 인상을 강제 색 환경에서 재현하려 하지 않는다. 목표는 **모든 정보가 판독 가능하고
모든 조작이 도달 가능**한 것이며, 유리·광원·글로우의 상실은 수용한다.

## Consequences

- (+) 다크 전용이 기록된 결정이 되어, 다음 사람이 "라이트 모드를 잊었나" 를 묻지 않는다.
- (+) Windows 배포가 고대비 사용자를 배제하지 않는다.
- (+) 제2 신호 2건은 고대비뿐 아니라 **색각 이상**에도 효과가 있다. 특히 요일 핍의
  teal/amber 구분은 적녹 색각 이상에서 원래도 약했다.
- (−) 요일 핍의 시각 언어가 조금 복잡해진다(채움/윤곽/링 3형태). 밀도가 높은 7개 핍에서
  5px 지름으로 이 구분이 실제로 읽히는지 **구현 후 확인이 필요하다** — 안 읽히면 핍 지름을
  키우는 것이 다음 수단이다.
- (−) 라이트 모드를 나중에 도입하면 토큰 체계 전면 재설계가 필요하다(§1 에서 명시 수용).
- (−) `forced-colors` 분기를 유지해야 하므로 스타일 코드가 한 겹 늘어난다. 카드·컨트롤·
  배경 3군데로 한정되어 관리 비용은 작다.
- (−) 고대비 모드 실측은 Windows 실기에서만 가능하다. 구현 후 검증 항목으로 남는다.

## A. 넘침을 어떻게 처리하나

### Q1. 목록이 카드보다 길어지면 무엇이 일어나야 하나

**배경/문제**: 오늘 목록·`결과물` 에 항목을 여러 개 넣으면 내용이 유리 카드의 둥근
모서리 밖까지 그려졌다. 원인은 정책이 아니라 배선이었다 — 주간 카드(WeekCard)는
루트에 `h-full` 이 있어 내부 `overflow-y-auto` 가 정상 발동하는데, 나머지 카드는
루트가 내용 높이로 자라 스크롤 기준 높이가 영영 성립하지 않았다. 오늘 목록은
스크롤 설정 자체가 없었다.

**선택지**:

- **카드 안에서 목록만 스크롤** — 카드 크기가 안정되고 이웃 카드를 건드리지 않는다.
  이미 WeekCard 가 쓰는 문법이라 새 패턴이 아니다.
- 카드가 내용만큼 자람(현상) — 한 카드의 데이터량이 다른 카드의 가용 공간을 잠식한다.
- 항목 수 제한 — 데이터를 UI 사정으로 막는 것이라 기획 원칙(개수를 막지 않는다,
  milestones R4)과 충돌한다.

**결정**: **카드 안에서 목록만 스크롤.** 카드 골격은 창 크기에서만 결정되고,
데이터량은 스크롤로 흡수한다.

**이유** (사용자 원문):

> 지금 디자인 상 문제가 리스트들이 여러개 추가될때 카드들을 벗어나는 문제가 생김
> 내 생각에는 스크롤이 생겨야 한다고 생각하거든

AI 도 같은 의견이었다 — 코드베이스가 이미 그 방향으로 설계돼 있었고(WeekCard),
버그는 방향이 아니라 높이 사슬이 끊긴 배선이었다.

**파생**: → Q2 (`결과물` 카드는 하한만 있고 상한이 없어 스크롤이 성립하려면 상한이
필요하다)

### Q2. `결과물` 카드의 상한 — % 인가 px 인가

**배경/문제**: `결과물` 섹션은 `min-h-[148px] shrink-0` 으로 하한만 있었다. 항목이
늘면 무한정 자라 같은 컬럼의 캘린더(`flex-1`)가 그만큼 짓눌렸다 — 사용자가 보고한
"캘린더가 밀리는" 버그의 원인. 스크롤이 발동하려면 자람이 멈추는 상한이 필요하다.

**선택지**:

- **컬럼의 40% (`max-h-[40%]`)** — 창 높이에 비례해 유연하다. 이 앱은 창 높이가
  가변이라 큰 화면에서는 더 보여주고 작은 화면에서는 캘린더 몫을 지킨다.
- 고정 px (예: 280px) — 예측 가능하지만 창이 크면 낭비, 작으면 여전히 캘린더를
  짓누를 수 있다.

**결정**: **컬럼의 40%.** 하한 `min-h-[148px]` 는 유지한다 (달 이동 시 캘린더가
출렁이는 기존 버그의 방지선이라 별개 근거로 서 있다).

**이유** (사용자 원문):

> 상한방식은 %이며

AI 추천(%)을 사용자가 그대로 채택했다.

## B. 조치 내역 (구현 결정)

사용자 승인 범위 안에서 AI 가 내린 구현 수준의 결정들이다.

### Q3. 높이 사슬 복구 — 왜 `결과물` 섹션만 flex 컨테이너인가

캘린더·오늘 섹션은 `flex-1` 이라 높이가 확정이어서 카드 루트에 `h-full`(%) 을 주면
풀린다 — WeekCard 와 같은 문법. 그러나 `결과물` 섹션은 내용 따라 자라는(auto) 높이라
% 가 성립하지 않는다. 상한에 닿았을 때 자식을 줄이는 길은 flex 수축(`min-h-0`)뿐이라,
그 섹션만 `flex flex-col` 컨테이너로 바꿨다. 이 비대칭은 CSS 제약이지 취향이 아니며,
App.tsx 주석으로 남겼다.

### Q4. 보관 목록을 스크롤 영역 안으로

MilestoneCard 의 보관 목록은 원래 스크롤 `ul` 바깥에 있어, 펼치는 순간 상한을 우회해
카드를 통째로 키웠다. 활성 목록·이월 안내·보관 목록을 한 스크롤 영역으로 묶고,
제목·배지·추가 버튼은 바깥에 고정했다 — 항목이 몇 개든 추가 진입점이 밀려나지 않는다.
오늘 목록의 직접 입력 폼도 같은 이유로 스크롤 밖 하단 고정이다.

### Q5. `overflow-hidden` 안전망

다섯 카드 섹션 전부에 `overflow-hidden` 을 얹었다. 내부 스크롤 사슬이 미래에 또
끊겨도 내용이 유리 카드 밖으로 그려지는 최악은 막는다. `.card` 클래스는 표면만
소유한다는 규율(global.css)이 있어 클래스가 아니라 App.tsx 의 섹션에 얹었다.

### Q6. 검증은 e2e 로

jsdom 은 레이아웃을 계산하지 않아 "스크롤이 발동했나"를 유닛 테스트로 잴 수 없다.
[card-overflow.spec.ts](../../e2e/card-overflow.spec.ts) 가 임시 프로필로 항목을
15개(오늘)·10개(`결과물`) 넣고 `scrollHeight > clientHeight`·카드 상한·캘린더 생존을
단언한다. 수정 전 코드에서는 실패하는 회귀 테스트다.

## 특기 사항

- **AI 단언 오류 1건**: e2e 초안에서 "마지막 행이 섹션 상자 안에 있다"를
  `boundingBox` 좌표 비교로 쟀는데, Playwright 의 `boundingBox` 는 overflow 클리핑을
  반영하지 않아 스크롤 아래 행도 레이아웃 좌표를 그대로 보고한다 — 단언이 잘못 실패했다.
  "스크롤 전에는 뷰포트 밖, `scrollIntoViewIfNeeded` 후 뷰포트 안" 판정으로 정정했다.

## 미결

- **반응형(미디엄·컴팩트 구간)**: 창을 좁히면 카드가 눌리는 상태는 이번 수정 범위가
  아니다 — App.tsx 가 명시한 별개 작업(M4 와 동일)이며 이번 변경은 와이드 레이아웃의
  넘침만 다뤘다.
- **40% 값의 튜닝**: 상한 방식(%)은 확정했지만 40 이라는 숫자는 실사용에서 조정될 수
  있다. 항목 수가 일상적으로 상한에 닿으면 그때 재논의한다.

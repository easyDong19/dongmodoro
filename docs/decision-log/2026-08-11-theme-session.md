## A. 원인 진단 (질문 이전)

세션의 출발점은 결정이 아니라 진단이었다. 결론은 **"토큰은 100% 맞고 형태가 전부 다르다"** 였다.

| # | 원인 | 근거 |
|---|---|---|
| 1 | **화면 골격을 담당하는 `app-shell` 기능이 미구현** | M1~M3b 계획서 어디에도 app-shell 태스크가 없다. M2 계획서가 "반응형 3단계·프레임리스 타이틀바·트레이"를 명시적으로 제외 목록에 넣었다 |
| 2 | **테마 토글은 배선이 끊긴 게 아니라 처음부터 없다** | `data-theme` 을 설정하는 코드 0건, theme IPC 채널 0건, `Tray` 0건. 있는 것은 `seed.ts` 의 시딩값뿐 |
| 3 | **컴포넌트 시각 어휘가 이식되지 않았다** | 와이어프레임의 40여 개 클래스 중 `global.css` 에 넘어온 것은 5개(`.card` `.eyebrow` `.card-title` `.control` `.control-raised`). 나머지는 컴포넌트마다 Tailwind 유틸 + 인라인 `style` 로 재발명 |

**구조적 뿌리:** `docs/CLAUDE.md` 는 tokens.md 를 "유일한 출처"로 못박고 raw hex 금지를 훅으로
강제하지만, 같은 문서가 와이어프레임에 대해서는 **"명세가 아니다 · 구속력 없음"** 이라고
명시한다. 그리고 각 마일스톤의 검증 기준은 전부 "동작한다"였다.
**값은 강제되고 형태는 아무도 강제하지 않는 규칙**이 만든 결과였다.

> 이 진단이 뒤의 Q9(검증 방법)에서 E2E 도입으로 이어진다.

**진단 중 발견한 사실 하나:** 현재 코드에서 **OS 가 라이트면 앱도 라이트로 뜬다.**
`tokens.css` 의 `@media (prefers-color-scheme: light)` 블록이 살아 있고 그것을 덮을
`data-theme='dark'` 를 아무도 붙이지 않기 때문이다. 사용자가 말한 "다크가 디폴트"와
문서(ADR-008 §4 "OS 선호를 따른다")가 이미 어긋나 있었다.

## B. 전환 경로와 범위

### Q1. 테마 토글을 어디에 놓나

- 배경/문제: ADR-008 §4 가 수동 전환 경로를 **트레이 서브메뉴 하나로** 못박았다. 그런데
  app-shell PRD R25 가 **"창 닫기=숨김과 트레이 상주는 분리 배포할 수 없다"** 고 정해,
  트레이를 만들면 창 수명주기·복귀 4경로·종료 경로가 통째로 딸려온다. 타이틀바도 없다
  (`window.ts` 에 `frame` 옵션 자체가 없어 OS 기본 프레임).
- 선택지:
  - A 트레이 서브메뉴 — ADR 을 안 뒤집는다. 대신 app-shell 마일스톤이 딸려온다
  - B 커스텀 타이틀바 — 시안의 최종 자리. 프레임리스 창·플랫폼 슬롯·드래그 핸들이 딸려온다
  - C 카드 밖 임시 토글 — 딸려오는 것 0. 대신 버려질 코드
- 경과: AI 는 처음 **C** 를 추천했다. 사용자가 **"C로 가보자"** 로 답한 직후 중단하고
  **"각각 어디에 위치하는지 html으로 만들어줘 보고 결정하게"** 를 요청했다.
  목업(4안: A / B / C1 떠 있는 버튼 / C2 셸 헤더 줄)을 그리는 과정에서 **C1 이 오늘 목록
  카드의 우상단을 덮는다**는 것이 드러나 AI 추천이 C1 → C2 로 바뀌었고, 사용자는 그
  그림을 보고 **B** 를 골랐다.
- **결정: B — 커스텀 프레임리스 타이틀바.**
- 이유: "B가 내가원하는바야"
- 파생: 이 계획서가 "테마"가 아니라 **"테마 + 타이틀바"** 계획서가 된다 → Q2.
  그리고 프레임리스로 가면 **창 컨트롤은 OS 가 그리는데 그 색은 CSS 를 따라오지 않으므로
  main 프로세스가 해석된 테마를 알아야 한다**는 제약이 생긴다 → Q3.

### Q2. 타이틀바를 어디까지 짓나

- 배경/문제: ux-spec §1.1·§1.2·§3.1 이 타이틀바에 넣기로 한 것은 넷(앱 이름 · MONTH 토글 ·
  날짜 라벨 · 창 컨트롤 폭 예약)이고 테마 컨트롤이 다섯 번째다. 전부 지으면 app-shell
  마일스톤이 되고, 다 빼면 "테마 버튼 하나 얹은 빈 바"가 된다.
- 선택지:
  - B-min 프레임리스 + 앱 이름 + 테마 — 최소. 정보가 0인 바
  - B-mid + 날짜 라벨 — 시안 타이틀바의 실제 모습
  - B-full + 반응형 포맷 + MONTH 토글 — ux-spec 전량
- **결정: B-mid.**
- 이유: "B-mid로 가자"
- 근거(AI 제시, 사용자 수용): 날짜 라벨은 `useClock()` 이 이미 전역 "오늘" 단일 출처로
  돌고 자정 넘어감도 `clock:boundary` 로 처리되므로 비용이 라벨 하나다. 반대로
  **MONTH 토글은 열 MONTH 컬럼(마일스톤·캘린더)이 미구현이라 아무것도 열지 않는 버튼**이
  되고, 반응형 축약은 그 구간 자체가 없다.
- 파생: `src/shared/time/` 에 `dayLabel` 포맷터가 새로 필요하다 —
  `weekRangeLabel`·`weekStartLabel` 은 있지만 `YYYY년 M월 D일` 은 없고,
  ADR-009 §3(시간 모듈 초크포인트)이 그 모듈 밖 포맷을 금지한다.

## C. 소유권과 계약

### Q3. 테마 상태를 누가 소유하나

- 배경/문제: Q1 의 파생 제약 때문에 순진하게 짜면 **해석 로직이 두 곳**에 생긴다 —
  렌더러의 CSS 와 main 의 창 컨트롤 색. 두 벌이 되면 반드시 어긋난다.
- 검증: Electron 의 `nativeTheme.themeSource` 가 **렌더러의 `prefers-color-scheme` 미디어
  쿼리까지 함께 움직인다**는 것을 확인했다. main 이 한 줄 설정하면 CSS 와 창 컨트롤이
  같은 출처에서 나온다.
- 선택지:
  - ① main `nativeTheme.themeSource` — 첫 페인트 깜빡임 0, `tokens.css` 수정 0, 해석 한 곳
  - ② renderer `data-theme` 속성 — IPC 왕복 후 적용이라 **깜빡임이 구조적으로 발생**, 해석 두 곳
  - ③ 둘 다 — 해석 세 곳. 어긋남 보장
- **결정: ① main 소유.**
- 이유: "1로 가고, 가로 가자"
- 핵심 근거: `main/index.ts` 에서 `seedSettings(uow)` 가 `createWindow()` 보다 먼저 돈다.
  그 사이에 설정을 읽어 `themeSource` 에 넣으면 **창이 태어나는 순간 이미 올바른 테마**다.

#### Q3-1. `[data-theme]` 선택자를 어떻게 하나 (Q3 파생)

- 배경/문제: ①을 고르면 OS 선호를 덮어쓰는 채널이 `data-theme` 이 아니라 `themeSource` 가
  되므로, ADR-008 §1 이 명시한 `:root[data-theme='light']` 선택자가 **쓰이지 않는 가지**가 된다.
- 선택지:
  - (가) 남긴다 — 테스트·스토리북에서 브라우저만으로 라이트를 강제할 통로
  - (나) 지운다 — 죽은 코드를 남기지 않는다
- **결정: (가) 존치. 단 "런타임은 `themeSource`, `data-theme` 은 테스트·문서 전용"을 ADR 에 명시.**
- 근거: 와이어프레임 문서의 테마 미리보기가 이미 `data-theme` 을 쓰고 있어, 지우면 문서와
  코드의 구조가 갈린다. 죽은 코드가 아니라 **용도가 다른 두 번째 진입점**으로 규정하는 편이 정직하다.

### Q4. IPC 표면을 어떻게 자르나

- 배경/문제: 렌더러가 main 에 물어볼 것은 하나뿐이다 — "사용자가 고른 값이 무엇인가".
  해석된 결과는 CSS 가 이미 알고 있어 물어볼 필요가 없다.
- 검증: `keys.ts` 에 `settings: () => ['settings']` 쿼리 키가 **이미 예약돼 있고 아무도 안 쓴다**는
  것을 확인했다.
- 선택지:
  - (a) `theme: { get, set }` 전용 도메인
  - (b) `settings: { getTheme, setTheme }` — 예약된 쿼리 키 이름과 일치
  - (c) `settings: { get, set }` 범용 key-value — **키별 검증 불가**
- **결정: (b).**
- 이유: "b로 가"
- 근거: (c) 는 값이 `string` 이라 `theme` 에 `'purple'` 이 들어가도 통과해, 이 채널에서만
  ADR-007 의 계약 규율("스키마가 원본, `strictObject` 로 모르는 키 거부")이 무력해진다.
  (a) 는 쿼리 키(`['settings']`)와 채널 이름(`theme:*`)이 갈리고, 앞으로 올 설정
  (뽀모 길이·주간 예산)이 도메인으로 흩어진다.
- 파생: **`settings:changed` 이벤트는 지금 필요 없다** — 쓰는 쪽이 렌더러 버튼 하나뿐이라
  무효화 초크포인트(ADR-025)로 충분하다 → Q6-1 에서 재확인.

## D. `system` 제거 — 사용자가 뒤집은 지점

### Q5. 컨트롤을 몇 택, 어떤 형태로

- 배경/문제: 저장값은 `system`/`light`/`dark` 3택인데(ADR-008 §4) 사용자가 처음 말한 표현은
  "토글 버튼"이었다. 그 둘이 어긋난다.
- 선택지:
  - A 2택 토글 — 최소. **`system` 으로 돌아갈 길이 UI 에 없다**
  - B 3택 세그먼트 — 상태가 한눈에. 타이틀바가 조금 붐빔
  - C 순환 버튼 1개 — 최소. 다음 상태 예측 불가
- 경과: AI 는 **B** 를 추천했다. 유일한 근거는 "설정 기본값이 `system` 인데 UI 가 2택뿐이면
  한 번 누르는 순간 영영 수동 고정된다"였다. 사용자가 그 전제 자체를 뒤집었다.
- **결정: A. 단 `system` 이라는 선택지 자체를 없앤다.**
- 이유: "A로 가는게 맞지 않나, 그리고 현재 OS단에 맞게 했는데, 그냥 OS단에서 따라간다는
  ADR을 수정하고 기획서도 수정하는게 어떨까 앱내에서만 수정가능하게 설정하는게
  관리하기도 쉬울꺼같아서 그래"
- 파생: ADR-008 §4 를 부분 supersede 하는 새 ADR 이 필요하고 문서 5곳·코드 2곳이 바뀐다 → Q6.
  그리고 **AI 의 B 추천 근거가 통째로 무력화**되어 A 로 정정했다 (특기 사항 ②).

### Q6. `system` 제거를 확정하나

- 배경/문제: `system` 은 **값이 값을 가리키는 간접 상태**다. 화면이 어두운 이유가 저장값과
  OS 둘로 갈린다. 제거하면 상태 공간이 3 → 2 가 되고 `nativeTheme.on('updated')` 구독도
  불필요해진다. 대신 **OS 의 일몰 자동 다크 전환**을 쓰는 사용자와 어긋난다.
- 확인한 것: `tokens.css` 는 여전히 **수정 0** 이다 — `themeSource` 가 명시값이면
  `prefers-color-scheme` 도 그 값으로 강제되므로 기존 미디어 쿼리가 그대로 맞는다.
  그리고 **고대비 모드(`forced-colors: active`)는 여전히 OS 가 이긴다** —
  "앱 안에서만 결정"이 그것까지 뒤집으면 접근성 회귀다.
- **결정: `system` 제거. 저장값 `light`/`dark`, 기본 `dark`. 고대비는 예외로 유지.**
- 바뀌는 곳: `design-system ADR-010`(신규) · adr-008 상태 줄 · tokens.md §9 ·
  app-shell prd R42 재작성 + **A34 삭제** · app-shell ux-spec §6.5 · adr-018 시딩 표 ·
  `seed.ts` + 테스트
- 파생: **기존 개발 DB 에 `"system"` 이 남아 있다.** `seed.ts` 는 멱등이라("키가 없을 때만")
  값을 덮지 않으므로, 읽을 때 정규화하고 **저장값까지 되쓰는** 경로가 필요하다.
  이것은 계획서 작성 단계에서야 발견됐다.

#### Q6-1. `settings:changed` 이벤트를 지금 넣나 (Q6 파생)

- 배경/문제: `system` 이 없어져도 **트레이가 생기면 같은 설정의 입구가 둘**이 된다.
  그 순간 이벤트가 필수가 된다 — 트레이(main)가 바꾼 값을 타이틀바가 모른다.
- 선택지:
  - (가) 지금은 타이틀바만. 트레이 때 추가 — ADR-026 이 이벤트 추가 절차를 4단계로 정형화해 둠
  - (나) 지금 깔아 둔다 — **아무도 발송하지 않는 채널**을 만드는 셈
- **결정: (가).**
- 이유: "(가)로 시작하자"

## E. 검증 체계

### Q7. 3 OS 중 어디까지 책임지나

- 배경/문제: PRODUCT.md 가 대상 OS 를 macOS·Windows·Linux 셋으로 확정했고 app-shell PRD
  **A17** 이 "Win·Linux 에서 창 컨트롤과 겹치지 않는다"를 인수 기준으로 걸었다. 그런데
  개발 환경이 macOS 하나다.
- 검증: Electron 43 타입 정의를 직접 열어 확인했다.
  - `titleBarOverlay` 의 `color`/`symbolColor` 는 `@platform win32,linux` — **Linux 도 지원**하고,
    Linux 는 `symbolColor` 생략 시 접근성 대비를 자동 계산한다
  - `titleBarOverlay` 를 켜면 **Window Controls Overlay CSS 환경 변수**가 활성화된다
- 선택지:
  - (가) 3 OS 코드 + macOS 만 검증 — 검증 안 된 코드가 "됐다"로 읽힘
  - (나) macOS 만 구현 — Win·Linux 에서 창 컨트롤이 타이틀바 위에 겹쳐 **못 쓰는 앱**이 됨
  - (다) 3 OS 코드 + macOS 검증 + **미검증을 계획서에 명시적 미결로 기록**
- **결정: (다).** (가)와 코드는 같고 기록만 다르다.
- 이유: "다로 가자"
- 부수 성과: ux-spec §1.1 의 **"창 컨트롤 폭은 플랫폼별 상수로 예약한다"** 가 불필요해졌다.
  CSS 환경 변수가 실제 폭을 런타임에 알려주므로 하드코딩한 숫자가 OS 업데이트로 어긋날 일이
  없다. **ux-spec 을 개선하는 방향의 정정**으로 계획서에 포함했다.

### Q8. 토글의 모양과 스타일 소유

- 배경/문제: "2택 토글"에 두 해석이 있었다 — ① 단일 버튼(누르면 뒤집힘) / ② 2세그먼트.
  ①이면 **아이콘이 "현재 상태"인지 "누르면 될 것"인지**가 정해져야 하는데 둘 다 관용적이고
  둘 다 헷갈린다. 그리고 진단 원인 3(컴포넌트 시각 어휘 미이식)과 여기서 만난다.
- 선택지 (스타일 소유):
  - (가) 이 버튼만 Tailwind 유틸 + 인라인 `style` — **진단한 실패를 그대로 재생산**
  - (나) `.seg` 하나만 `global.css` 로 이식 — 첫 이식 사례
  - (다) 컨트롤 클래스 전량 이식 — 기존 컴포넌트 전부 재작성. 별도 계획서 감
- **결정: ② 2세그먼트 + (나) `.seg` 만 이식.**
- 이유: "(나)로 가자" (`.seg` 는 정의상 세그먼트 컨트롤이라 ①과 양립 불가)
- 근거: ②는 "지금"과 "누르면"이 동시에 읽혀 아이콘 방향 모호성이 사라지고,
  design-system ADR-006 §3 의 **"선택 상태에 보더"** 규칙(고대비 모드에서 배경이 사라짐)을
  이미 만족한다. ①은 선택 상태라는 개념 자체가 없어 그 규칙 밖으로 나간다.

### Q9. 검증을 어떻게 하나 — E2E 도입

- 배경/문제: 지금까지 계획서의 검증 기준이 전부 "동작한다"였고 그것이 진단한 원인의
  구조적 뿌리였다. 그리고 ADR-008 이 **라이트 테마의 대비 판정 지점을 타이틀바**로 지정하고
  그 때문에 `--ink-dim` 알파를 0.60 → 0.65 로 올렸는데, **타이틀바가 없어서 그 판정을 한 번도
  실측한 적이 없다.** 이번 작업이 그 지점을 처음 만든다.
- 선택지:
  - (가) 단위 테스트만 — "저장된다"까지만 확인. 화면이 뒤집히는지는 못 봄
  - (나) 단위 + 명문화된 수동 체크리스트 — 낮은 비용
  - (다) 단위 + Electron E2E — 새 의존성·CI·실행시간
- 경과: AI 는 **(나)** 를 추천했다. 근거는 "Playwright 도입은 그 자체로 설정 작업이라
  테마 계획서에 얹으면 테마보다 도구 도입이 커진다"였다. 사용자가 기각했다.
- **결정: (다) E2E 도입.**
- 이유: "(다)로 하는게 맞는거 같아 이왕하는김에 e2e테스트 기능도 깔자"
- 파생: 작업 덩어리가 셋이 된다(E2E 하네스 · 타이틀바 · 테마) → Q10.
  그리고 E2E 는 `getComputedStyle` 로 **대비 수치를 자동 계산**할 수 있어,
  ADR-008 이 계산으로만 통과시킨 4.97:1 을 기계가 실측하게 됐다.
- 검증: Playwright 의 Electron 지원(`_electron.launch()`)과, Chromium 의 `--user-data-dir`
  스위치를 Electron 이 존중해 **main 코드를 한 줄도 안 고치고 DB 를 격리**할 수 있음을 확인했다.
  이것이 "첫 실행이 다크인가" 케이스의 전제가 된다.

### Q10. 계획서를 하나로 가나 나누나

- 배경/문제: `CONTRIBUTING.md` 가 스쿼시 머지를 강제하므로 PR 제목 한 줄이 main 커밋이 된다.
  "Playwright 도입 + 프레임리스 창 + 테마"를 한 줄 Conventional Commits 로 쓸 방법이 없다 —
  `feat:` 인지 `test:` 인지부터 안 정해진다.
- 선택지:
  - (가) 1개 — 리뷰 불가능한 diff
  - (나) 2개 (E2E → 타이틀바+테마) — 순차
  - (다) 3개 (E2E → 타이틀바 → 테마) — **과분할**. 타이틀바 없이는 테마 버튼을 놓을 자리가
    없고, 창 컨트롤 색이 테마를 따라야 해서 둘은 분리 불가. 쪼개면 중간 상태가 "빈 타이틀바"
- **결정: (나) 2개. E2E 가 먼저.**
- 이유: "(나) ㄱㄱ"
- 근거: 하네스를 나중에 만들면 테마를 수동 검증한 뒤 다시 자동화하게 되어 같은 검증을 두 번 한다.
  먼저 깔면 테마 계획서의 검증 절이 "E2E 로 확인" 한 줄이 된다.

### Q11. E2E 를 어디서 돌리나

- 배경/문제: CI 를 열어 보니 **`pnpm test` 가 어디서도 자동 실행되지 않는다.**
  CI 는 `pr-language.yml`(PR 언어 검사) 하나뿐이고, husky 는 `pre-commit`=lint-staged,
  `pre-push`=브랜치 보호, `commit-msg`=commitlint 가 전부다. 타입체크도 단위 테스트도
  자동 실행 지점이 없다.
- 선택지:
  - (가) 로컬 전용 — 안 돌리면 없는 것과 같음
  - (나) CI 에 E2E 만 추가 — **단위 테스트는 여전히 안 돎.** 지붕부터 얹는 격
  - (다) CI 파이프라인 신설 (typecheck · lint · format · test · build · e2e)
- **결정: (다).**
- 이유: "다로 가자"
- 함께 결정한 것: **스크린샷 회귀(`toHaveScreenshot`)는 넣지 않는다** — 폰트 렌더링이 OS 마다
  달라 macOS 로컬 베이스라인과 ubuntu CI 결과가 일치하지 않는다. 상시 실패하는 테스트는 곧
  무시된다. 대신 **스크린샷을 아티팩트로 업로드하고 비교는 사람이 한다.**

## 특기 사항 (AI 오판·정정·번복)

### ① 배치 추천이 C1 → C2 로 바뀌었다 — 그림을 그린 뒤에야 보였다

Q1 에서 AI 는 처음 "카드 밖 임시 토글(C)"을 추천했고 사용자도 **"C로 가보자"** 로 동의했다.
그런데 사용자가 즉시 중단하고 목업을 요구했고, **그리는 과정에서 C1(떠 있는 버튼)이 오늘
목록 카드의 우상단을 덮는다**는 것이 드러났다. 지금은 그 자리가 비어 있지만 그 카드에
컨트롤이 하나라도 생기면 충돌한다. 표로만 비교할 때는 안 보이던 문제였다.
**"HTML로 만들어줘 보고 결정하게"라는 요구가 아니었으면 그대로 갔을 결정이다.**

### ② 컨트롤 형태 추천(B)이 통째로 무력화됐다

Q5 에서 AI 가 3택 세그먼트(B)를 추천한 **유일한 근거**는 "`system` 이 있으니 2택은 되돌아갈 수
없는 문이 된다"였다. 사용자가 `system` 자체를 없애자고 제안하면서 그 전제가 사라졌고,
AI 는 추천을 A 로 정정했다. **선택지의 우열이 아니라 전제를 의심하는 쪽이 옳았던 경우다.**

### ③ E2E 도입 반대가 기각됐다

Q9 에서 AI 는 "(나) 수동 체크리스트"를 추천하며 "Playwright 도입은 테마 계획서가 감당할
크기가 아니다"라고 했다. 사용자가 **"이왕하는김에"** 로 기각했다. 결과적으로 E2E 는 대비
수치 자동 실측이라는, 수동 체크리스트로는 불가능한 검증을 가능하게 했다.

### ④ `vitest exclude` 설정이 불필요했다 — 계획서 작성 직전 정정

Q10 정리 시점에 AI 는 "vitest 가 e2e 파일을 집지 않게 `exclude` 를 설정해야 한다"고 적었다.
`vitest.config.ts` 를 실제로 열어 보니 `include` 가 `src/**`·`scripts/**` **화이트리스트**라
`e2e/` 는 자동으로 제외된다. 계획서에 쓰기 전에 정정했다.

### ⑤ 계획서를 쓰면서 새로 나온 문제 3건

설계 합의가 끝난 뒤 계획서를 구체화하는 단계에서 세 가지가 추가로 드러났다.
**설계 대화만으로는 안 보이고 태스크를 쪼개야 보이는 것들이었다.**

1. **기존 개발 DB 에 `"system"` 이 남는다** — `seed.ts` 가 멱등("키가 없을 때만")이라 기본값을
   바꿔도 기존 DB 는 안 바뀌고, 그 값은 새 계약 `z.enum(['light','dark'])` 를 통과하지 못한다.
   읽을 때 정규화하고 **저장값까지 되쓰는** 경로를 태스크로 넣었다.
2. **색 값 4개가 CSS 밖으로 새어 나간다** — main 은 CSS 변수를 못 읽는데 Win·Linux 창 컨트롤
   색은 JS 로 줘야 한다. "raw hex 금지"의 실질적 예외이므로 한 파일에 가두고,
   **`tokens.css` 를 직접 읽어 값 일치를 검사하는 테스트**를 붙였다.
3. **OS 오버레이 영역은 투명할 수 없다** — 앱 타이틀바는 라디얼 광원 위에 투명하지만 OS 가
   그리는 컨트롤 영역은 불투명 `--bg-deep` 이라, Win·Linux 에서 미세한 색 이음매가 보인다.
   해결 방법이 없어 **알려진 한계로 기록**했다.

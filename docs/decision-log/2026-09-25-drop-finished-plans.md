# 의사결정 기록 — 2026-09-25 끝난 계획서 정리 세션

> `docs/` 구조를 훑다가 "코드로 이미 구현된 계획서가 남아 있다"는 문제를 발견하고,
> [2026-08-04 M1 계획 세션](./2026-08-04-m1-plan-session.md) Q1 의 "실행이 끝난 계획은 이력으로
> 보존한다" 규칙을 뒤집은 기록.
> 각 항목: 질문 → 선택지 → **결정** → 결정 이유(사용자 원문) → 파생 효과.
> 의사결정 흐름의 시각화: [2026-09-25-drop-finished-plans-flow.html](./2026-09-25-drop-finished-plans-flow.html)

---

## 진행 방식

1. `docs/` 폴더 구조 확인 → 사용자가 "구현이 끝났는데 안 지워진 문서"를 물음
2. 계획서·설계 스펙 17건을 코드·git 이력과 대조 → 끝났는데 상태 표시가 없는 5건 확인 (Q1)
3. 사용자가 삭제 방향을 제안 → AI 가 인바운드 링크를 전수 조사해 "설계 근거가 계획 폴더에
   섞여 있다"는 사실을 확인 (Q2)
4. 옮길 곳·링크 처리·폴더 단일화·백로그 구출 계획을 제시하고 승인받음 (Q3~Q5)
5. 근거 이전 → 링크 교체 → 규칙 개정 → 삭제를 PR 하나로 수행

## A. 끝난 계획을 남길 것인가

### Q1. 구현이 끝난 계획서를 어떻게 다루나

- 배경: `docs/plans/` 13건과 `docs/superpowers/` 4건이 모두 머지된 작업의 계획·설계였다.
  2026-08-04 규칙대로 이력으로 남아 있었지만, 5건은 끝났다는 표시가 없었다 — time-currency
  (체크 3/48, #62 머지), adjust-as-baseline (0/48, #78), remove-milestone-archive (0/29, #89),
  medium-breakpoint 계획 (0/52, #90), medium-breakpoint 설계 스펙 ("상태: 승인 대기", #90).
  문서만 보면 아직 할 일로 읽혔다.
- 선택지:
  - **끝난 계획에 상태 줄만 추가하고 보존 (AI 첫 추천)** — 2026-08-04 규칙과 맞고 수정 범위가
    작다. 대신 끝난 계획서가 계속 검색에 걸린다
  - **끝난 계획을 삭제하고 규칙을 바꿈 (사용자 제안)** — 트리에는 진행 중인 계획만 남는다.
    대신 링크·근거·백로그를 먼저 옮겨야 한다
- **결정: 끝난 계획은 삭제한다.** docs/CLAUDE.md·루트 CLAUDE.md 의 규칙을 함께 고친다.
- 이유: "흠 내생각에 이미 실행이 끝나 Code로 구현된 문서들은 삭제하는게 LLM이 문서를
  이해하고 활용하는데 도움이 될거라 생각하는데 그래서 claude.md나 규칙들을 좀 수정하는
  방향성이 괜찮아 보이는데 타당성에 대해서 어떻게 생각해?"
  - AI 가 동의한 근거: 계획서는 `**Goal:**`·`- [ ] Task` 형식이라 LLM 이 검색으로 만나면
    현재 지시로 읽는다. 옛 모델(2.0.0 이전 뽀모 개수 통화, 마일스톤 보관, 정산 패널의
    `조정` 폼)이 현재 사실처럼 남는다. 2026-08-04 에 `docs/plans/` 를 만든 근거가 "git 이력에
    남는다"였으므로, 같은 논리가 트리에서 빼는 쪽을 지지한다.
- 파생: → Q2 (무엇을 먼저 옮겨야 지울 수 있나), `docs/tmp/` 의 "구현하면 삭제" 원칙이
  계획서로 확장됨.

### Q2. 일괄 삭제인가, 문서 종류를 나눠 처리하나

- 배경: 인바운드 링크를 조사하니 "계획은 결정을 만들지 않는다" 규칙이 실제로는 지켜지지
  않았다. [ADR-033](../architecture/decisions/adr-033-adjust-as-baseline.md) 이 설계 문서를
  **"결정 근거 원장"** 으로 링크했고, ADR-025·026 과 design-system ADR-011 도 설계 스펙을
  근거로 링크했다. 일괄 삭제하면 ADR 의 근거가 사라진다.
- 선택지:
  - 일괄 삭제 — 간단하지만 ADR 근거 유실·링크 깨짐
  - **실행 계획은 바로 삭제, 설계 문서는 근거를 ADR 로 옮긴 뒤 삭제 (AI 추천)**
- **결정: 종류를 나눠 처리한다.** 설계 문서 4건을 하나씩 대조해 다른 문서에 없는 내용만 옮긴다.
  - adjust-as-baseline 설계 → ADR-033 에 "기각된 선택지" 절과 Decision §6(저장이 먼저,
    엔진 상태는 그 뒤) 추가
  - medium-breakpoint 설계 → design-system ADR-011 에 §4(구간 판정은 `useBreakpoint` 훅
    한 곳이 소유) 추가. 오버레이 전환 표는 app-shell ux-spec §5 에 이미 있었다
  - query-keys-and-events 설계 → 옮길 것 없음. ADR-025·026 이 이 초안을 확장한 최종본이다
  - m3a week-plan 설계 → 옮길 것 없음. 유일한 자체 결정(§6 est 어긋남 미표시)은 2.0.0 의
    est 폐기로 의미가 없어졌다
- 이유: "ㅇㅇ 그렇게하자" (제시안 승인)
- 파생: → Q3, 규칙에 "삭제 전에 '왜'를 소유 문서로 옮긴다" 단계가 들어감.

## B. 지운 뒤의 연결

### Q3. 삭제된 문서를 가리키던 링크를 어떻게 하나

- 배경: ADR 5곳, 기능 overview 2곳, PRODUCT.md 6곳, decision-log 3개 파일이 계획·스펙을
  링크하고 있었다.
  decision-log 는 추가 전용 기록이라 본문을 고칠 수 없다.
- 선택지:
  - 링크 삭제 — 과거 기록이 무엇을 근거로 했는지 추적이 끊긴다
  - **삭제 직전 커밋의 GitHub permalink 로 교체 (AI 추천)** — 이력은 열 수 있고 트리는 깨끗하다
- **결정: permalink 로 교체.** 기준 커밋은 `bff905a`. 기능 overview 와 PRODUCT.md 처럼
  "구현됐다"의 근거로 계획을 링크한 곳은 구현 PR(#39·#52·#57·#62) 링크로 바꿨다 — 상태의
  근거로는 계획보다 PR 이 맞다.
  decision-log 는 링크 대상만 바꾸고 본문은 건드리지 않았다.
- 이유: "ㅇㅇ 그렇게하자" (제시안 승인)

### Q4. `docs/superpowers/` 를 어떻게 하나

- 배경: docs/CLAUDE.md 의 구조도에 없는 폴더다. 2026-08-04 Q1 에서 기각된 경로(계획 작성
  스킬의 기본 경로)였는데, 이후 스킬이 기본 경로에 계획 1건·스펙 3건을 만들었다. 계획서가
  두 곳에 흩어졌다.
- **결정: 폴더를 없애고, 계획·스펙은 `docs/plans/` 에만 둔다.** 스킬 기본 경로 사용 금지를
  docs/CLAUDE.md 와 루트 CLAUDE.md 에 명시했다 — 규칙 없이 두면 스킬이 다시 만든다.
- 이유: "ㅇㅇ 그렇게하자" (제시안 승인)

### Q5. 계획서에만 있던 "미룬 범위"를 어떻게 하나

- 배경: m3a·m3b 등 계획서에 "이번 마일스톤에서 뺀 것" 표가 있었고, 이 목록은 다른 문서
  어디에도 없었다. 예: 기타 행 드릴다운은 지금도 미구현이며, 코드에는 테스트 이름
  ("드릴다운은 이번 마일스톤에서 뺐다")으로만 흔적이 있다. 계획과 함께 지우면 백로그가 사라진다.
- **결정: 코드와 대조해 아직 안 만들었고 지금도 유효한 항목만 `docs/tmp/` 로 옮긴다.**
  구현됐거나 이후 결정으로 의미가 없어진 항목은 버린다.
- 이유: "ㅇㅇ 그렇게하자" (제시안 승인)
- 결과: 서브에이전트가 17건 전체에서 이연 항목 약 45건(중복 합산)을 뽑아 코드·ADR·PRD 와
  대조했고, AI 가 핵심 근거를 코드에서 다시 확인했다.
  - 구현됨 11건 · 이후 결정으로 무의미 6건 · 다른 문서에서 이미 추적 중 약 20건 → 버림
  - **아직 안 만들었고 어디에도 추적되지 않은 7건 → `docs/tmp/` 로 이전**: 기타 행 드릴다운,
    Sprint 행의 Milestone 배지, 오늘 목록 빈 상태 두 갈래(+ 자정 힌트), 플래너 선언형 확정의
    동시성 약점, Windows·Linux 배포 열기, 코어 루프 E2E 백필, timer-host `stop()` 의 만료
    타이머 잔존(버그)
  - 판정 보류 1건: 첫 실행 온보딩 — 아래 "미결"

## 특기 사항

- **AI 의 첫 추천이 번복됐다.** AI 는 2026-08-04 규칙을 전제로 "상태 줄만 추가"를 추천했다.
  사용자가 규칙 자체를 문제 삼았고, AI 는 검토 후 동의했다.
- **AI 가 규칙에 없는 브랜치 이름을 말했다.** 계획 제시 때 "`docs/*` 브랜치"라고 했으나
  CONTRIBUTING 은 `feature/`·`fix/` 만 허용한다. 실행 때 `feature/drop-finished-plans` 로 정정했다.
- **AI 가 링크 전수 조사에서 PRODUCT.md 를 놓쳤다.** 첫 조사는 `../plans/` 형태의 상대 링크만
  찾았고, 루트 문서의 `docs/plans/` 형태 링크 6곳은 서브에이전트의 감사 보고로 발견해 고쳤다.
- **"계획은 결정을 만들지 않는다" 규칙은 지켜지지 않고 있었다.** 설계 스펙이 계획 폴더에
  들어가면서 ADR 이 계획 폴더를 근거로 가리키게 됐다. 새 규칙의 "삭제 전 '왜'를 옮긴다"
  단계는 이 누수를 PR 마다 닫는 장치다.

## 미결

- 기능 overview 의 `현재 상태`(Draft·In Review 등)가 구현 현황과 어긋난다. 이번 범위 밖이다.
- docs/CLAUDE.md 의 "spacing 만 아직 미토큰화 — M1 Task 7 에서 결정" 문구는 삭제된 M1
  계획서를 가리킨다. 사실 확인이 필요해 이번에 고치지 않았다.
- **첫 실행 온보딩의 지위가 문서끼리 어긋난다.** ADR-033 §3 은 길이 편집 경로를 대기 중인
  타이머 하나로 정했는데, app-shell R31·ux-spec §7.1 과 PRODUCT.md 는 온보딩을 "편집 경로
  중 하나"로 자리 예약하고 있다. tmp 메모를 만들기 전에 이 불일치부터 정리해야 한다.
- 이연 항목 감사 중 발견한 낡은 문장 — 이번 범위 밖이라 고치지 않았다.
  - PRODUCT.md: "반응형 셸 아직 없다"(미디엄은 #90 으로 구현됨), 비범위의 "정산 진입점 하나만
    열려 있다"(ADR-033 으로 사라짐), 미결정의 "Query invalidation 키 계층"(ADR-025 로 닫힘)·
    "최소 창 ~420px"(현재 720px, design-system ADR-011)
  - week-plan ux-spec §3.1 의 `+ 오늘로` 행, today-tasks R20 카피 — #85·#86 이후 낡음

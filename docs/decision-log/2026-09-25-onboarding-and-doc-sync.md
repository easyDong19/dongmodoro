## A. 첫 실행 온보딩

### Q1. 첫 실행 온보딩 화면을 어떻게 하나

- 배경: 첫 실행 온보딩은 앱을 처음 켤 때 1회 뜨는 화면으로, 뽀모 길이 3종을 묻고 건너뛸 수
  있게 예약돼 있었다. **구현된 적은 없다** — 새 설치의 기본값은 시딩이 넣는다(ADR-018 §4).
  문서가 둘로 갈려 있었다.
  - 길이 규칙의 소유자 쪽은 이미 정리돼 있었다: [ADR-033](../architecture/decisions/adr-033-adjust-as-baseline.md)
    §3 "길이 편집 경로는 대기 중인 타이머 하나", pomo-baseline PRD R11 "온보딩은 미구현이며
    기본값은 시딩이 담당", 폐기 표의 "옛 R11: 편집 진입점 2개(온보딩·정산)".
  - app-shell 쪽은 ADR-033 이전 서술 그대로였다: R31 "첫 실행 온보딩이 그 편집 경로 중
    하나", 인수 기준 A23, ux-spec §7.1, PRODUCT.md 의 "편집 경로 2개". R31 이 말하는 "다시
    열리는 경로(상시 편집 진입점)"는 이미 폐기된 정산 `조정` 폼이었다.
  - app-shell 안에서도 R30("환영 모달·설정 강요 화면을 만들지 않는다")·ux-spec §7("전용
    온보딩 화면으로 갈아치우지 않는다")과 R31 의 "1회 오버레이"가 취지상 부딪혔다.
  - 방치하면: 누가 "app-shell 스펙대로 구현해줘"라고 하면 AI 가 R31·A23 을 근거로 온보딩을
    만들고, 길이 편집 경로가 다시 둘이 된다 — ADR-033 이 없앤 문제가 되살아난다.
- 선택지:
  - **온보딩 폐기 (AI 추천)** — 소유자(pomo-baseline)가 이미 정한 쪽에 나머지를 맞추는 일.
    첫 화면에 ± 칩이 보이고 기본값 25분은 대개 그대로 쓸 수 있다. 대신 "길이를 바꿀 수
    있다"는 안내 장치가 없어 ± 칩의 가시성에 기댄다
  - 온보딩 유지 + ADR-033 부분 개정 — 처음부터 자기 리듬으로 시작할 수 있다. 대신 온보딩 값과
    ± 칩의 관계를 새로 정해야 하고 ADR-018 도 다시 봐야 한다
  - 보류 (v1 비범위로 표기, tmp 메모) — 결정을 미룬다. 오해 위험은 줄지만 불일치는 남는다
- **결정: 온보딩을 폐기한다.** app-shell R31·A23 을 폐기 표기하고(번호는 남긴다), ux-spec §7.1 을
  폐기 노트로 바꾸고(절 번호는 링크 보존용으로 남긴다), app-shell overview·범위 문구,
  pomo-baseline PRD·overview, PRODUCT.md 를 맞췄다.
- 이유: "1번 온보딩 폐기하자"
- 파생: 새 ADR 은 만들지 않았다 — 결론은 ADR-033 §3 이 이미 갖고 있고, 이번 결정은 그
  결론을 app-shell 문서에 반영한 것이다.

## B. 같은 PR 의 범위

### Q2. 옛 UI 용어(#86) 동기화를 이번에 함께 하나

- 배경: 1순위로 제시한 "스펙이 코드와 반대로 적힌 곳"에는 두 종류가 섞여 있었다.
  - #85 가 없앤 행의 `+ 오늘로` 버튼이 week-plan ux-spec 에 "원클릭 pull"로 살아 있음 — **동작**이 다르다
  - #86 이 바꾼 UI 문구(`결과물`→`Milestone`, `이번 주 할당`→`Sprint`, `조각`→`task`)가 스펙 카피
    표에 옛 문구로 남음 — `조각` 만 143곳이고, 스펙이 적은 카피 원문을 코드 문자열과 한 줄씩
    대조해야 한다
- **결정 (AI, 사용자 보고 전): `+ 오늘로` 만 이번 PR 에서 고치고, 용어 동기화는 별도 PR 로 뺀다.**
  동작이 다른 쪽이 AI 가 없앤 기능을 되살릴 위험이 더 크고, 용어 대조는 분량이 커서 한 PR 에
  섞으면 리뷰가 어려워진다.
- today-tasks R20 의 빈 상태 카피는 새 문구를 지어내지 않고 "다시 써야 한다"는 경고 블록만
  달았다 — 카피는 구현 착수 시 정한다 ([tmp 메모](../tmp/today-empty-state-branches.md)).

### Q3. 기능 상태(Draft·In Review·Published)를 이번에 맞추나

- 배경: 8개 기능이 모두 출시됐는데 overview 와 meta.yaml 의 상태가 제각각이다 (milestones 는
  overview `In Review`, meta `draft` 로 서로 다르다). 그런데 docs/CLAUDE.md 는 상태 값 3개를
  나열만 하고 **각 값의 뜻을 정의하지 않는다** — 문서 검토 단계인지 구현 여부인지 알 수 없다.
- **결정 (AI, 사용자 보고 전): 이번 PR 에서 빼고 사용자에게 묻는다.** 값을 고르는 순간 상태의
  정의를 새로 만드는 셈이라 AI 가 정할 일이 아니다.

## 특기 사항

- **AI 가 한 번 잘못 고쳤다가 되돌렸다.** week-plan ux-spec §3.4(기타 행)의 "pull 버튼 없음"을
  "캐럿 없음"으로 바꿨는데, §3.4 는 드릴다운용 캐럿을 정의하고 있어 스펙과 충돌했다. 커밋 전에
  "요일 핍·이월 배지 없음"으로 되돌렸다.
- #85·#86 은 코드와 CONTEXT.md 만 고치고 스펙을 고치지 않았다. "용어를 바꾸면 같은 PR 에서
  CONTEXT.md 를 갱신한다" 규칙은 지켜졌지만, **스펙 본문까지 같은 PR 에서 고친다**는 규칙은 없다.
  이번 불일치의 근본 원인이다.

## 미결

- 옛 UI 용어(#86) 동기화 — week-plan ux-spec 카피 표 중심, `조각` 143곳 등 (Q2)

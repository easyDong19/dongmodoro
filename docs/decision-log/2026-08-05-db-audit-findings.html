착수 전 심사 · M1 Task 4

DB 계층에 들어가기 전에 닫아야 하는 것들

격리된 두 심사가 계획된 스키마와 백엔드 구조를 독립적으로 검토했고, 핵심 주장 네 건은 실제 SQLite 로 재현했다. 결론은 같다 — 지금 상태로 첫 마이그레이션을 내면 안 된다.

대상 계획서 Task 4·5 · ADR 8건 · 기능 PRD 8건 · 구현 코드 12파일 검증 better-sqlite3 13.0.3 / SQLite 3.53.4 날짜 2026-08-05
01

결론

판정 — 조건부

설계 판단은 옳다. 빠진 것은 판단이 아니라 실행분이다.

ADR 이 정한 것들 — 불변 달력 키, 제약을 첫 마이그레이션에 전부 넣기, 정정 체인 관리 — 은 전부 정확하다. 문제는 그 결정을 실제로 강제하는 코드가 작동하지 않거나 아예 없다는 것이다. 주 키를 지키는 제약은 쓰레기 값을 통과시키고, 데이터를 지키는 백업은 열리지도 않는다.

발견은 40건 가까이 되지만 전부 지금 다룰 필요는 없다. Task 4 를 실제로 막는 것은 결정 네 개이고, 나머지는 착수 후에 순서대로 처리하면 된다. 이 문서는 그 네 개를 가려내기 위해 쓰였다.

핵심 비대칭이 하나 있다. SQLite 는 CHECK·NOT NULL·FK 를 나중에 바꾸려면 테이블을 재작성해야 하고, 그 SQL 은 사용자의 실데이터 위에서 앱이 켜질 때 돈다. 지금 고치면 비용이 0 이고 나중에 고치면 가장 비싸다. ADR-011 §6 이 "제약은 초기 마이그레이션에 전부"라고 정한 이유가 그것이고, 이 심사가 지금 필요한 이유도 같다.

02

어떻게 확인했는가

설계자가 자기 설계를 검토하면 자기가 의도한 것을 읽는다. 그래서 사전 맥락이 전혀 없는 심사자 둘에게 각각 문서와 코드만 주고 판단하게 했다. 한쪽은 스키마 정합성, 다른 쪽은 레이어 구조를 맡았다 — 두 문제는 틀리는 방식이 다르기 때문이다. 스키마는 "이 제약이 실제로 거부하나" 같은 국소적·검증 가능한 문제고, 구조는 "정산 로직이 어느 파일에 사는가" 같은 전역적 문제다.

두 심사 모두 발견마다 스스로 반박을 시도해 살아남은 것만 보고하도록 했고, 실증한 것과 추론한 것을 구분하게 했다. 그리고 가장 결정적인 주장 네 건은 내가 다시 재현했다 — 아래 §3 이 그 결과다.

두 심사가 독립적으로 같은 결론에 도달한 것

WAL 백업 결함 · Windows 경로 버그 · 백업 파일 무한 축적. 서로의 존재를 모른 채 같은 세 건을 짚었다는 것은 이들이 해석 문제가 아니라는 뜻이다.

03

재현한 증거

아래 네 건은 주장이 아니라 실행 결과다. 계획서에 적힌 DDL 과 PRAGMA 를 그대로 재현하고, 값을 넣고, 결과를 받았다.

증거 1 — 주 키 제약이 잘못된 값을 거의 다 통과시킨다

주 키 CHECK — 계획안 대 수정안 weeks.week 컬럼에 직접 INSERT
넣은 값 계획안
strftime('%w', week) = '1'		 수정안
week IS date(week) AND …		 정체
'2026-08-03' 통과 통과 월요일 — 유일하게 통과해야 하는 값
'2026-08-04' 거부 거부 화요일 — 정상 거부
'garbage' 통과 거부 날짜가 아닌 임의 문자열
'' 통과 거부 빈 문자열
'2026-8-3' 통과 거부 zero-pad 없음 — 같은 날인데 문자열이 다르다
'2026-02-30' 통과 거부 존재하지 않는 날짜
'2026-08-03T09:00:00Z' 통과 거부 순간(instant)을 달력 키 자리에 저장
계획안은 7개 중 5개를 잘못 통과시킨다. 수정안은 전부 정확히 판정한다. 같은 패턴이 weeks.week · week_items.week · week_items.origin_week · sessions.local_week 네 곳에 있다.

왜 이렇게 되는가

SQLite 의 두 가지 성질이 겹친 결과다.

fail-open 메커니즘'garbage' 를 넣었을 때
입력 'garbage' 날짜로 해석할 수 없는 값
→
strftime NULL 파싱 실패 시 오류가 아니라 NULL 을 돌려준다
→
비교 NULL = '1' NULL 과의 비교 결과도 NULL 이다
→
CHECK 판정 통과 CHECK 은 결과가 FALSE 일 때만 거부한다. NULL 은 통과다
결과적으로 이 제약은 "월요일인 날짜"가 아니라 "월요일이거나, 아예 날짜가 아닌 값"을 허용한다. 의도와 정확히 반대다. 수정안의 week IS date(week) 는 IS 가 NULL-safe 비교라 이 구멍이 닫힌다.

실질 피해 — 조용한 오답

집계 술어 전체가 sessions.local_week = week_items.week 라는 문자열 동등 비교다 (ADR-012 §1). 한쪽이 '2026-8-3' 이고 다른 쪽이 '2026-08-03' 이면 조인이 조용히 0건이 되고, 그 뽀모는 에러 없이 "계획에 없던 집중"으로 흘러간다. 총합 등식은 여전히 닫히기 때문에 사용자도 개발자도 영영 모른다.

"zod 가 막지 않나" — 막지 않는다

WeekKey 정규식은 월요일인지 검사하지 않고 '2026-99-99' 를 통과시킨다. 무엇보다 문제의 값들은 IPC 경계를 건너지 않는다. local_week 은 main 의 weekKey() 가, origin_week 은 정산 트랜잭션이 만든다. DB CHECK 이 main 프로세스 버그에 대한 유일한 방어선이다.

덧붙이면, ADR-010 이 이 CHECK 식을 그대로 적으면서 "(SQLite 검증 실증)"이라고 표기해 두었다. 그 문장은 사실이 아니다.

증거 2 — 백업 파일이 열리지도 않는다

계획서의 PRAGMA 세트(WAL + synchronous = NORMAL)를 그대로 켜고 200행을 커밋한 뒤, 계획서대로 copyFileSync 로 app.db 를 복사했다.

WAL 모드에서 데이터가 실제로 있는 곳200행 커밋 직후
복사 대상 app.db
4,096 바이트 — 헤더뿐, 데이터 0행
copyFileSync → 복사본 열기 실패
no such table: t
복사 안 됨 app.db-wal
12,392 바이트 — 커밋된 200행 전부
체크포인트를 먼저 돌린 뒤 같은 방식으로 복사하면 백업 행수가 200 으로 회복된다. 즉 문제는 복사 방식이 아니라 복사 시점에 데이터가 그 파일에 없다는 것이다.

WAL 모드에서는 커밋된 데이터가 -wal 에 살고 메인 파일은 체크포인트 전까지 헤더만 남는다. synchronous = NORMAL 이라 체크포인트도 지연된다. 결과적으로 ADR-011 §7 이 "크래시·데이터 파손 방지"를 위해 요구한 백업이, 정작 복구가 필요한 순간에 못 여는 파일이다.

이건 백업이 없는 것보다 나쁘다. 있다고 믿게 만들기 때문이다. 정산 기술 명세가 "최악의 경우 그날의 백업으로 복구 가능하다"고 적어둔 문장이 그대로 거짓이 된다.

증거 3 — 요구된 상태 하나를 표현할 컬럼이 없다

오늘 목록 명세 R13 은 조각을 × 했을 때의 동작을 그날 세션 유무로 가른다. 세션이 0건이면 pull 행을 지우고, 1건 이상이면 지우지 않고 "치움" 표시만 남긴다 — 오늘 목록에서는 빠지되 그 날짜의 이력으로는 남아야 한다.

task_pulls 가 표현해야 하는 상태 현재 컬럼: task_id, pull_date — 그리고 그 둘이 곧 PK
1 행 없음 — 오늘 목록에 올린 적 없다 행 부재로 표현 가능
2 행 있고 오늘 목록에 표시 중 행 존재로 표현 가능
3 목록에서 치웠지만 그날 이력에는 남아 있다 표현 수단 없음
우회도 불가능하다. 행을 지우면 인수 기준 A13("세션이 기록된 조각을 × 한 뒤에도 그 날짜 화면에 남는다")이 깨지고, 안 지우면 A1("오늘 목록 = 치우지 않은 행 수")이 깨진다.

task_pulls 를 단일 컬럼에서 행으로 승격한 유일한 목적이 이 이력 보존이었다 (ADR-011 §2). 목적과 컬럼이 어긋나 있다. 

// 권장
taskId:    text('task_id').notNull().references(() => tasks.id),
pullDate:  text('pull_date').notNull(),
removedAt: text('removed_at'),   // 순간. NULL = 오늘 목록에 표시 중
createdAt: text('created_at').notNull()  // R4 의 2차 정렬 키

재-pull 은 removed_at 을 NULL 로 되돌리면 되므로 "다시 담으면 원래 행과 구분되지 않는다"는 R14 도 자동으로 성립한다.

증거 4 — ADR-011 의 근거 문장 하나가 낡았다

ADR-011 §7 은 foreign_keys = ON 을 켜야 하는 이유로 "better-sqlite3 기본 OFF — 켜지 않으면 위 FK 가 전부 장식이다"라고 적었다. 13.0.3 에서 확인한 기본값은 1 이다.

명시적으로 켜는 것 자체는 유지해야 한다 — 버전에 따라 달라질 수 있는 것에 의존하지 않는 편이 낫다. 다만 ADR 의 근거 문장은 갱신 대상이다. 결정이 바뀐 게 아니라 근거가 낡은 경우라, 본문은 이력으로 두고 상태 줄에 정정을 단다.

04

발견의 다섯 갈래

발견을 심각도로만 늘어놓으면 무엇을 고쳐야 할지는 알아도 왜 이런 일이 반복되는지는 안 보인다. 원인의 종류로 묶으면 다섯 갈래가 된다.

A. 강제 장치가 있는데 작동하지 않는다

제약도 있고 백업 코드도 있다. 다만 둘 다 의도한 일을 하지 않는다. §3 의 증거 1·2 가 여기 속하고, 이 갈래가 가장 위험하다 — 장치가 있다는 사실이 검증을 면제해 주기 때문이다.

HIGH재현함 주 키·달력 키 CHECK 4종이 fail-open
고치는 법
strftime 앞에 IS date(...) 를 붙여 NULL 경로를 닫는다. sessions.local_date 와 task_pulls.pull_date 의 GLOB 검사도 같은 문제가 있다 — '0000-00-00' 과 '9999-99-99' 를 통과시킨다.
언제
지금. CHECK 변경은 나중이면 테이블 재작성이다.
HIGH재현함 두 심사 일치 WAL 환경에서 백업이 빈 파일이다
고치는 법
복사 전에 wal_checkpoint(TRUNCATE), 또는 better-sqlite3 의 온라인 백업 API 를 쓴다. 종료 시 체크포인트 경로도 함께 만든다 — 지금 main/index.ts 에는 DB 를 닫는 코드가 아예 없다.
같은 함수의 이웃 결함
백업이 매 실행마다 쌓인다 — 조건이 dbVersion > 0 뿐이라 적용할 마이그레이션이 없어도 백업한다. 지우는 코드도 없다. 하루 5번 켜면 1년에 1,800개다.
Windows 에서 경로가 깨진다 — dbPath.split('/') 는 C:\… 를 쪼개지 못한다.
언제
Task 4. 세 건이 한 함수에 있으니 한 번에 고친다.
HIGH Unit of Work 가 ADR 스스로 요구한 것을 어긴다
무슨 일인가
ADR-015 는 async 콜백을 넘기면 "트랜잭션이 커밋된 뒤에 본문이 실행되는 조용한 버그"가 된다며 "타입으로 Promise 반환을 막는다"고 명시했다. 그런데 같은 ADR 의 코드와 계획서의 ports.ts 는 run<T>(work: (repos) => T): T 라 T = Promise<X> 를 완벽히 허용한다.
무엇이 깨지나
정산 확정처럼 8단계가 원자적이어야 하는 곳에서 롤백이 통째로 사라진다. 계약 테스트도 동기 throw 만 검사해서 이 케이스를 못 잡는다.
언제
Task 5. 지금은 3줄이고 나중엔 전 서비스 시그니처다.

B. 요구사항을 스키마가 표현할 수 없다

기능 문서가 명확히 요구하는 상태인데 컬럼 집합으로 만들 수가 없다. 이 갈래는 구현하다 막히는 종류라, 발견 시점이 늦을수록 비싸다.

HIGH재현함 "목록에서 치움" 상태를 만들 수 없다
상세
§3 증거 3 참조.
언제
지금이 낫다. 컬럼 추가는 나중에도 되지만, M2 에서 오늘 목록을 짜다 막히면 마이그레이션을 한 번 더 내야 한다.
HIGH 온보딩을 건너뛴 사용자의 첫 뽀모가 기록되지 않는다
세 문서가 서로 모순된다
R8 — weekly_capacity 의 미설정은 NULL 이고 오류가 아니다. 첫 실행에 기본 배열을 넣지 말 것, 특히 [0,0,0,0,0,0,0] 초기화 금지.
R14 — weeks 행은 그 주의 첫 세션이 기록될 때 생기고, 그때 capacity·budget 을 함께 박제한다.
계획서 DDL — 그 두 컬럼이 NOT NULL.
무엇이 깨지나
온보딩은 건너뛸 수 있다. 그러면 capacity 가 NULL 인 채로 쓰는 게 정상 경로인데, 첫 뽀모가 끝나는 순간 weeks 행을 만들어야 하고 넣을 값이 없다. [0,…] 을 넣으면 R8 이 금지한 "미설정과 예산 0 의 구분 불가"가 스냅샷에 영구히 박제된다. 타이머 PRD 의 목표 1 — "계획이 0개여도 타이머·기록·알림이 완전히 동작한다" — 이 첫 화면에서 실패한다.
언제
지금. NOT NULL 변경은 테이블 재작성이다.

C. 문서끼리 모순된다

MEDIUM "남은 몫" 정의가 두 기능 문서에서 다르다
같은 값, 다른 인수 기준
정산 문서는 max(1, est − 소진), 주간 계획 문서는 max(0, est − 소진) 이다. est 3 · 소진 5 인 항목의 남은 몫이 각각 1 과 0 이 된다.
왜 지금 닫아야 하나
아래 갈래 D 에서 추가하려는 est_pomos >= 1 CHECK 과 충돌한다. 이월된 항목의 est 가 0 이 될 수 있다면 그 CHECK 이 정상 정산을 죽인다. CHECK 을 쓰기 전에 결정이 필요하다.

D. 강제할 수 있는데 하지 않고 있다

DB 로 옮길 수 있는 불변식이 앱 코드의 규율로 남아 있는 경우다. 전부 "지금은 잘 지켜지고 있는" 것들이라 티가 안 난다.

HIGH PRD 가 명시적으로 스키마에 위임한 제약 2건이 없다
문서가 직접 넘겼다
주간 계획 문서 — "est 는 정수 ≥ 1. 단 is_system = 1 인 기타 항목은 예외로 est = 0. 이 예외를 컬럼 제약으로 어떻게 표현하는지는 ADR-011 §6 소관이다."
뽀모 기준 문서 — "길이 하한은 1분, 정수만. 거부는 경계에서 — IPC 스키마 + SQLite CHECK"
지금 들어가는 값들
est_pomos = -3 · focus_min = 0 · budget = -99 · duration_sec = -100 · days = 'nope' · capacity = 'not json'
가장 나쁜 것
is_system = 7. ADR-012 §4 의 차액 정의가 is_system = 0 술어에 의존하는데, 7 인 행은 = 0 에도 = 1 에도 안 걸려 양쪽 어디에서도 세어지지 않는다. "이중 계상도 누락도 산술적으로 불가능"이라던 성질이 깨진다.
MEDIUM 성공 지표를 DB 가 지키게 할 수 있는데 FK 가 없다
지표 원문
"세션이 있는 주 중 weeks 스냅샷이 없는 주가 0건 — 쿼리로 검증 가능하다."
문제
sessions.local_week → weeks.week FK 가 없다. 분기 하나만 빠뜨려도 조용히 깨지고, 깨지면 "행 없으면 전역값" 폴백으로 과거 주가 최신 전역값으로 해석된다 — ADR-013 이 존재하는 이유 자체가 되살아난다. 그리고 "쿼리로 검증 가능하다"는 말은, 그 쿼리를 아무도 안 돌리면 아무 일도 안 일어난다는 뜻이다.
고치는 법
한 줄. 트랜잭션 순서가 이미 "weeks 먼저, 세션 나중"이라 즉시 FK 로 성립한다.
주의
week_items.week 에는 같은 FK 를 걸면 안 된다. 정산 확정 트랜잭션이 week_items 를 먼저 넣고 weeks 를 나중에 만든다.
MEDIUM ADR-006 이 지정한 것 두 가지가 빠졌다
settings 에 updated_at 이 없다
ADR-006 §2 는 네 테이블(tasks · week_items · milestones · settings)을 명시했다. settings 는 워터마크와 베이스라인을 담는, 멀티기기에서 가장 충돌 가능성이 높은 테이블이다.
어느 테이블에도 $onUpdate 가 없다
ADR-006 이 지정한 자동 갱신 수단이 통째로 빠져서, 모든 UPDATE 경로가 손으로 updated_at 을 넣어야 하고 누락은 컴파일러가 못 잡는다.
덤
settings.value 는 "JSON" 이라고 주석만 있고 검증이 없다. 그리고 R8 이 말한 "키 부재 또는 NULL" 중 후자가 NOT NULL 때문에 표현 불가다.
MEDIUM 순간 컬럼 21개 중 형식 검사가 있는 건 1개
그마저도 느슨하다
GLOB '*Z' 는 'Z' 한 글자도, 'hello Z' 도 통과시킨다. ended_at 에는 형식 검사도 ended_at >= started_at 순서 검사도 없다.
왜 중요한가
created_at 은 항목 목록과 정산 3택의 정렬 키다. 형식이 섞이면 사전순 = 시간순이 깨진다.

E. 구조에 빈 자리가 있다

스키마가 아니라 백엔드 구조 쪽 발견이다. "틀렸다"기보다 정의된 적이 없어서 누구든 아무 데나 놓게 되는 자리들이다.

"주간 정산 확정" 한 건이 지나가는 길 클릭에서 커밋까지 · 빨간 줄이 정의되지 않은 자리
renderer 확정 버튼 → useMutation 화면은 사용자가 바꾼 예외만 보낸다. 전체 목록을 보내지 않는다
preload contextBridge 화이트리스트 1줄 채널 문자열이 계약과 맞는지는 컴파일러가 검사하지 않는다
main · 핸들러 발신자 검증 → 요청 parse → 서비스 호출 → 응답 parse handleIpc 가 유일한 등록 경로. 여기까지는 구현돼 있다
서비스 services/review.ts — 이 파일은 계획 어디에도 이름이 없다 정산 로직이 살 파일이 지정되지 않았다
트랜잭션 안 판정 → 대상 조회 → 순수 계산 → 폐기·이월·재부모화 → 스냅샷 → 워터마크 8단계가 원자적이어야 한다. I/O·await·사용자 확인이 하나도 없어 동기 트랜잭션에 정확히 들어간다
순수 도메인 이 계층이 살 디렉토리가 문서 어디에도 없다 ADR-008 은 3층을 선언하지만 폴더를 지정하지 않는다. ESLint 도 이 경계만 규칙이 0개다
커밋 이후 트레이 갱신 · 알림 · renderer 통지 — 순서 규칙이 없다 트랜잭션 안에서 알림을 띄우면, 롤백돼도 사용자는 "완료" 알림을 받는다
트랜잭션 경계 자체는 건전하다 — 계획된 유스케이스 중 트랜잭션 안에 비동기가 필요한 것은 없다. 문제는 "필요 없다"가 아니라 "불가능하게 막혀 있지 않다"는 것이다 (갈래 A 의 UoW 항목).
HIGH main 이 스스로 만든 변경을 renderer 가 알 방법이 없다
무엇이 깨지나
타이머는 main 이 소유한다. 창이 닫혀 있어도 main 이 세션을 INSERT 한다. 세션 1행이 들어가면 오늘 목록 도트·주간 게이지·캘린더 점·마일스톤 진척이 전부 바뀐다. 그런데 renderer 는 그 mutation 을 호출한 적이 없으니 캐시를 무효화할 계기가 없다. 창을 열어둔 채 25분 뽀모를 완주하면 화면 숫자가 그대로다. 앱의 핵심 루프가 조용히 틀린 값을 보여준다.
지금 있는 방향과 없는 방향channels.ts · preload · api.ts
renderer
invoke → handle
요청·응답. 구현돼 있고 zod 로 양방향 검증된다
main
renderer
타이머 전이 · DB 변경 통지 · 테마 변경
채널도, 계약 형태도, preload 노출도 없다
main
계획서는 "타이머 상태 구독 방식"을 별도 ADR 로 이연해 두었다. 그런데 이연된 것은 타이머 상태이고, DB 변경 통지는 어느 문서에도 이연 표기조차 없다. Api 타입이 {req, res} 형태에만 매칭되는 구조라, push 를 추가하면 해당 멤버가 never 가 되어 제네릭 기계 자체를 고쳐야 한다.
HIGH 도메인 에러와 버그를 renderer 가 구분할 수 없다
무슨 일인가
handleIpc 는 모든 실패를 new Error(문자열) 로 던지고, Electron 의 invoke 는 커스텀 클래스나 code 프로퍼티를 경계 너머로 보내지 못한다. 그런데 정산 기술 명세는 STALE_RANGE 라는 에러 코드와 그에 대한 화면 처리를 계약으로 규정하고 있다 — 예외가 아니라 정상 UX 경로다.
무엇이 깨지나
renderer 는 "계약 위반(버그)" · "STALE_RANGE(정상 경로)" · "제약 위반(데이터 사고)"를 전부 같은 rejected promise 로 받는다. 구현하다 보면 결국 e.message.includes('STALE_RANGE') 를 쓰게 되고, 그 순간 계약이 문자열 파싱으로 퇴화한다.
권장
기대 가능한 실패는 에러가 아니라 값으로 만든다 — res 를 성공/실패 판별 유니온으로 두면 zod 로 검증되고 타입이 renderer 까지 그대로 간다. "계약은 단일 정의"라는 ADR-007 원칙과도 일관된다.
MEDIUM "DB 없이 정산을 테스트한다"는 이득이 절반만 참이다
왜
ADR-008 이 위험 로직으로 꼽은 것은 "carry 사슬에 건너뛴 주 가산, 남은 몫 계산, 절반 올림"이다. 그런데 기술 명세는 remaining·carryWeeks·항목 소진을 전부 SQL 식으로 정의한다. 즉 ADR-008 이 "버그 나면 데이터가 오염된다"고 지목한 바로 그 산술이 SQL 안에 있어 실 DB 없이는 못 잡는다.
권장
포트가 원자 사실만 반환하게 한다 — { id, week, originWeek, estPomos, spentPomos }. 나머지 산술을 순수 함수로 올리면 인수 기준 여러 개가 그대로 DB 없는 테이블 테스트가 된다.
05

지금 결정해야 하는 네 가지

나머지는 전부 착수 후에 처리할 수 있다. 아래 넷만 스키마를 확정하기 전에 정해야 한다 — 되돌리려면 사용자 실데이터 위에서 테이블을 재작성해야 하는 것들이기 때문이다.

결정 1

capacity 미설정 상태를 어떻게 담을 것인가

온보딩을 건너뛴 사용자가 첫 뽀모를 완주할 때 weeks 행에 넣을 값이 없는 문제.

Acapacity·budget 을 nullable 로 바꾸고 "행은 있는데 예산 기록은 없음"을 1급 상태로 인정한다.
Bweeks 행 생성 시점을 첫 세션이 아니라 "capacity 가 정해진 뒤"로 미루고, "세션 있는 주는 반드시 스냅샷을 가진다"는 R17 을 완화한다.
결정 2

"남은 몫"을 어느 정의로 통일할 것인가

정산은 max(1, …), 주간 계획은 max(0, …). 이걸 정해야 est_pomos CHECK 을 쓸 수 있다.

A정산 쪽(min 1)이 이월 est 를 소유하고, 주간 계획의 max(0, …) 은 "표시용"임을 문서에 명시해 분리한다.
B한쪽으로 통일하고 다른 쪽 인수 기준을 고친다.
결정 3

task_pulls 에 치움 표현을 넣을 것인가

넣지 않으면 오늘 목록의 인수 기준 두 개 중 하나는 반드시 깨진다. 사실상 선택지가 없지만, 컬럼 이름과 재-pull 의미론은 정해야 한다.

—removed_at(순간, NULL = 표시 중) + created_at(2차 정렬 키) 추가를 권장한다.
결정 4

제약 강화안을 승인할 것인가

CHECK 재작성(달력 키 4종 + 순간 컬럼 + 값 범위), 누락 FK 1건, 부분 UNIQUE 인덱스 1건. 전부 초기 마이그레이션에 들어가야 하는 것들이다.

—새 결정이 아니라 ADR-011 §6 이 이미 정한 것의 실행분이다. 다만 양이 많아 한 번 훑고 넘어가는 편이 낫다.

07

제안하는 ADR

계획은 결정을 만들지 않는다 — 설계 결정은 ADR 로 먼저 남긴다. 위 결정들을 성격별로 묶으면 세 건이 된다.

ADR-018

첫 실행 상태와 weeks 스냅샷

capacity 미설정의 표현, 시딩 대상과 비대상의 목록, settings.value 의 NULL 표현. 결정 1 이 여기 들어간다.

ADR-019

제약 실행분 확정

CHECK 강화안, 누락 FK, task_pulls 컬럼, "남은 몫" 정의 통일. 결정 2·3·4 가 여기 들어간다. ADR-011 §6 의 결정을 뒤집는 게 아니라 실행분을 확정하는 것이다.

ADR-020

DB 안전장치

WAL 을 인지하는 백업 방식, 보존·회전 정책, 손상 감지와 마이그레이션 실패 복구 경로. Task 4 의 구현이 이걸 따른다.

그리고 ADR-010 의 잘못된 CHECK 식과 "실증" 표기, ADR-011 §7 의 foreign_keys 기본 OFF 문장은 상태 줄에 정정을 단다. 결정이 뒤집힌 게 아니라 근거가 틀렸거나 낡은 경우이므로 본문은 이력으로 그대로 둔다.

08

잘 되어 있는 것

심사는 결함을 찾도록 지시받았지만 양쪽 다 자발적으로 같은 것들을 짚었다. 이건 형식적 균형 맞추기가 아니라, 왜 고칠 가치가 있는지에 대한 답이다 — 토대가 부실하면 이런 심사 자체가 무의미하다.

스키마

  • ADR 정정 체인이 정확히 반영됐다. ADR-011 의 폐기된 판이 한 군데도 안 남았고, ADR-014 의 삭제 표현이 테이블별로 정확히 다르게 배치됐다 — "세 ADR 을 손으로 병합한 결과물치고 오류가 0"이라는 평가를 받았다.
  • 불변 달력 키 설계가 실측으로 검증됐다. 모든 날짜 조회가 인덱스를 탄다. 조회 시점에 strftime() 으로 파생했다면 타임존 이동에 과거 기록이 소급해 옮겨 가고 인덱스도 못 썼을 것이다.
  • origin_week 박제로 이월 배지를 사슬 추적 대신 날짜 산술로 바꾼 것이 건너뛴 주 버그를 구조적으로 없앤다.

구조

  • 응답까지 검증하는 handleIpc — 흔히 빠뜨리는 방향이다. main 쪽 버그가 renderer 를 조용히 깨는 대신 경계에서 죽는다. 에러 메시지에 입력값을 싣지 않는 판단도 정확하다.
  • 정산의 워터마크 단일 저장값 설계가 정시·지각·첫 실행·확정 직후를 분기 없이 통과시킨다. 경계 시나리오 15행이 그대로 테스트 테이블이 된다.
  • ADR 의 정정 관행 — 어느 절이 죽고 어느 절이 사는지 상태 줄에 명시하는 것 — 이 이번 심사에서 문서 간 충돌을 판정 가능하게 만들었다.
이 심사의 한 줄 요약

"첫 마이그레이션에 제약을 전부 넣겠다는 ADR-011 §6 의 판단 자체가 옳다. 누락된 것은 판단이 아니라 실행분이다."

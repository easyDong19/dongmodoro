이 문서가 다루는 것: 기획 문서가 전부 확정된 뒤(같은 날 오전 세션), 첫 구현 마일스톤 M1 스캐폴딩(창·DB·IPC 왕복까지의 워킹 스켈레톤)의 계획을 세우면서 내린 결정들이다. 계획서를 어디에 두고 어디까지 담을지에서 시작해, IPC 계약 보강을 거쳐, main 프로세스의 DB 접근 구조(DIP 도입) 논쟁으로 끝났다. 각 카드는 문제 → 고민한 선택지 → 결정 → 이유 순서로 읽으면 된다. ● 표시가 최종 선택이다.
반전 AI 추천을 기각했거나 선택을 번복한 지점 재설명 결정 전에 상세 설명·분석을 요구한 지점 검증 조사·외부 자료 대조로 사실을 확인한 지점 점선 카드 = 질문이 아닌 이벤트

1 · 상태 확인

"어디까지 했더라"에서 시작했다. 기억과 저장소의 사실이 달랐다.

START

"스캐폴딩하다 멈춘 것 같은데" — 사실 확인 검증

git 브랜치·워크트리·스태시·reflog·스크래치 디렉토리·과거 세션 기록을 전수 확인한 결과, 스캐폴딩은 시작된 적이 없었다. 저장소에는 문서만 있고 앱 코드는 0줄. 비슷해 보인 유일한 흔적(미커밋 .claude/skills/electron/)은 앱 코드가 아니라 참고 지식 스킬 문서였다. 결론: 잃어버린 작업 없음, 처음부터 시작하면 됨.

2 · 계획의 골격 — 어디에, 어디까지

코드를 만들기 전에 계획서의 위치와 범위부터 확정했다.

Q1

구현 계획서를 어디에 기록하나

문제

docs/ 구조 규칙에는 origin·design-system·architecture·features 4종만 있고 "구현 계획서"(작업 지시서)는 어디에도 속하지 않는 새 문서 종류였다. 이력 밖(.claude/ 나 PR 본문)에 두면 "왜 이 순서로 만들었지"를 나중에 추적할 수 없다.

고민한 선택지
  • docs/plans/ 신설 (AI 추천) — git 이력에 남고 M2·M3 계획도 같은 자리에. 규칙 3줄 추가 필요
  • docs/superpowers/plans/ — 스킬 기본 경로. 규칙 추가는 없지만 폴더명이 문서 구조와 이질적
  • 저장소 밖 — docs/ 불변이지만 계획이 이력에서 사라짐
결정

docs/plans/ 신설. 규칙도 함께: 계획은 결정을 만들지 않고 ADR 을 참조만 하며, 끝난 계획은 이력으로 보존한다.

→ 이후 모든 구현 계획서의 자리가 됨. 첫 입주자: 2026-08-04-m1-scaffolding.md

Q2

첫 계획은 어디까지 담나

고민한 선택지
  • 스캐폴딩만 (AI 추천) — 창·DB·IPC·UI 세팅까지. 기능은 다음 계획으로
  • M1 전체 — 계획서가 커지고, 미결 2건(타이머 상태 구독·Query 키 계층)을 먼저 결정해야 함
결정

스캐폴딩만. 미결 2건은 타이머 착수 직전 별도 ADR 로 미룬다.

→ 태스크 7개짜리 계획서 초안 작성·커밋. Q5 반영 후 8개가 된다

3 · IPC 경계 — 표준과 대조하다

계획서의 IPC 패턴을 외부 기준과 대조해 갭을 찾고, 라이브러리 도입까지 검토했다.

Q3

IPC 계약에 보강할 것이 있나 검증

문제

계획서 Task 3 의 첫 유스케이스는 입력이 없어 응답 검증만 보여줬다. 이대로 패턴이 복제되면 입력 검증이 빠진 핸들러가 생긴다. 로컬 electron 스킬 + Electron 공식 보안 가이드와 대조하니 기존 방향(zod 단일 정의·화이트리스트·도메인 명령형)은 표준 이상이었지만 갭이 2건 있었다.

결정

보강 2건 채택 — ① 채널마다 요청/응답 zod 스키마 쌍 ② 발신자 검증(senderFrame 가드, 공식 가이드 요구사항). 둘을 강제하는 handleIpc 헬퍼가 유일한 등록 경로.

ㅇㅇ 보강해야할듯 — 작업 위치는 "판단만" 요청 → 계획서가 main 미반영이므로 같은 브랜치에 커밋 추가로 확정.

새 ADR 불필요 (ADR-007 "경계에서 검증"의 구체화) → 계획서 Task 3 수정

Q4

electron-trpc 를 도입하나 재설명

문제

수동 3파일 패턴(채널·스키마·preload 매핑)의 보일러플레이트 대신 tRPC 기반 라이브러리를 쓰는 선택지가 있었다. 학습 곡선·트레이드오프· "나중에 갈아타고 싶으면 지금 구조로 되나"까지 분석을 요구했다.

고민한 선택지
  • 수동 3파일 패턴 유지 (AI 추천) — IPC 표면이 작고(유스케이스 20~30개), 계약 설계 자체가 학습 목표(ADR-007)
  • electron-trpc — 라우터·자동 타입·Query 통합. 의존성 + 추상화 한 겹 + 푸시를 subscription 으로 전환 + ADR-007 supersede 필요
결정

도입하지 않는다. 전환 대비 확인: 핸들러가 얇고 zod 가 공용이라 갈아탈 때 교체 범위가 가장자리 3곳(핸들러 등록·preload·api 파사드)에 갇힌다. 조건 하나 — renderer 는 shared/api.ts 파사드로만 IPC 접근.

→ 이 논의 말미의 "서비스가 인터페이스에 의존하나?" 질문이 Q5 로 이어짐

4 · DB 접근 구조 — DIP 논쟁

이 세션의 가장 큰 결정. AI 권고가 두 번 기각되고 문서 서술 오류가 정정됐다.

Q5

main 서비스는 DB 에 직접 의존해도 되나 반전 재설명

문제

overview.md 는 "IPC 경계가 이미 그 추상화다"라며 리포지토리 계층을 안 만들기로 했었다. 그러나 IPC 경계는 renderer 를 위한 유스케이스 파사드일 뿐, main 내부에서는 서비스가 Drizzle 에 직접 의존한다 — 사용자 지적("엄밀히 따지고보면 아니지 않나")으로 서술의 부정확함이 확인됐다. A/B 구조 비교 도식을 요청해 보고 결정했다.

고민한 선택지
  • A. 직접 호출 유지 (AI 추천, 2회) — 테스트는 실제 인메모리 SQLite, 로직 격리는 순수 함수. 구현체 1개인 인터페이스는 의식(ceremony)이라는 근거
  • B. 리포지토리 포트 (DIP) — 서비스는 포트에만 의존, Drizzle 구현체 격리, 테스트 더블 교체 가능. 대신 파일 증가 + Unit of Work 설계 필요
결정

B. 리포지토리 포트 도입. ("B안으로 가자")

그니깐 인터페이스화해서 DIP를 구현해놓는게 맞는거 같다. 테스트를할때 무조건적으로 하나의 DB로 하지 않을꺼고, 직접 테스트 DB도 띄워서 할수도 있기떄문이지 추상화를 지금 해놔야 나중에 기획변경이나 스택 변경에 유리할꺼같아 이거는 비용을 지불할만한 단계인거같아

→ ADR-015 신설: 포트는 서비스가 정의(범용 CRUD 금지) / Drizzle import 는 db/ 하위만 / UoW 는 동기 트랜잭션(async 콜백 금지) / 구현체 공유 계약 테스트. ← Q4 의 파사드 조건과 합쳐져 main·renderer 양쪽 심(seam)이 완성됨

END

## A. 계획 문서의 골격

### Q1. 구현 계획서를 어디에 기록하나

- 배경: `docs/` 구조는 docs/CLAUDE.md 가 `origin / design-system / architecture / features`
  4종으로 규정하는데, "구현 계획서"(작업 지시서)는 어디에도 속하지 않는 새 문서 종류였다.
- 선택지:
  - **docs/plans/ 신설 (AI 추천)** — 이력이 git 에 남고 M2·M3 계획도 같은 자리에 쌓임. 대신 docs/CLAUDE.md 규칙 추가 필요
  - docs/superpowers/plans/ — 계획 작성 스킬의 기본 경로. 규칙 추가는 불필요하나 폴더명이 프로젝트 문서 구조와 이질적
  - 저장소 밖(.claude/ 또는 PR 본문) — docs/ 를 안 건드리지만 계획이 이력에 남지 않음
- **결정: docs/plans/ 신설.** docs/CLAUDE.md 에 규칙 3줄 추가 — 계획은 결정을 만들지
  않고 ADR 을 참조만 하며, 실행이 끝난 계획은 이력으로 보존한다.
- 이유: 선택지 제시 후 추천안 그대로 선택. (이 프로젝트는 결정 원장·ADR 등 이력
  추적을 중시하는 저장소라 계획서만 이력 밖에 두면 원칙과 어긋난다는 근거)
- 파생: 이 원장을 포함해 이후 모든 구현 계획서의 위치가 확정됨.

### Q2. 첫 계획의 범위

- 선택지:
  - **스캐폴딩만 (AI 추천)** — 프로젝트 뼈대(창·DB·IPC·UI 세팅)까지만. 기능 구현은 다음 계획으로 분리
  - M1 전체(스캐폴딩+코어 루프) — 계획서 하나로 끝나지만 커지고, 미결 2건(타이머 상태 구독·Query 키 계층)을 먼저 결정해야 함
- **결정: 스캐폴딩만.** 미결 2건은 타이머 착수 직전 별도 ADR 로 미룸.
- 파생: 계획서가 태스크 7개(→ Q5 반영 후 8개)의 워킹 스켈레톤 계획으로 확정.

## B. IPC 경계

### Q3. IPC 계약에 보강할 것이 있나

- 배경: "궁금한게 아직 IPC 형식 인터페이스같은건 안만들었지? 그거에 대해서
  best-practice같은건 없나? skills나 인터넷에서 찾아서 말이지" — 계획서 Task 3 의
  IPC 패턴을 외부 기준과 대조 요청.
- 검증: 로컬 electron 스킬(ipc-security.md) + Electron 공식 보안 튜토리얼 + 커뮤니티
  라이브러리 비교. 결과: 기존 방향(zod 단일 정의·화이트리스트·도메인 명령형)은 표준과
  일치하거나 그 이상. 갭 2건 발견 —
  ① 응답만 검증하고 **입력 검증이 패턴에 없음** ② **발신자 검증(senderFrame) 부재**
  (Electron 공식 가이드: "모든 IPC 메시지의 발신자를 검증하라").
- **결정: 보강 2건 채택 — 채널마다 요청/응답 zod 스키마 쌍 + 발신자 검증.
  둘을 강제하는 `handleIpc` 헬퍼를 유일한 핸들러 등록 경로로 삼는다.**
- 이유: "ㅇㅇ 보강해야할듯"
- 작업 위치 판단(부속 결정): "근데 현재 브랜치에서 저걸 작업해야하나 아니면 어떻게
  작업해놔야할까? 판단만해줘" → 계획서가 아직 main 미반영이므로 **같은 브랜치에 커밋
  추가, PR 1개로** 확정.
- 파생: 새 ADR 불필요 판단 (ADR-007 "경계에서 검증"의 구체화) → 계획서 Task 3 수정.

### Q4. electron-trpc 를 도입하나

- 배경: "현재는 ipc에 직접 구현하고 레이어계층을 나눠서 작업하지만 electron-trpc를
  도입하는것도 하나의 방법일꺼같은데 학습 곡선이 좀 크나? 트레이드오프와 현 프로젝트의
  복잡성을 비교해봤을떄 어떻게 생각해?"
- 선택지:
  - **수동 3파일 패턴 유지 (AI 추천)** — 채널·스키마·preload 매핑 보일러플레이트를 감수. IPC 표면이 작고(유스케이스 20~30개) 계약 설계 자체가 학습 목표(ADR-007)
  - electron-trpc 도입 — 라우터·자동 타입·TanStack Query 통합을 얻지만, 의존성·추상화 한 겹·푸시 이벤트의 subscription 전환 비용. ADR-007 supersede 필요
- **결정: 도입하지 않는다. 단, 나중에 갈아탈 수 있는 구조인지 확인하고 유지한다.**
- 근거 확인: 핸들러가 얇고(zod parse → 서비스 호출) zod 스키마가 tRPC 입력 파서로
  재사용 가능해, 전환 시 교체 범위가 가장자리 3곳(핸들러 등록·preload·renderer api
  파사드)에 갇힘. renderer 의 IPC 접근을 `shared/api.ts` 파사드 한 곳으로 유지하는
  것이 조건.
- 파생: → Q5 (이 논의의 "서비스가 인터페이스에 의존하나?"라는 질문이 DB 접근 구조
  논쟁으로 이어짐)

## C. DB 접근 구조

### Q5. main 서비스는 DB 에 직접 의존해도 되나 (DIP 논쟁)

- 배경: Q4 말미의 질문 "서비스계층에 구현체가 인터페이스에만 의존하게 계획이
  짜여져있나?"에 AI 가 "의도된 부재(YAGNI, ADR-008)"라고 답하자 반박이 나왔다:
  "그럼 의미에서 이 구조가 코드 베이스 자체에서 직접 호출하는 구조아닌가? 리포지토리
  추상화계층은 만들어야하지 않나? IPC 경계가 이미 추상화라고했는데, 그건 아니지 않나
  엄밀히 따지고보면?"
- 사실 정정: 지적이 옳았다. overview.md 의 "IPC 경계가 이미 그 추상화다"는 엄밀하지
  않다 — IPC 경계는 **renderer 를 위한 유스케이스 파사드**일 뿐, main 내부에서는
  서비스가 Drizzle 에 직접 의존한다. (→ 특기 사항 2)
- 선택지 (구조 비교 도식을 요청해 검토 후 결정):
  - A. 직접 호출 유지 (AI 추천) — 테스트는 실제 인메모리 SQLite, 로직 격리는 순수 함수 계층. 구현체 1개인 인터페이스는 의식(ceremony)이라는 근거
  - **B. 리포지토리 포트 (DIP)** — 서비스는 포트에만 의존, Drizzle 구현체 격리, 테스트 더블 교체 가능. 대신 파일 증가 + Unit of Work 설계 필요
- **결정: B. 리포지토리 포트 도입.** ("B안으로 가자")
- 이유: "그니깐 인터페이스화해서 DIP를 구현해놓는게 맞는거 같다. 테스트를할때
  무조건적으로 하나의 DB로 하지 않을꺼고, 직접 테스트 DB도 띄워서 할수도 있기떄문이지
  추상화를 지금 해놔야 나중에 기획변경이나 스택 변경에 유리할꺼같아 이거는 비용을
  지불할만한 단계인거같아"
- 파생: [ADR-015](../architecture/decisions/adr-015-repository-ports.md) 신설
  (포트는 서비스가 정의 / Drizzle import 는 `db/` 하위만 / UoW 동기 트랜잭션 /
  구현체 공유 계약 테스트). overview.md 확장성 절 갱신, ADR-008 부분 정정 표기,
  계획서에 Task 5(포트 패턴 고정) 신설로 태스크 8개.

## 특기 사항 (AI 오판·정정)

1. **"스캐폴딩 하다 멈췄다"는 기억은 사실이 아니었다.** 세션 시작 시 "스캐폴딩하다가
   중간에 멈춘거같은데"라는 인식이 있었으나, git(브랜치·워크트리·스태시·reflog)·
   스크래치 디렉토리·과거 세션 기록 전수 확인 결과 **스캐폴딩은 시작된 적이 없음**을
   확정했다. 유일하게 비슷한 흔적은 미커밋 `.claude/skills/electron/` 폴더였는데,
   앱 코드가 아니라 Electron 참고 지식 스킬 문서였다.
2. **AI 가 overview.md 의 부정확한 서술을 그대로 옹호했다.** "IPC 경계가 이미
   리포지토리 추상화"라는 문서 서술을 근거로 리포지토리 계층 불요를 주장하다가,
   사용자의 "엄밀히 따지면 아니지 않나" 지적에 두 개념(유스케이스 파사드 vs
   리포지토리 추상화)이 다름을 인정했다. 문서 자체도 이번에 정정됐다.
3. **AI 는 DIP 도입(Q5-B)을 두 차례 반대 권고했으나 기각됐다.** 반대 근거(구현체 1개,
   인메모리 실 DB 테스트가 목보다 정확, YAGNI)는 ADR-015 의 Context 에 기각된
   선택지로 보존돼 있다.

## 미결 (의도적으로 미룬 것)

- **타이머 상태 구독 방식**(ADR-002 미결)과 **Query invalidation 키 계층** — 스캐폴딩에
  불필요하고 타이머 구현의 관심사라서, 타이머 착수 직전 별도 ADR 로 결정한다.
- **main→renderer 푸시 채널의 구독 패턴**(리스너 등록 함수가 해제 함수를 반환) —
  타이머 태스크에서 다룬다.
- **잔여물 정리** — 미커밋 스킬 폴더 2개(`.claude/skills/electron/`, `plain-report/`)와
  빈 `worktree-agent-*` 로컬 브랜치 8개·머지 완료 원격 브랜치 2개. 별도 작업으로 미룸.

의사결정 플로우 — 시간 통화 전환

2026-08-12 · 원장: 2026-08-12-time-currency-session.md

"뽀모 길이를 바꿨는데 되돌아간다"는 문제 제기가 진단을 거쳐 기획 변경으로 커진 세션. 결론: 계획의 통화(예상 뽀모·예산·가용량)를 버리고 진행 표시를 측정 시간으로 바꾼다. 결론의 소유자는 ADR-029 · ADR-030.
반전 AI 추천 기각 / 선택 번복 재설명 결정 전 상세 분석 요구 검증 코드·DB 로 사실 확인

Phase 1 · 발단과 진단

문제가 버그인지 설계인지부터 확인했다.

문제 제기 검증

"지금 바꿔도 껐다키면 다시 50분으로 바뀌는데" — 뽀모 길이 편집이 반영되지 않는 것으로 보임.

진단: app.db 직접 조회. 저장은 정상(settings.focus_min=50), 원인은 이번 주 weeks 행에 박제된 스냅샷 — ADR-013 의 효력 지연이 설계대로 동작한 것.

버그가 아니라 "설계가 사용자에게 저장 실패로 읽히는" 기획 문제로 재정의.

기획 변경 선언 재설명

사용자 원문: "1. 뽀모 세팅값은 변경하면 저장하게 해야함 2. 예상뽀모, 없애고 대신 절대적 시간 값을 측정하는게 좋아보임. 예상뽀모를 추가하는건 플로우를 복잡하게 함. 3. 그에따라 … 관련 DB테이블도 삭제해야함"

AI 분석: 즉시 적용(1)은 예상 뽀모 폐지(2)의 따름정리 — 효력 지연의 보호 대상이 개수 예산이므로. 측정은 새 장치 불요 — sessions.duration_sec 가 이미 저장 중.
→ Q1~Q5 (갈림길 5개로 분해)

Phase 2 · 새 통화의 화면별 형태

예상 뽀모가 빠진 자리를 화면마다 하나씩 정했다.

Q1. 주간 계획 층의 모습

"얼마만큼"에 답하던 숫자(est·예산·가용량)가 사라지면 층의 정체성을 다시 정해야 한다.

  • 숫자 없는 리스트 — 예산·과적·게이지 전부 삭제
  • 시간 예산("주 20시간")으로 대체 — 과적 일부 생존
  • est 만 삭제, 예산 유지 — 반쪽 삭제
결정: 숫자 없는 리스트. 주간은 "이번 주에 뭘 할까"만 답한다.

"예상뽀모를 추가하는건 플로우를 복잡하게 함" — 숫자 입력 자체가 제거 대상이므로 시간 예산도 같은 부담의 재생산.

→ Q2 (정산의 분모 소멸) · → 미결 1 (과적 신호 없이 가기로)

Q2. 정산 요약

`계획 대비 소진(차액 포함)` 요약에서 계획 숫자가 죽는다.

  • 측정 시간 요약 — 총·항목별·자유 집중, 사실만
  • 처분(이월/폐기)만 남김
  • 시간 + 완료 개수 병기
결정: 측정 시간 요약.

"사실만 표시하고 판단은 사용자에게" 원칙과 일치 (추천안 수용).

→ 차액 정의(ADR-027) 폐기 — 자유 focus 시간 직접 합산으로 단순화

Q3. 월 마일스톤 롤업

`이번 주 3/8` 의 분모(예상 뽀모 합)가 죽는다.

  • 시간 롤업 — `이번 주 3시간 20분`
  • 뽀모 횟수만 — `이번 주 3뽀모`
  • 롤업 삭제 — 제목만
결정: 시간 롤업. 월 층 "수치 입력 없음" 원칙과 무충돌 — 입력이 아니라 파생이다.

Q4. 오늘 목록·주간 항목의 진행 표시

항목당 `소진/예상 뽀모`. 타이머는 계속 뽀모 사이클로 돌므로 단위 자체는 남는다.

  • 측정 시간만 — 표시 규칙 하나
  • 시간 + 뽀모 횟수 병기
  • 뽀모 횟수만 — 길이 가변 문제가 표시에 잔존
결정: 측정 시간만.
→ CONTEXT.md 의 뽀모 정의가 "집계 화폐" → "타이머 사이클 단위"로 좁아짐

Phase 3 · 데이터와 버저닝

파괴적 변경의 크기를 정했다.

Q5. 기존 데이터

  • 마이그레이션 — est·예산·가용량만 제거, 세션·항목 보존. 과거 주도 시간 표시 소급
  • DB 초기화 — 기록 전부 유실
결정: 마이그레이션.

Q6. 버저닝

"버저닝을추천해줘 이정도면 꽤 큰 변경사항이라서 말이지"

  • 2.0.0 — 통화 교체 + 테이블 삭제 + 화면 의미 변경
  • 1.2.0 — 파괴적 변경을 마이너에 싣게 됨
결정: 2.0.0. (AI 추천 수용, 현재 main 은 1.1.0)

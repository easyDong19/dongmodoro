테이블 7개와 그 사이의 관계. 방금 정한 네 가지 결정이 반영된 상태이며, 아직 결정하지 않은 항목은 따로 표시했다.

01

관계도

화살표는 참조 방향이다 — 화살표를 가진 쪽이 상대의 키를 컬럼으로 들고 있다.

일반 외래 키 이번에 추가하는 FK 논리 관계 — FK 를 걸 수 없다 자기 참조 필수 / 선택 FK 컬럼이 NOT NULL 인가 · 몇 개인지는 §03 표에

읽는 법 — 이 도형의 중심은 week_items 다

주간 항목이 계획의 단위이자 이월의 단위다. 위로는 마일스톤에 묶이고, 아래로는 할 일 조각으로 쪼개지며, 옆으로는 자기 자신을 가리켜 이월 사슬을 만든다. 나머지 테이블은 전부 이 축에 붙는다.

초록 선 — 이번에 추가하는 FK

sessions.local_week → weeks.week. "세션이 있는 주는 반드시 자기 스냅샷을 가진다"는 규칙이 지금까지는 앱 코드의 규율이었고, 성공 지표도 "쿼리로 검증 가능하다"로만 적혀 있었다. 이 한 줄이 그걸 DB 강제로 바꾼다 — 스냅샷 없는 주에 세션을 넣으면 INSERT 가 실패한다.

붉은 점선 — FK 를 걸면 안 되는 관계

week_items.week 도 논리적으로는 weeks.week 를 가리킨다. 그런데 정산 확정 트랜잭션이 이월 항목을 먼저 넣고 대상 주의 weeks 행을 나중에 만든다. 즉시 FK 를 걸면 그 순서에서 실패한다.

그래서 이건 앱이 지켜야 하는 불변식으로 남는다 — §04 목록의 첫 항목이다.

settings 는 어디와도 연결되지 않는다. 키-값 테이블이고, 담는 값은 베이스라인 길이·요일별 가용량·정산 워터마크·테마다. 관계가 없는 대신 값의 형식을 DB 가 검사하지 못한다 — 그게 §04 의 마지막 항목이다.

관계 하나에는 질문이 둘이다. "부모 하나에 자식이 몇 개 붙나" 와 "자식 하나가 부모를 몇 개 가리키나". 방향을 밝히지 않은 숫자는 뜻이 흐려진다.

표기 읽는 법

앞 숫자가 최소, 뒤가 최대다.

0..N없어도 되고, 여러 개여도 된다
0..1없어도 되고, 있어도 하나뿐
1반드시 정확히 하나
표기와 컬럼 정의는 같은 말이다

자식 쪽이 1 이면 그 FK 컬럼이 NOT NULL 이고, 0..1 이면 nullable 이다. sessions.task_id 가 nullable 인 것이 곧 "미분류 집중을 허용한다"는 뜻이다.

그래서 이 표에서 실제로 정보를 담은 쪽은 오른쪽 열이다. 왼쪽은 전부 0..N — 이 스키마에서 자식이 없어도 되는 부모는 예외 없이 전부다.

04

DB 가 지킬 수 없는 불변식

위 제약을 전부 넣어도 남는 것들이다. 앞으로 버그가 사는 자리이므로 코드 리뷰와 테스트가 여기를 봐야 한다.

불변식DB 가 못 잡는 이유
week_items.week 에 해당하는 weeks 행이 존재한다 정산 트랜잭션이 항목을 먼저 넣고 주를 나중에 만든다
집계 술어에 항상 sessions.local_week = week_items.week 가 붙는다 조건 누락은 문법 오류가 아니라 조용히 틀린 숫자다
weeks 의 스냅샷 컬럼은 행 생성 후 UPDATE 되지 않는다 SQLite 에 컬럼 단위 불변성이 없다
local_date·local_week 이 started_at 의 로컬 값과 정합 UTC 저장값에서 로컬 키를 재파생하는 것 자체가 금지라 검산 불가
이월 시 origin_week·milestone_id 를 승계한다 컬럼 값의 출처는 제약 대상이 아니다
마일스톤 삭제 시 자식의 updated_at 도 갱신한다 FK 의 SET NULL 은 다른 컬럼을 건드리지 않는다
부모 항목을 soft delete 하면 자식 조각도 함께 한다 soft delete 는 FK 가 인지하지 않는 UPDATE 다
settings 값이 키별 형식에 맞는다 키-값 테이블 — 값의 스키마를 컬럼 제약으로 표현할 수 없다

"한 주에 기타 항목 최대 1개"는 원래 이 목록에 있었는데, 부분 UNIQUE 인덱스로 DB 에 넘겼다. 목록에서 하나를 덜어낸 셈이다.

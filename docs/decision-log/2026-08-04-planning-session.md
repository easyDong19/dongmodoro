## A. 시간 체계

### Q1. 하루 경계

- 선택지: 자정 고정 / 오프셋(새벽 4시) / 오프셋+설정
- **결정: 자정 고정. 단, 그 기준이 뷰에서 드러나야 한다.**
- 이유: "하루가 바뀌는 시간은 자정이며, 그 기준에 대해서는 뷰에서 언급이 되어야
  바뀌는 시간이 뭔지 알 수 있을 것 같다." (AI 추천은 4시 오프셋이었으나 기각)
- 파생: 뷰 노출 방식은 Q18에서 확정.

### Q2. 자정을 걸친 세션의 날짜 귀속

- 선택지: started_at 기준 / ended_at 기준 / 더 긴 쪽
- **결정: `started_at` 기준.**
- 파생: 캘린더 점·스트릭·날짜 패널 전부 이 컬럼 하나로 파생.
  부수효과(자정 직후 빈 오늘 목록)는 Q18의 힌트로 완화.

### Q8-1. 주 시작 요일

- 선택지: 일요일(초안·시안 기준) / 월요일(ISO)
- **결정: 월요일.**
- 이유: "일반적으로 그게 통용되어 있으니까." + 일요일에 주간 계획을 세우는 건
  규칙으로 두되 나중에 바꿀 수 있게 확장 가능해야 함.
- 파생: `weekly_capacity` 인덱스 0 = 월요일로 재정의, 시안의 요일 UI(DOW 배열,
  캘린더 그리드, 요일 칩) 전부 월요일 시작으로 변경. 계획일 분리는 아래
  plan_lead_days 모델로 해결.

### plan_lead_days 모델 (Q8-1 파생)

- **결정: 계획일 = 주 시작 D-`plan_lead_days`일. 기본 1(일요일). v1 설정 미노출.**
- 판정식: 계획 대상 주 = week_of(오늘 + lead) / 정산 범위 = 워터마크+1 … 계획 대상 주−1.
- 이유: HTML 플로우 시각화(정시/지각/첫 실행 시나리오 표) 검토 후 "ㅇㅇ 이렇게 가자."
- 알려진 부작용 수용: 일요일 밤 리뷰 확정 후의 세션은 정산된 주에 들어감
  (리뷰 요약엔 미포함, 캘린더·소진엔 정상 반영). 막지 않는다.

### Q9. 주 키 표현 (2단계에 걸쳐 결정)

- 선택지: B `'2026-W32'` ISO 문자열 / E 그 주 월요일 날짜 `'YYYY-MM-DD'` / D 병기
- 경과: 처음 B 선택("절대 기준으로 보기 편하고 산술하기도 편하고")
  → AI가 정정: **산술은 B의 약점** (2026년은 53주 연도, `W52+1=W53`이라 문자열
  산술 불가) → "그러면 E가 맞지 않을까? 그 전에 실무 타임포맷 관리 방식과
  비교 분석해달라" → 타임포맷 규약 검토 후 **E 확정.**
- **결정: E — 주 키 = 그 주 월요일 날짜 `'YYYY-MM-DD'`. `W32` 라벨은 렌더 전용.**
- 근거: 프로젝트 시간 포맷이 3개(순간/달력 키/초)로 닫힘. `2026-08-03`은 달력만
  알면 직독되는 절대 기준. CHECK(`strftime('%w')='1'`)로 DB가 월요일 아닌 값 거부.

### 시간 포맷 규약 (Q9 파생)

- **결정: 4종 분류 채택. ADR로 남긴다.**
  - 순간 = UTC ISO 8601 `'...Z'` TEXT (started_at, created_at, …)
  - 달력 키 = 로컬 기준, 쓰는 순간 1회 계산 후 불변 (`local_date`, `pull_date`, `month`, 주 키)
  - 길이 = INTEGER 초
  - 런타임(타이머 IPC) = epoch ms, 저장 안 함
- `now()`/`dayKey()`/`weekKey()`는 시간 모듈 하나가 소유 (초크포인트).

## B. 타이머

### Q3. 휴식 사이클

- 선택지: 사이클 없음(시안 그대로) / 모드 자동 제안+시작 수동 / 휴식 자동 시작
- **결정: 모드만 자동 전환(4회차마다 긴 휴식), 시작은 수동.**
- 이유: "뽀모도로 앱이니 휴식이라는 개념이 필요함."
- 파생: 긴 휴식 카운터는 ERD 평가(S10) 반영으로 "그날 focus mod 4"가 아니라
  **"마지막 long 세션 이후 focus 수"**로 파생 (자정 경계에서 안 끊김).

### Q4. "완료 처리" 버튼 (시안에만 있던 조기 완료)

- 선택지: 제거 / 유지+온전한 1뽀모 / 유지+경과 하한
- **결정: 유지 + 온전한 1뽀모.**
- 이유: "오조작하는 경우가 많이 없기 때문에, 아쉽게 된 거고. 오조작이 너무
  많아진다면 나중에 완료한 태스크 롤백 패치를 넣으면 된다."
- 파생: `duration_sec`에 실제 경과 저장 → 시간 기준 통계 복원 가능.

### Q16. 창 닫기와 종료

- 선택지: 닫기 = 창만 닫힘(타이머 상주) / 닫기 = 종료
- **결정: 닫기 = 창만 닫힘, 타이머는 main에서 계속. ⌘Q가 진짜 종료.**
- 소결정: **focus 실행 중 ⌘Q는 확인 1회** ("종료하면 이 세션은 기록되지 않아요").
  크래시 복원은 v1에서 만들지 않음.
- 이유: "A 맞고, 1번 확인 묻는 게 맞음."

## C. 데이터 모델·집계

### Q5. 정산 필요 판정 (워터마크)

- 배경: `last_settled_week`의 갱신값·초기값이 초안에 없음 → 병합 정산 후 배너
  무한 반복 / 설치 직후 헛배너 가능. (상세 설명 요청 후 결정)
- 선택지: ① 워터마크 단독 / ② 정산 레코드 테이블 조회 / ③ 하이브리드
- **결정: ③ — 판정은 워터마크 단독, `week_settlements`(→weeks)는 스냅샷 이력 전용.**
- 워터마크는 정산한 주가 아니라 항상 "계획 대상 주 − 1"을 기록. 초기값 동일.

### Q6. 정산 리뷰의 범위

- 선택지: 마지막 활동 주만(초안) / 워터마크 이후 전 구간 병합 / 모달 강제
- **결정: 전 구간 병합.** 몇 주를 비웠든 리뷰 화면은 항상 1개, 항목 수만 증가.
- 파생: 초안의 "마지막 활동 주"·"빈 주 자동 통과" 문구는 범위 정의 한 줄로 대체.

### Q7. 부모 없는 task의 저장 위치

- 배경: 초안 세 곳 모순 (task→week 필수 vs 직접 입력·사후 캡처는 미연결).
  (테이블·키 개념부터 재설명 요청 후 결정)
- 선택지: A `week_item_id` nullable / B 주차별 시스템 "기타" 항목
- **결정: B — 기타 항목.** "예외를 컨트롤하는 것도 괜찮고."
- 기타 행 규칙: est 0 (과적·부하 미산입) / 플래너 편집·삭제 불가 / 리뷰 3택 제외 / lazy 생성.
- 파생: 사용자 관점에서 "주간에 속하지 않은 일간 계획"은 존재하고,
  데이터로는 존재하지 않는다 (항상 기타에 배선).

### Q10. 집계 귀속 기준 (ERD 평가 B1)

- 배경: 주간 총 소진(날짜 기준)과 항목 소진(관계 기준)이 어긋날 수 있음.
  유일한 구멍 = 일요일 밤 리뷰 확정 후 다음 주 항목 pull.
- 선택지: A pull을 오늘이 속한 주의 항목으로 제한 / B 날짜 필터+버킷 행 / C 관계 기준 허용
- **결정: A.** 두 기준이 구조적으로 항상 일치 → 게이지 = 항목 합 + 미분류가 무조건 닫힘.
- 대가 수용: "내일 계획을 오늘 밤 미리 시작"은 불가.

### Q11. 주간 카드의 시스템 행

- 선택지: A "기타"+"미분류 집중" 한 행 통합 / B 두 행 분리
- **결정: A — 한 행 ("기타 — 계획에 없던 집중").** 드릴다운에서 이름 있는 것/없는 것 구분.

### Q12. 이월 배지 "N주째"

- 선택지: A `origin_week` 박제 / B `carry_count` 저장 / C 재귀 CTE
- **결정: A.** 배지 = `(week − origin_week)/7 + 1` — SQL 한 줄, 건너뛴 주 자동 포함.
- `carry_from_id`는 직전 원본 추적·이력 전용으로 축소.

### Q13. 항목 est vs task est

- 선택지: A 독립 (다른 질문에 답함) / B 어긋남 사실 표시 추가
- **결정: A.** 리뷰의 "남은 몫"은 항목 est 기준. 드로어 사실 표시는 구현 시 재판단.

### Q14. 주간 항목의 완료 확정

- 선택지: A 자동 제안+수동 확정 / B 항상 수동 / C 자동 완료
- **결정: A.** 완료의 사실을 만드는 건 항상 사용자 클릭.
  완료된 항목의 드로어는 열람 가능·pull만 차단, 해제 시 재개.

### ERD 평가 수용분 (질문 없이 근거 확인 후 수용)

| 항목 | 내용 |
|---|---|

| B4 | `weeks` 테이블 신설 — 주별 예산 오버라이드·capacity·뽀모 길이·planned_at/settled_at. `week_settlements` 흡수, `long_break_min` 누락 보완 |

- **결정: B — 반응형.** "지금 단계에서 레이아웃 결정을 해야 편할 듯.
  반응형 레이아웃에 대한 계획도 세워야겠지."

### Q17-1. 반응형 3단계 계획

- **결정: 승인.**
  - 와이드(≥~1200px): 시안 3컬럼 그대로
  - 미디엄(~800–1199px): MONTH 컬럼 접힘 → 토글 시 오버레이. WEEK/TODAY 유지
  - 내로우(<~800px): 1컬럼 — 타이머 상단 고정(축약형) + `오늘|주간|월간` 탭
  - 최소 창: 내로우가 성립하는 크기(~420×640 부근, 실측)로 하한
  - 브레이크포인트는 tokens.md 토큰 + ADR
- 접힘 우선순위 근거: 원칙 1 "타이머가 코어 루프, 계획은 레이어" — 좁아질수록
  계획 레이어부터 접히고 타이머·오늘이 끝까지 남는다.

### Q18. 하루 경계(자정)의 뷰 노출

  2. 자정 직후 빈 오늘 목록: "새 날이 시작됐어요 — 어제 조각은 주간 카드에서 다시 가져올 수 있어요"

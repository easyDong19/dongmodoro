# 의사결정 기록 — 2026-08-12 시간 통화 전환 세션

> "뽀모 길이를 바꿨는데 껐다 켜면 되돌아간다"는 문제 제기에서 시작해, 원인 진단 →
> 예상 뽀모 폐지 결정 → 새 통화(측정 시간)의 화면별 형태 → 버저닝(2.0.0)까지 진행한
> 세션의 전체 기록. 각 항목: 질문 → 선택지 → **내 결정** → 결정 이유(내가 말한 것) → 파생 효과.
> 의사결정 흐름의 시각화: [2026-08-12-time-currency-session-flow.html](./2026-08-12-time-currency-session-flow.html)

결론만 요약하면: **계획의 통화(예상 뽀모·예산·가용량)를 버리고, 진행 표시를 세션에서
파생하는 측정 시간으로 바꾼다. 뽀모 길이 편집은 다음 세션부터 즉시 적용된다.**
결론의 소유자는 [ADR-029](../architecture/decisions/adr-029-baseline-immediate-effect.md) ·
[ADR-030](../architecture/decisions/adr-030-time-as-progress-currency.md) 이고,
실행 순서는 [구현 계획](../plans/2026-08-12-time-currency.md)이 갖는다.
이 문서는 그 결론에 이른 **과정**만 소유한다.

---

## 진행 방식

1. 사용자의 문제 제기("바꿔도 안 먹는다")를 실제 DB(`app.db`) 직접 조회로 진단
2. 진단 결과를 두고 사용자가 기획 변경 3건을 선언 (원문은 §A)
3. 갈림길 5개를 객관식으로 하나씩 결정 (Q1~Q5)
4. 화면·플로우를 HTML 와이어프레임으로 그려 눈으로 확인 후 설계 승인
5. 이 기록 + ADR 2건 + 구현 계획서 작성으로 종결

---

## A. 발단 — 문제 제기와 진단

### 무엇이 있었나

사용자가 정산 패널의 `조정` 에서 뽀모 길이를 바꿨는데 반영되지 않는 것을 발견했다.

> "그러면 기본 뽀모 값을 고정시키는건 어떻게 해야함 지금 바꿔도 껐다키면 다시
> 50분으로 바뀌는데"

DB 를 직접 열어 확인한 진단: **저장은 되고 있었다.** `settings.focus_min = 50` 으로
정상 기록됐고, 타이머가 계속 50분으로 돈 이유는 이번 주 `weeks` 행에 50분이 이미
박제돼 있었기 때문이다 — [ADR-013](../architecture/decisions/adr-013-baseline-budget-effect.md) §3
"편집은 언제든, 효력은 다음 주부터"가 설계대로 동작한 것이다.

즉 버그가 아니라 **설계가 사용자에게 "저장이 안 된다"로 읽힌 것**이 문제였다.
효력 지연은 "뽀모 개수로 잡은 주간 예산이 길이 변경으로 재해석되는 것"을 막는
보호 장치인데, 그 보호 대상(개수 예산)의 가치를 사용자가 인정하지 않았다.

### 사용자의 기획 변경 선언 (원문)

> "내 생각에는 기획 변경이 있어야 함
>
> 1. 뽀모 세팅값은 변경하면 저장하게 해야함
> 2. 예상뽀모, 없애고 대신 절대적 시간 값을 측정하는게 좋아보임. 예상뽀모를
>    추가하는건 플로우를 복잡하게 함.
> 3. 그에따라 예상뽀모와 체킹하는 로직이 삭제되야하며 관련 DB테이블도 삭제해야함"

### AI 의 구조 분석 (결정 전 공유)

- 1번과 2번은 한 묶음이다. 효력 지연의 존재 이유가 개수 예산 보호이므로, 예상 뽀모를
  없애면 지킬 분모가 사라져 즉시 적용이 자연스러워진다. **1번은 2번의 따름정리다.**
- 절대 시간 측정은 새 측정 장치가 필요 없다 — `sessions.duration_sec` 가 M2부터
  모든 세션의 실제 경과 초를 이미 저장하고 있다. 표시만 바꾸면 되고, 과거 주에도
  소급 적용된다.
- 예상 뽀모에 딸려 나가는 것: `weeks.budget`·`capacity`, `settings.weekly_capacity`,
  과적 경고, 예산 게이지, 정산의 `계획 대비`·차액, 마일스톤 롤업의 분모,
  `weeks` 스냅샷·효력 지연, PRODUCT.md 포지셔닝 1번("뽀모 개수가 단일 통화").

## B. 새 통화의 화면별 형태 (Q1~Q4)

### Q1. 예상 뽀모가 사라진 주간 계획 층은 어떤 모습인가

- **배경**: 주간 층은 "얼마만큼"이라는 질문에 뽀모 개수로 답하는 층이었다. 그 숫자가
  사라지면 층의 정체성 자체를 다시 정해야 한다.
- **선택지**:
  1. **숫자 없는 리스트** — 예산·가용량·과적·게이지 전부 삭제. 주간은 "이번 주에 뭘
     할까" 리스트로만. 가장 단순, 삭제 범위 최대.
  2. 시간 예산으로 대체 — "주 20시간" 같은 시간 단위 예산은 남긴다. 과적 개념 일부
     생존, 삭제 범위 중간.
  3. est 만 삭제, 예산 유지 — 항목별 예상만 없애고 주간 예산·가용량은 남긴다.
     반쪽 삭제라 비추천.
- **결정**: **1. 숫자 없는 리스트.**
- **이유**: 문제 제기 원문 그대로 — "예상뽀모를 추가하는건 플로우를 복잡하게 함."
  계획 시점의 숫자 입력 자체가 제거 대상이었으므로 시간 예산으로 바꿔 다는 것도
  같은 부담의 재생산이다.
- **파생**: → Q2 (비교할 계획 숫자가 없어져 정산 요약을 다시 정해야 함)
  → 과적을 계획 시점에 알 방법이 사라진다 (§미결 1)

### Q2. 정산 요약에 무엇을 보여주나

- **배경**: 정산 요약은 `계획 대비 소진(차액 포함)` 이었다. 계획 숫자가 죽으면 요약의
  분모가 사라진다.
- **선택지**:
  1. **측정 시간 요약** — 그 주 총 집중 시간 + 항목별 시간 + 자유 집중. 사실만 표시.
  2. 처분만 남김 — 요약 섹션 자체를 없애고 이월/폐기만. 가장 얕은 화면.
  3. 시간 + 완료 개수 — 완료 항목 수·뽀모 횟수 병기. 개수 집계가 다시 들어옴.
- **결정**: **1. 측정 시간 요약.**
- **이유**: "사실만 표시하고 판단은 사용자에게" 원칙(PRODUCT.md)과 일치하는 유일한
  선택지. (객관식 답변으로 결정 — 추천안 수용)
- **파생**: → 차액 정의([ADR-027](../architecture/decisions/adr-027-other-row-domain.md))가
  존재 이유를 잃는다. "계획에 없던 집중"은 차액이 아니라 자유 focus 세션의 시간
  직접 합산으로 단순화된다.

### Q3. 월 마일스톤 롤업의 형태

- **배경**: 롤업이 `이번 주 3/8`(소진 뽀모/예상 뽀모 합)인데 분모가 죽는다.
- **선택지**:
  1. **시간 롤업** — `이번 주 3시간 20분`. 새 통화와 일관.
  2. 뽀모 횟수만 — `이번 주 3뽀모`. 단위가 표시용으로 생존.
  3. 롤업 삭제 — 제목만 남김. 월 층 "수치 없음" 원칙의 완성형이지만 진행감이 없다.
- **결정**: **1. 시간 롤업.**
- **이유**: (객관식 답변으로 결정 — 추천안 수용) 월 층의 "수치 입력 필드를 두지
  않는다" 원칙과 충돌하지 않는다 — 이 숫자는 입력이 아니라 파생이다.
- **파생**: → milestones PRD 의 롤업 정의·CONTEXT.md `롤업` 용어 갱신

### Q4. 오늘 목록·주간 항목의 진행 표시

- **배경**: 항목당 `소진/예상 뽀모` 표기에서 분모가 죽는다. 타이머는 그대로 뽀모도로
  사이클로 돌므로 "뽀모"라는 단위 자체는 남는다.
- **선택지**:
  1. **측정 시간만** — 항목당 누적 집중 시간. 표시 규칙이 하나.
  2. 시간 + 뽀모 횟수 병기 — 정보는 많지만 한 항목에 숫자 두 개.
  3. 뽀모 횟수만 — 길이 가변 문제가 표시에 그대로 남는다.
- **결정**: **1. 측정 시간만.**
- **이유**: (객관식 답변으로 결정 — 추천안 수용) 통화를 바꾸는 김에 표시 규칙을
  하나로 통일한다.
- **파생**: → 뽀모의 정의가 "집계 화폐"에서 "타이머 사이클 단위"로 좁아진다
  (CONTEXT.md 갱신)

## C. 데이터와 버저닝 (Q5~Q6)

### Q5. 기존 데이터 처리

- **배경**: 지금 DB 에 세션 기록·주간 항목·est 값들이 들어 있다. 스키마에서 컬럼과
  테이블이 사라진다.
- **선택지**:
  1. **마이그레이션** — est·예산·가용량 컬럼만 제거하고 세션·항목 기록은 보존.
     `duration_sec` 가 이미 있어 과거 주도 시간 표시가 소급 적용된다.
  2. DB 초기화 — 스키마를 새로 짜고 기존 `app.db` 는 버린다. 마이그레이션 비용 0,
     기록 전부 유실. 1인용이라 가능은 하다.
- **결정**: **1. 마이그레이션.**
- **이유**: (객관식 답변으로 결정 — 추천안 수용)
- **파생**: → 구현 계획의 마이그레이션 태스크 (drop column ×2 · drop table ×1 ·
  settings 키 삭제)

### Q6. 버저닝

- **배경**: 사용자가 버저닝 추천을 요청했다.

  > "그리고 버저닝을추천해줘 이정도면 꽤 큰 변경사항이라서 말이지"

- **선택지**:
  1. **2.0.0** — 도메인 통화 교체 + 테이블 삭제 + 기존 화면 의미 변경. 파괴적 변경.
  2. 1.2.0 — 마이너로 처리. 스키마 파괴·화면 의미 변경을 마이너에 싣게 돼 부적절.
- **결정**: **2.0.0.** (AI 추천을 사용자가 수용)
- **이유**: 도메인 모델(통화)이 바뀌고 DB 스키마가 파괴적으로 변하며, 같은 화면이
  다른 것을 말하게 된다. 현재 main 은 1.1.0(월 레이어 포함).
- **파생**: → PRODUCT.md 가 1.x 로 약속했던 반응형 셸·트레이는 2.x 이후로 재배치

## 특기 사항 — AI 의 정정·지적

1. **"저장이 안 된다"는 인지를 정정했다.** 초기 문제 제기는 "바꿔도 껐다 켜면
   되돌아간다"였으나, DB 조회로 저장 자체는 정상이고 `weeks` 스냅샷의 효력 지연이
   원인임을 확인했다. 문제를 "버그 수정"이 아니라 "설계가 사용자에게 거짓말로 읽히는
   기획 문제"로 재정의한 것이 이 세션의 출발점이다.
2. **트레이드오프를 명시하고 넘어갔다.** 예상 뽀모가 죽으면 "이번 주에 얼마만큼"에
   답하는 층이 없어지고, 과적을 계획 시점에 알 방법이 사라진다. AI 가 이를 리스크로
   지적했고 사용자가 그대로 진행을 선택했다 — **알고 버린 것**이다.
3. **AI 오판 없음.** 이 세션에서 철회된 주장이나 잘못된 사실 확인은 없었다.

## 미결 — 의도적으로 미룬 것

1. **과적을 대신할 신호.** 계획 시점의 과적 경고가 사라진 자리에 다른 신호(예: 지난
   몇 주의 측정 시간 평균 대비 이번 주 항목 수)를 둘지는 정하지 않았다. 일단 없이
   써 보고 필요하면 그때 결정한다.
2. **첫 실행 온보딩.** 편집 경로 2개 중 나머지 하나였던 온보딩은 이번 변경과 독립이라
   건드리지 않는다. 다만 온보딩에서 물을 값이 가용량 없이 길이 3종만으로 줄었다.
3. **시간 예산의 재도입.** "주 20시간" 류 시간 단위 예산은 Q1 에서 기각했지만, 측정
   시간이 쌓인 뒤 기준선으로 다시 논의할 수는 있다. 지금은 만들지 않는다.

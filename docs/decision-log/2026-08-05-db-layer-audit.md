## 진행 방식

심사를 **두 축으로 나눠** 격리된 세션 둘에 맡겼다. 두 문제는 틀리는 방식이 다르기
때문이다 — 스키마는 "이 제약이 실제로 거부하나" 같은 국소적·검증 가능한 문제고,
구조는 "정산 로직이 어느 파일에 사는가" 같은 전역적 문제다. 한 세션에 둘 다 맡기면
둘 다 얕아진다.

두 심사 모두 (a) 발견마다 스스로 반박을 시도해 살아남은 것만 보고 (b) 실증한 것과
추론한 것을 구분 (c) 저장소 파일 수정 금지로 제약했다.

**두 심사가 서로를 모른 채 같은 세 건을 짚었다** — WAL 백업 결함 · Windows 경로 버그 ·
백업 무한 축적. 독립 수렴은 해석 문제가 아니라는 신호로 취급했다.

그리고 결정에 직결되는 주장 넷은 **오케스트레이터가 직접 재현**했다. 심사 결과를 그대로
믿지 않는다는 원칙이며, 실제로 재현 과정에서 심사가 놓친 사실 하나
(`foreign_keys` 기본값)와 심사 자신의 테스트 버그 하나를 잡았다.

# 1부 — 재현으로 확정한 사실

아래 넷은 주장이 아니라 실행 결과다. 환경: better-sqlite3 13.0.3 / SQLite 3.53.4 / Node 22.21.1.

## F1. 달력 키 CHECK 4종이 fail-open

계획된 `CHECK (strftime('%w', week) = '1')` 에 값을 직접 넣은 결과 **7개 중 5개가 잘못
통과**했다: `'garbage'` · `''` · `'2026-8-3'` · `'2026-02-30'` · `'2026-08-03T09:00:00Z'`.

원인은 SQLite 의 두 성질이 겹친 것이다 — `strftime()` 은 파싱 실패 시 NULL 을 반환하고,
CHECK 은 결과가 **FALSE 일 때만** 거부한다(NULL 은 통과). 따라서 이 제약은 "월요일인
날짜"가 아니라 "월요일이거나 아예 날짜가 아닌 값"을 허용한다.

> **사고 추적용 메모**: 집계가 조용히 0건이 나오는 버그를 만나면 여기를 의심하라.
> 집계 술어는 `sessions.local_week = week_items.week` 문자열 동등 비교이므로
> 한쪽이 `'2026-8-3'` 이면 조인이 소리 없이 비고, 그 뽀모는 "계획에 없던 집중"으로
> 흘러가 총합 등식은 여전히 닫힌다. **에러가 나지 않는다.**

## F2. WAL 환경에서 `copyFileSync` 백업은 열리지도 않는다

계획된 PRAGMA 세트로 200행 커밋 후 복사한 결과:

```
원본 행수 200 | app.db 4,096 바이트(헤더뿐) | app.db-wal 12,392 바이트(데이터 전부)
백업 열기 → no such table: t
체크포인트 후 재복사 → 200행 회복
```

문제는 복사 방식이 아니라 **복사 시점에 데이터가 그 파일에 없다**는 것이다.

## F3. `task_pulls` 가 요구된 상태 하나를 표현할 수 없다

today-tasks R13 이 요구하는 상태는 셋(행 없음 / 표시 중 / **치웠지만 이력엔 남음**)인데
컬럼은 `(task_id, pull_date)` 둘뿐이고 그 둘이 PK 다. 우회 경로(행을 지우고 세션에서
유도)는 calendar-records R18 의 "출처 구분 표시" 요구 때문에 막힌다 — 가져온 조각이
"사후 캡처로 생긴 항목"으로 잘못 분류된다.

## F4. ADR-011 §7 의 근거 문장이 낡았다

`foreign_keys` 기본값이 13.0.3 에서 **1** 이다. ADR-011 §7 은 "better-sqlite3 기본 OFF"
를 근거로 명시 pragma 를 요구했다. **결정은 유지하되**(버전 의존을 없애려고) 근거만
갱신 대상이다. 이건 두 심사 중 한쪽만 발견했고 재현으로 확정했다.

# 2부 — 사용자 결정 4건

착수를 막는 것만 골라 하나씩 결정했다. 넷 다 **되돌리려면 사용자 실데이터 위에서 테이블을
재작성해야 하는** 종류다(ADR-011 §6 이 "제약은 초기 마이그레이션에 전부"라 정한 이유와 같다).

## D1. 온보딩을 건너뛴 사용자의 첫 뽀모 — `capacity`·`budget` 만 nullable

- **배경**: 문서 셋이 겹치면 막힌다. R8(미설정은 NULL, `[0,…]` 초기화 **금지**) ·
  ADR-013 §2(첫 세션에 `weeks` 행 생성하며 `capacity`·`budget` 함께 박제) ·
  계획서 DDL(두 컬럼 NOT NULL). app-shell R31 이 온보딩을 건너뛸 수 있다고 했으므로
  capacity NULL 은 정상 경로다. 그 사용자의 첫 뽀모에서 **넣을 값이 없다.**
  `[0,…]` 을 넣으면 R8 이 금지한 구분 불가 상태가 불변 스냅샷에 영구 박제되고,
  INSERT 를 포기하면 timer 목표 1("계획이 0개여도 완전히 동작한다")이 첫 화면에서 실패한다.
- **선택지**
  - A **`capacity`·`budget` 만 nullable, 길이 3종은 NOT NULL 유지** — `weeks` 행이 담는
    두 스냅샷의 성격이 다르다는 관찰에 근거. 길이 기준은 전역 기본값이 있어 항상 값이
    있고, 계획 의사는 없을 수 있다. ADR-013 이 막으려던 것은 **길이 기준의 소급 왜곡**
    이므로 목적이 유지된다. R17·FK 도 그대로 성립. 대가는 R11 계약 판별 조건 한 줄 확장.
  - B `weeks` 행 생성 시점을 "capacity 가 정해진 뒤"로 미룬다 — 스키마 무변경. 대신
    세션 있는 주에 행이 없을 수 있어 R17 폐기, FK 불가, 그리고 **"과거 주가 최신
    전역값으로 해석되는" ADR-013 이 죽인 버그가 되살아난다.**
- **결정: A.** ([ADR-018](../architecture/decisions/adr-018-first-run-state.md) §1·§2·§3)
- **이유**: B 는 스키마를 안 건드리는 대신 **지난달에 명시적으로 죽인 버그를 되살린다.**
  A 의 대가인 R11 수정은 계약 표현을 실제 데이터에 맞추는 쪽에 가깝다 — 반환값 집합은
  불변이고(개수 또는 "기록 없음") 판별 조건만 넓어진다.
- **남는 것**: 예산 기록이 없는 과거 주가 존재하게 된다. 그 주의 표시는 "기록 없음"이고
  주간 게이지의 분모가 없다. 사용자가 계획한 적 없으므로 사실에 부합한다.

## D2. "남은 몫" 정의 충돌 — 수량과 정책을 분리

- **배경**: weekly-review R14 는 `최소 1`, week-plan R9 는 `max(0, …)`. **같은 입력
  (est 3·소진 5)에 인수 기준이 각각 1 과 0 으로 정면 충돌**한다. 정산이 이월 시 새 항목의
  `est_pomos` 에 남은 몫을 그대로 넣으므로, 0 이 가능하면 D4 의 `est_pomos >= 1` CHECK 이
  **정상 정산을 죽인다.** 즉 CHECK 을 쓰기 전에 닫아야 했다.
- **결정적 관찰**: week-plan 자신이 "이월 시 새 항목의 est 를 무엇으로 둘지는
  **weekly-review 가 결정한다**"고 적어 놓고 바로 앞 줄에서 공식을 썼다. 두 값이
  하나의 이름을 공유하고 있었던 것이다.
- **선택지**
  - A 이름을 나눈다 (정산의 "남은 몫" / 계획 화면의 "잔여") — 두 문서 다 자기 값 유지.
    대가는 CONTEXT.md 에 새 용어 등재, 그리고 **비슷한 두 단어가 생겨 이번 사고의 원인을
    반복한다.**
  - B `max(1, …)` 로 통일 — 수정 최소. 대가는 est 3·소진 5 인 항목의 계획 화면에
    "남은 몫 1" 이 뜬다. **산술적으로 틀린 값을 사용자에게 보여주는 것**이고 원칙 6
    (판단하지 않고 사실만 표시)과 어긋난다.
  - C **수량과 정책을 분리** — 남은 몫 = `max(0, est − 소진)` 하나로 정의하고, 하한 1 은
    이월 규칙(`이월 est = max(1, 남은 몫)`)으로 옮긴다. 용어 하나 유지, week-plan A12 참,
    하한이 "이월할 때 적용되는 정책"이라는 사실이 드러난다.
- **결정: C.** ([ADR-019](../architecture/decisions/adr-019-constraint-implementation.md) §1)
- **이유**: 하한 1 은 수량의 성질이 아니라 **이월의 정책**이다. 정책을 수량 정의에 섞은
  것이 이번 모순의 원인이었다. 같은 계열의 판단을 이 프로젝트가 이미 한 적 있다 —
  예산을 `budget NULL` 파생에서 확정 저장으로 바꾼 ADR-013 §1.
- **파생 (논의 중 안 짚었던 것)**: R15 의 축소 기본값이 `1 … 남은 몫` 클램프인데
  남은 몫이 0 이면 **`1..0` 빈 구간**이 된다. 기준을 이월 est 로 옮겼다 —
  `ceil(이월 est / 2)`, `1 … 이월 est`. 영향 범위는 technical-spec **네 곳**(213·224·314·386).

## D3. `task_pulls` 에 세 컬럼 추가

- **배경**: F3. 그리고 R14("재-pull 결과는 원래 행과 구분되지 않는다")와
  R4(2차 정렬 키 = pull 행 생성 순서)를 함께 보면, **행을 지우고 다시 넣는 방식은
  정렬 위치가 바뀌어 R14 를 어긴다.** R14 는 괄호로 "행이 다시 생기든 관측 가능한
  차이가 없다"고 적었으나 정렬을 감안하면 엄밀히 사실이 아니다.
- **결정: 세 컬럼 다.** ([ADR-019](../architecture/decisions/adr-019-constraint-implementation.md) §5)
  - `removed_at` — R13 의 치움 상태. 사실상 강제(우회 불가)
  - `created_at` — R4 정렬 키. 없으면 암묵적 `rowid` 에 의존
  - `updated_at` — `removed_at` 이 생기면 이 테이블은 append-only 가 아니게 되므로
    ADR-006 §2 의 mutable 테이블 규칙이 그대로 적용된다
- **이유**: 셋 다 서로 다른 문서의 요구를 받고 있어, 하나라도 빼면 그 요구가 코드 규율로
  내려간다.

## D4. 제약 강화안 전체 승인

- **배경**: F1 + 기능 문서가 **명시적으로 스키마에 위임한** 제약 2건이 없음
  (week-plan R9 "이 예외를 컬럼 제약으로 어떻게 표현하는지는 ADR-011 §6 소관" /
  pomo-baseline R5 "거부는 경계에서 — IPC 스키마 + SQLite CHECK"). 현재 스키마에
  `est_pomos = -3` · `focus_min = 0` · `is_system = 7` 이 전부 들어간다.
- **가장 위험했던 것**: `is_system = 7` 은 `= 0` 술어에도 `= 1` 술어에도 안 걸려
  **ADR-012 §4 의 차액 정의에서 양쪽 어디에서도 세어지지 않는다.** "이중 계상도 누락도
  산술적으로 불가능"이라던 성질이 깨진다.
- **결정: 전체 승인.** ([ADR-019](../architecture/decisions/adr-019-constraint-implementation.md) §2·§3·§4·§7)
  달력 키 NULL-safe 재작성 · 순간 형식과 순서 · 값 범위 · 누락 FK
  (`sessions.local_week → weeks.week`) · 부분 UNIQUE 인덱스(기타 항목 유일성).
- **검증**: 결정 D1~D3 이 반영된 제약 전체를 만들고 **31개 케이스로 확인, 전부 의도대로**
  판정했다. 스크립트는 [2026-08-05-constraints-probe.mjs](./2026-08-05-constraints-probe.mjs).
- **성격**: 새 결정이 아니라 ADR-011 §6 의 **실행분**이다. 그래서 ADR-019 의 제목이
  "제약 실행분 확정"이다.

> **네 결정은 서로 맞물린다.** D2 가 없으면 D4 의 `est_pomos >= 1` 이 정상 정산을 죽이고,
> D1 이 없으면 `capacity` NOT NULL 이 첫 뽀모를 막는다. 순서를 바꿔 결정했다면 다른
> 결론이 나왔을 수 있다.

# 3부 — 오케스트레이터 권고와 사용자 수락

4건 결정 후, ADR 초안에 **결정 범위 밖의 판단**이 들어간 것을 스스로 표시해 검토받았다.
사용자 판정: *"너의 권고대로 가되 이 권고가 나오기까지 의사결정들을 의사결정 폴더에 담아서
기록해줘"*.

## R1. 시딩 목록을 ADR-018 에 신설 — 유지

- **배경**: R6 은 "기본값 25/5/15 가 `settings` 에 저장된다"고 하고 R8 은
  "`weekly_capacity` 는 넣지 말라"고 하는데, **누가 언제 쓰는지가 없었다.**
  technical-spec:427 이 `readSetting('focus_min')` 을 폴백 없이 `weeks` 에 박제하므로,
  키가 없으면 `undefined` 가 불변 스냅샷에 박힌다.
- **결정**: 세 부류로 확정 — 정적 시딩(길이 3종 · `plan_lead_days` 1 · `theme` `'system'`) /
  계산 부트스트랩(`last_settled_week`, weekly-review §0.2 소관) / 시딩 안 함(`weekly_capacity`).
  규칙 셋: 멱등(키 없을 때만) · 마이그레이션 직후·창 생성 이전 · 목록 밖 키는 시딩 안 함.
- **값의 출처**: 전부 기존 문서. `plan_lead_days` 1 은 ADR-010 §3, `theme` `'system'` 은
  design-system ADR-008(실재 확인).
- **기각한 대안**: 시딩하지 않고 읽는 쪽에서 코드 기본값 사용 → R6 이 거짓이 되고,
  `weeks` 스냅샷에서 **"코드 기본값"과 "사용자가 정한 값"이 구분되지 않는다.**

## R2. `settings.value` 는 NOT NULL 유지, "키 부재"만 미설정 — 유지

- **배경**: R8 이 미설정을 "키 부재 **또는 NULL**"이라 했는데 DDL 은 `value NOT NULL`.
  둘 중 하나가 틀렸다.
- **이유**: 두 표현을 다 허용하면 **같은 뜻의 상태가 둘**이 되고, 판정 코드가 두 조건을
  검사해야 한다. 하나만 검사하면 조용히 틀린다 — R8 이 걱정한 "미설정 분기를 쓰는 화면이
  잘못된 쪽을 고른다"가 오히려 늘어난다. "값을 지운다"는 행 삭제로 자연히 표현된다.
- **기각한 대안**: nullable 로 두면 "설정했다가 지웠다"와 "한 번도 없다"를 구분할 수
  있으나, **이 앱에 그 구분이 필요한 자리를 찾지 못했다.**
- **딸려오는 것**: R8 문구에서 "또는 NULL" 삭제 필요.

## R3. 인덱스 — 절충 (정의 다듬기만 지금, 신설은 미룸)

- **배경**: 실측에서 전체 스캔 2건 + 임시 정렬 2건. 초안에서는 4건 전부를 지금 하기로
  썼는데, 이는 심사 보고서에서 인덱스를 "나중에도 공짜"로 분류한 것과 어긋났다.
- **결정 기준**: **비용이 0 인 것만 지금.** 어차피 초기 마이그레이션에서 만들 인덱스의
  정의를 바꾸는 것은 공짜, 없던 인덱스 신설은 나중에 `CREATE INDEX` 한 줄.
- **지금**: `week_items(week)` → `(week, created_at)` · `sessions(task_id)` → 부분 인덱스
- **미룸**: `milestones(month, sort_order)` · `week_items(milestone_id)` 신설
  → [알고도 미룬 것](#알고도-미룬-것--사고-시-여기부터-본다) 참조

## R4. `settings.updated_at` + 전 테이블 `$onUpdate` — 유지

- **배경**: ADR-006 §2 가 mutable 테이블로 넷을 지목했는데 `settings` 것만 누락됐고,
  ADR-006 이 지정한 자동 갱신 수단(`$onUpdate`)이 어느 컬럼에도 안 걸려 있다.
- **이유**: ADR-006 자신의 문장이 근거다 — "컬럼 추가 자체는 나중에도 쉽지만 **과거
  데이터의 갱신 시각은 영영 복원 불가**하므로 지금 넣는다." `NOT NULL` 로 나중에
  추가하려면 기존 행의 값을 지어내야 한다. `$onUpdate` 는 없으면 모든 UPDATE 경로가
  손으로 넣어야 하고 **누락을 컴파일러가 못 잡는다.**

## R5. 백업 정책 — 자동 복원 안 함 + "백업 폴더 열기" 버튼

- **배경**: 백업을 뜬 직후 `migrate()` 가 실패하면 뭘 할 것인가가 미정이었다.
- **이유(자동 복원 안 함)**: Drizzle 이 각 마이그레이션을 트랜잭션으로 감싸므로 실패 시
  DB 는 대개 **이전 세대 상태로 온전하다.** 백업으로 덮으면 오히려 멀쩡한 파일을 과거로
  되돌린다. 손상의 경우도 범위를 앱이 판단할 수 없는데 파일 전체를 갈아치우는 건 과하다.
- **보완**: 경로 문자열만 보여주면 데스크톱 사용자는 무엇을 할지 모른다. 안내 창에
  **"백업 폴더 열기"** 버튼(`shell.showItemInFolder`)을 둔다 — 결정권은 넘기되 도달
  비용은 낮춘다. 이 때문에 안내는 `showErrorBox` 가 아니라 `showMessageBox` 다.
- **보존 5개**: 근거가 약한 임의값임을 인정한다. 마이그레이션이 있을 때만 만들어지므로
  5개면 최근 5세대를 덮고, 개당 DB 전체 크기(5년치 약 7MB)라 35MB 수준이다.

# 알고도 미룬 것 — 사고 시 여기부터 본다

**전부 심사에서 발견됐고, 고칠 방법도 알고 있으며, 의도적으로 미룬 것들이다.**
관련 증상이 나타나면 여기에 이미 답이 있다.

# 확신도가 낮은 결정

**여기서 비롯된 문제라면 결정을 바꾸는 것이 정답일 수 있다.**

| 결정 | 확신도 | 약한 지점 |
|---|---|---|
| 백업 보존 **5개** (ADR-020 §3) | **낮음** | 근거가 약한 임의값. 3이면 더 가볍고 10이면 더 안전 |
| 자동 복원 안 함 (ADR-020 §4) | 중간 | 방향은 맞다고 보나 **UX 가 불친절할 수 있다.** "백업 폴더 열기" 버튼으로 보완했으나 실사용 검증 안 됨 |
| 축소 기본값 기준 이동 (ADR-019 §1) | 중간~높음 | 논리는 필연이나 **UI 문구가 어색할 수 있다** — "남은 몫 0" 인 항목의 축소 기본값이 1 로 뜬다. ux-spec 확인 필요 |
| `integrity_check` 를 시작 경로에 (ADR-020 §4) | 중간 | DB 가 커지면 시작이 느려진다. 현재 규모(7MB)에서는 무시 가능 |

# 이 심사가 뒤집지 않은 것

혼동 방지를 위해 명시한다. 아래는 **검토했고 유효하다고 확인된** 것들이다.

- ADR-011 §6("제약은 초기 마이그레이션에 전부") — 판단 자체가 옳다. 누락된 것은 실행분이었다
- ADR-012 §4 차액 정의 — `is_system` 오염이 있어도 총합 등식은 깨지지 않음을 실증
- ADR-013 §2·§3·§4 — 행 생성 시점, 편집·효력 분리, 총 집중 시간 표시 전부 유효
- ADR-013 §1 은 **부분 정정** — `budget` NOT NULL 부분만 D1 이 바꿨고, "확정 저장" 원칙은 유효
- 불변 달력 키 설계 — 실측에서 모든 날짜 조회가 인덱스를 탐
- ADR-015 포트 + UoW — 구조는 건전. 타입 차단(P3)만 실행분 누락
- ADR-007 IPC 계약 — 응답까지 검증하는 설계가 "흔히 빠뜨리는 방향"으로 평가됨

# 정정된 선행 ADR

결정이 아니라 **근거가 틀렸거나 낡은** 경우다. 본문은 이력으로 두고 상태 줄에만 표기한다.

## A. 계획서 가져오기 — 방향

### Q1. 계획 입력을 어떻게 덜 번거롭게 하나

- 배경: 한 주를 계획하려면 Milestone 추가, Sprint 제목·요일, 드로어 task, Milestone 연결을
  하나씩 눌러야 한다. 클릭이 수십 번이다.
- 사용자 제안: "dongmodoro skills가 있고 해당 스킬를 사용해서 에이전틱 코딩으로 하면 포맷에
  맞게 커리큘럼이나 계획 작성해주고 그걸 input으로 넣으면 알아서 계획 설정하게 하면
  좋을꺼같은데 어떻게 생각함?"
- 선택지:
  - 스킬이 SQLite 에 직접 쓴다 — 켜진 앱의 캐시가 어긋나고, 이월·워터마크 규칙이 있는
    서비스 계층을 건너뛴다. "경계는 zod IPC 만" 원칙도 깨진다. **기각**
  - ● 스킬은 형식이 정해진 텍스트(계획서)까지만 만들고, 앱이 붙여넣기 → 검사 → 미리보기 →
    한 트랜잭션 등록을 한다 — 형식이 계약이 되어 Claude·Codex·일반 챗봇 어디서 써도 같다
  - 로컬 MCP 서버로 에이전트가 앱을 조작 — 지금은 과하다. 같은 형식 위에 나중에 얹을 수 있다. **보류**
- **결정: 형식 계약 + 앱의 가져오기.** 스킬은 Claude Code·Codex 가 함께 쓰는 한 폴더.
- 이유: "skills: cluade나 codex 다른 agent가 사용 할 수 잇게 만들꺼임 해당 스킬은 이제 계획서를
  dongmodoro 포맷에 맞게 작성해주는 스킬임 dongmodoro에는 input이 있고 그 input에 해당 스킬로
  작성한 output(계획서)를 넣으면 계획서를 알아서 등록해줌"
- 파생: → Q2 (입력 뷰), → Q3 (형식)

### Q2. 입력 뷰를 어디에 띄우나 (미결 — 3안 제시까지)

- 경과: AI 가 먼저 에이전트 → 계획서 → 앱까지의 **흐름** 와이어프레임을 그렸다. 사용자
  정정: "내가 원한건 흐름 와이어프레임이 아니라, input 넣는 뷰에 대한 와이어프레임이었어
  확인해볼래?" → 입력 뷰만 3안 × 상태 4개(비어 있음 / 붙여넣음 / 형식 오류 / 이미 Sprint 가
  있는 주)로 다시 그렸다.
- 선택지:
  - ● (AI 추천) C 계획 컬럼을 덮는 비모달 시트 — MONTH 오버레이와 같은 문법, 타이머를 막지 않는다
  - B 가운데 모달, 좌우 분할 — 가장 넓지만 타이머를 막는다 (PRD R10)
  - A WEEK 카드 안의 모드 — 새 표면이 없지만 360px 라 확인 화면으로 좁다
- 검증 후 보정: 화면 에이전트가 480px 시트가 창 최소 폭(720px)에서 타이머 왼쪽 약 96px 을
  덮는다는 것을 찾았다 → 360px 로 줄여야 한다.
- **결정: 아직 없음.** 사용자가 고르지 않았다. → 미결

### Q3. 계획서 형식 — YAML 인가 txt 인가

- 배경: AI 가 YAML 을 기본값처럼 골랐다. 사용자가 이유를 물었다: "yaml로 할꺼야?
  일반사람들은 txt가 익숙할껀데 그렇게 한이유가있어? 바꾸라는소리는아님"
- 전제: 앱에 AI 가 없으므로 어떤 형식이든 규칙대로 읽혀야 한다. 자유 txt 는 앱이 Sprint 와
  task 를 확실히 구분할 수 없다.
- 선택지:
  - ● YAML — 에이전트가 틀리지 않고 쓰고, JSON 보다 읽기 쉽고, zod 로 줄 단위 오류를 낸다.
    약점은 들여쓰기 민감·값 오해석(날짜, `no`)·낯선 확장자
  - Markdown 식 자체 문법 — 메모처럼 보여 손으로 고치기 쉽지만, 파서와 오류 메시지를 직접 만들어야 한다
  - JSON — 따옴표·괄호가 많아 사람이 훑기 어렵다
- 갈림길: "사람이 손으로 자주 고치는가". 틀리면 오류를 복사해 에이전트에게 돌려주는
  흐름이라 사람이 고칠 일이 적다.
- **결정: YAML.** 모든 값을 문자열로만 읽어 오해석을 막고, 확장자가 아니라 내용을 읽어 `.txt` 도 받는다.
- 이유: "음 yaml이 맞을꺼같다 어차피 AI가 작성해주니깐 ㅇㅇ"

### 이벤트 — 공존 평가 (서브에이전트 3개)

"에이전트 켜서 현재 이 플로우 추가되더라도 기존의 동작들 정상동작되며, 자연스럽게
녹여지는지 평가해줘" 에 따라 데이터·서비스 / 화면·UX / 도메인·원칙 세 관점으로 읽기 전용
평가를 돌렸다. 설계 그대로면 막히는 곳 4건:

1. 계획 단계 task 생성이 week-plan R12 "task 목록은 계획서가 아니라 누적 기록" 과 정면 충돌 → Q4
2. AI 가 쓴 예시 계획서의 Milestone 연결이 서비스에서 거부된다 — 9/28 주는 9월 주라 10월
   Milestone 에 새로 연결할 수 없다 (R14, `week-plan.ts:244`) → Q5
3. 대상 주 제한(이번 주·다음 주)이 화면에만 있고 서비스에 없다 — 지난 주로 가져오면 정산이
   영원히 못 보는 Sprint 가 생긴다
4. 480px 시트가 타이머를 가린다 → Q2 보정

그 밖에 트랜잭션 중첩 불가(`drizzle.ts:1016`) → 저장소를 한 `uow.run` 안에서 조합하는 새 서비스
필요, 새 무효화 사건 `plan-imported`, 오른쪽 오버레이 한 장 소유, 전역 ⌘V 금지 등.

### Q4. task 를 계획서로 미리 넣어도 되나

- 배경: R12 는 task 를 "해 온 일의 누적 기록"으로 정의한다. 첫 pull 이 첫 task 를 만든다.
- 선택지:
  - (AI·도메인 에이전트 추천) v1 은 `tasks` 를 빼고 Sprint 만 가져온다 — 기존 정의를 지킨다. **기각**
  - ● R12 를 개정해 두 방식이 공존 — 드로어는 task 0개(첫 조각 작성)와 task 있음(다중 선택)을
    이미 다 다루므로 새 코드가 거의 없다
- **결정: 공존.** 계획서의 `tasks` 는 선택 필드. 없으면 기존처럼 드로어에서 쪼개고, 있으면
  `+ 오늘로` 한 번에 다음 task 가 순서대로 들어온다.
- 이유: "기존 정의와 충돌해도 됨, 음 내가 원하는건 기존의 방식과 현재 방식이 공존했음 좋겠다는거임"
- 파생: R12 문장과 CONTEXT.md 의 task 정의("드로어에서 만들고")를 계획서 기능 PR 에서 개정한다.

## B. Milestone 연결 규칙

### Q5. 다른 달 Milestone 에 연결할 수 있게 하나

- 배경: 주는 월요일이 속한 달에 통째로 귀속된다 (R18). 새 연결은 그 달 Milestone 만 (R14).
  예외로 이월은 원래 연결을 유지한다 (R15). 카드는 이번 주가 그 달에 귀속될 때만 숫자를
  보여주고 (R20), 아니면 `이번 주(8/31~9/6)는 8월에 속한 주예요` 문구를 띄운다 (R23).
  달이 바뀌는 주(9/28–10/4)에 10월 목표를 걸 수 없다.
- 사용자 요청: "그거에 대해서 자세하게 가능한지 여부를 일단 생각해볼까?"
- 재설명 경과: "좀더 쉽게 설명해볼래? 지금 이해가안감" → "나에 대해서 좀더 자세하게
  설명해볼래?" → "흠 규칙이 너무 복잡하다 규칙이 어떻게 되는지 확인해볼래?" → "흠 규칙에 대해서
  수정하게되면 어떻게 되는지 html 아티펙트로 만들어볼래?" (상황 4개 × 규칙 2개를 비교하는
  인터랙티브 아티팩트로 답했다)
- 선택지:
  - (가) 지금 규칙 유지 — 코드 변경 0. 스킬이 "주의 귀속 달"을 알고 쓰면 된다. 경계 주에 그 달 목표를 못 다는 게 어색하다
  - (나) 경계 주만 두 달 허용 — AI 의 첫 추천. 규칙 6개 위에 예외를 하나 더 얹는다. **기각** (사용자가 복잡하다고 짚음)
  - ● 단순화 — 연결 규칙에서 "귀속 달"을 뺀다. 규칙 6개 → 3개:
    1. Milestone 은 한 달에 속한다
    2. Sprint 는 어느 달 Milestone 에나 연결할 수 있다
    3. Milestone 카드는 그 Milestone 에 연결된 **이번 주** Sprint 의 시간을 보여준다
    R18 은 정산·주간 합계·캘린더를 위해 남는다.
- **결정: 단순화.**
- 이유: "음 규칙 바꾸는게 더 낫겠다 좀더 쉽게 가는게 맞음"
- 파생: 이월 예외(R15 의 "유일한 경로")와 R23 문구가 사라진다. 기존 버그(아래 이벤트)가 같은
  수정으로 해결된다. → Q6

### 이벤트 — 규칙 변경 검증 (서브에이전트 2개)

"하기전에 일단 agent띄워서 수정 가능한지, 예상가능한 버그는 없는지 확인해보자" 에 따라:

- **기존 버그 재현.** 8월 Milestone 에 연결된 Sprint 를 9/7 주로 이월하고 9/8 에 25분 집중 →
  저장소 `rollup('2026-08','2026-09-07')` 은 1500초를 세지만 8월 카드 `rollupWeek: null`,
  9월 카드 항목 없음. A13("그 Milestone 이 놓인 달 카드에 나타난다")이 지켜지지 않고 있었다.
  원인은 `milestones.ts:89` 의 `monthOfWeek(weekKey) === month` 게이트. 저장소 테스트만 있어 안 잡혔다.
- **구현 가능.** 저장소 `rollup` 은 이미 어떤 주든 받는다. 변경은 후보 쿼리 1개, 서비스 게이트
  2곳, 무효화 대상 달, 드로어 달 묶음, 카드 문구 삭제, 문서.
- **새 규칙의 예상 버그 3건**: 자정 달 전환 시 드로어 후보가 낡음(서버 거부가 조용함) / 연결
  변경 시 한 달 카드만 새로고침 / 드로어 후보에 달 표시 없음.
- **기존 버그 추가 발견**: 보내주기·계획 확정이 월 카드를 무효화하지 않음, `setMilestone` 에
  `onError` 없음, 롤업 라벨에 범위 없음, 드로어가 열린 채 Milestone 삭제 시 낡은 목록.

### Q6. 지난 달 Milestone 에 새로 연결하는 것을 막나

- 배경: 단순화 규칙 2를 처음에는 "지난 달 Milestone 에 새로 연결하는 것만 안 된다"로 적었다.
  그러면 10/2 에 9/28 주 Sprint 를 9월 Milestone 에 못 걸고, 자정 달 전환 버그도 따로 막아야 한다.
- 선택지:
  - (가) 막는다 — "지난 달은 읽기 전용"에 문자 그대로 맞는다. 규칙과 버그가 하나씩 늘어난다
  - ● (나) 막지 않는다 — 연결은 Milestone 자체를 고치는 게 아니므로 읽기 전용과 부딪히지 않는다.
    자정 달 전환 버그가 사라진다
- **결정: (나) 막지 않는다.** 규칙 2는 "Sprint 는 어느 Milestone 에나 연결할 수 있다". 드로어
  후보는 이번 달 → 다음 달 → 그 뒤 → 지난 달 순, 달별로 묶는다.
- 이유: "1번 나로해야함"

## 특기 사항 (AI 의 오판·정정)

1. **캘린더 점 오진.** 디자인 점검에서 "DB 에 기록이 없는데 24일에 점이 생겼다"를 버그 후보로
   보고했다. pull 도 `기록 있음` 의 항이라 점은 맞았다. 진짜 버그는 드로어 pull 이 캘린더를
   무효화하지 않아 점이 **늦게** 뜨는 것이었다 (PR #98 에서 수정).
2. **와이어프레임 범위 오해.** 입력 뷰를 원했는데 전체 흐름을 그렸다 (Q2).
3. **자기 예시가 규칙 위반.** AI 가 쓴 예시 계획서가 R14 를 어겼다 (9/28 주 → 10월 Milestone).
   공존 평가 에이전트가 잡았다.
4. **480px 시트.** AI 가 추천한 C안 폭이 타이머 가림 규칙을 어겼다. 화면 평가 에이전트가 잡았다.
5. **(다)안 성급한 기각.** 처음에 "어느 달이든 허용"을 "월 경계가 사라진다"며 비추천했다.
   집계가 Milestone 기준이라 경계가 섞이지 않는다는 점을 놓쳤다. 사용자가 "규칙이 너무 복잡하다"고
   짚은 뒤 정정하고 추천을 바꿨다.
6. **(나)안이 복잡도를 늘림.** 첫 추천이 예외를 하나 더 얹는 안이었다 (Q5).
7. **설명 과부하.** Q5 에서 사용자가 쉬운 설명을 세 번 요청했다. 규칙 이름(R14·R18)과 코드 위치를
   앞세운 설명이 원인이었다.

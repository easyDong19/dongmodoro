이 문서가 다루는 것: dongmodoro(1인용 뽀모도로 Electron 앱)의 구현된 화면이 와이어프레임과 다르다는 문제 제기에서 시작해, 원인을 진단하고 다크·라이트 테마 전환을 어떻게 만들지 결정한 기록이다. 각 카드는 문제(무엇이 비어 있거나 모순이었나) → 고민(어떤 선택지와 트레이드오프가 있었나) → 결정(무엇을 골랐고 왜) 순서로 읽으면 된다. ● 표시가 최종 선택이다.
반전 AI 추천을 기각했거나 선택을 번복한 지점 재설명 결정 전에 상세 설명·분석을 요구한 지점 검증 코드 실행·타입 정의 확인으로 사실을 확인한 지점 점선 카드 = 질문이 아닌 이벤트

1 · 진단 — 왜 시안과 다른가

결정을 시작하기 전에, "디자인이 완전히 다르다"는 문제 제기의 실제 원인을 코드로 확인했다.

START

와이어프레임 대 구현 코드 전수 대조 검증

확인한 것

색·폰트·radius·유리 표면 토큰은 시안과 정확히 일치했다. 렌더러의 raw hex·rgb 사용은 0건이고 색은 전부 토큰 매핑 유틸이었다. 어긋난 것은 형태였다 — 3컬럼 그리드 대신 flex 3장, 타이틀바 없음, MONTH 컬럼(마일스톤·캘린더) 통째로 없음, 카드 내부 스크롤 영역 없음.

원인 3
  • ① app-shell 기능 미구현 — M1~M3b 계획 어디에도 태스크가 없고, M2 계획서가 명시적으로 제외했다
  • ② 테마 토글은 배선이 끊긴 게 아니라 처음부터 없다 — data-theme 설정 코드 0건, theme IPC 0건, Tray 0건
  • ③ 컴포넌트 시각 어휘 미이식 — 시안 40여 클래스 중 global.css 에 넘어온 것은 5개
구조적 뿌리

docs/CLAUDE.md 는 토큰을 훅으로까지 강제하지만 와이어프레임에 대해서는 "명세가 아니다 · 구속력 없음" 이라고 명시한다. 그리고 각 마일스톤의 검증 기준은 전부 "동작한다"였다. 값은 강제되고 형태는 아무도 강제하지 않는 규칙이 만든 결과다.

발견

현재 코드에서 OS 가 라이트면 앱도 라이트로 뜬다. tokens.css 의 @media (prefers-color-scheme: light) 가 살아 있고 그것을 덮을 data-theme='dark' 를 아무도 붙이지 않기 때문이다. 사용자가 말한 "다크가 디폴트"와 문서(ADR-008 §4 "OS 선호를 따른다")가 이미 어긋나 있었다.

2 · 전환 경로와 범위

"토글 버튼을 어디에 놓느냐"가 이 세션에서 가장 결과가 크게 갈린 결정이었다 — 딸려오는 작업의 크기가 안마다 완전히 달랐다.

Q1

테마 토글을 어디에 놓나 반전 재설명

문제

ADR-008 §4 가 수동 전환 경로를 트레이 서브메뉴 하나로 못박았다. 그런데 app-shell PRD R25 가 "창 닫기=숨김과 트레이 상주는 분리 배포할 수 없다" 고 정해, 트레이를 만들면 창 수명주기·복귀 4경로·종료 경로가 통째로 딸려온다. 타이틀바도 없다 — window.ts 에 frame 옵션 자체가 없어 OS 기본 프레임이다.

고민한 선택지
  • A 트레이 서브메뉴 — ADR 을 안 뒤집는다. 대신 app-shell 마일스톤이 통째로 딸려온다
  • B 커스텀 프레임리스 타이틀바 — 시안의 최종 자리. 버려지는 코드 0. 프레임리스 창·플랫폼 슬롯·드래그 핸들이 딸려온다
  • C 카드 밖 임시 토글 — 딸려오는 것 0. 대신 버려질 코드이고 임시 티가 난다
경과 — 추천이 두 번 움직였다

AI 는 처음 C 를 추천했고 사용자도 "C로 가보자"로 동의했다. 그런데 사용자가 즉시 중단하고 목업을 요구했다. 그리는 과정에서 C1(떠 있는 버튼)이 오늘 목록 카드의 우상단을 덮는다는 것이 드러나 AI 추천이 C1 → C2 로 바뀌었고, 사용자는 그 그림을 보고 B 를 골랐다.

결정

각각 어디에 위치하는지 html으로 만들어줘 보고 결정하게 — 표로만 비교했으면 그대로 갔을 결정이었다

→ Q2 이 계획서가 "테마"가 아니라 "테마 + 타이틀바"가 된다
→ Q3 프레임리스면 창 컨트롤은 OS 가 그리는데 그 색은 CSS 를 안 따라온다 — main 이 테마를 알아야 한다

ux-spec 이 타이틀바에 넣기로 한 것은 넷(앱 이름 · MONTH 토글 · 날짜 라벨 · 창 컨트롤 폭 예약)이고 테마 컨트롤이 다섯 번째다. 전부 지으면 app-shell 마일스톤이 되고, 다 빼면 테마 버튼 하나 얹은 빈 바가 된다.

  • B-min 프레임리스 + 앱 이름 + 테마 — 정보가 0이라 "왜 있는지" 설명이 안 된다
  • B-mid + 날짜 라벨 — 시안 타이틀바의 실제 모습

Q3

테마 상태를 누가 소유하나 검증

문제

렌더러의 CSS 와 main 의 창 컨트롤 색이 각자 테마를 해석하면 두 벌이 되어 반드시 어긋난다. 한 곳으로 모을 장치가 필요했다.

확인한 사실

Electron 의 nativeTheme.themeSource 를 설정하면 렌더러의 prefers-color-scheme 미디어 쿼리까지 함께 움직인다. main 이 한 줄 설정하면 CSS 와 창 컨트롤이 같은 출처에서 나온다.

고민한 선택지
  • ① main nativeTheme.themeSource — 첫 페인트 깜빡임 0, tokens.css 수정 0, 해석 한 곳
  • ② renderer data-theme 속성 — IPC 왕복 후 적용이라 깜빡임이 구조적으로 발생. 해석 두 곳
  • ③ 둘 다 — 해석 세 곳. 어긋남 보장
결정

① main 소유. main/index.ts 에서 seedSettings 가 createWindow() 보다 먼저 돌므로, 그 사이에 읽어 넣으면 창이 태어나는 순간 이미 올바른 테마다.

Q3-1

[data-theme] 선택자를 어떻게 하나

문제

①을 고르면 OS 를 덮어쓰는 채널이 data-theme 이 아니라 themeSource 가 되므로, ADR-008 §1 이 명시한 선택자가 쓰이지 않는 가지가 된다.

고민한 선택지
  • (가) 남긴다 — 테스트·문서에서 브라우저만으로 라이트를 강제할 통로
  • (나) 지운다 — 죽은 코드를 안 남긴다. 대신 와이어프레임 문서와 코드 구조가 갈린다
결정

(가) 존치. "런타임은 themeSource, data-theme 은 테스트·문서 전용"을 ADR 에 못박는다 — 죽은 코드가 아니라 용도가 다른 두 번째 진입점이다.

Q4

IPC 표면을 어떻게 자르나 검증

  • (c) 범용 key-value settings: { get, set } — 값이 string 이라 theme 에 'purple' 이 들어가도 통과한다

(b). (c) 는 이 채널에서만 ADR-007 의 계약 규율을 무력화한다.

4 · system 제거 — 사용자가 전제를 뒤집은 지점

AI 는 선택지의 우열을 따지고 있었는데, 사용자는 선택지가 서 있는 전제를 없앴다.

Q5

컨트롤을 몇 택, 어떤 형태로 반전

문제

저장값은 system/light/dark 3택인데 사용자가 처음 말한 표현은 "토글 버튼"이었다. 그 둘이 어긋난다.

고민한 선택지
  • A 2택 토글 — 최소. 단, system 이 남아 있는 한 "되돌아갈 수 없는 문"이 된다
  • B 3택 세그먼트 (AI 추천) — 상태가 한눈에. 타이틀바가 붐빔
  • C 순환 버튼 1개 — 최소. 다음 상태를 예측 못 하고 목표까지 2클릭
결정 — 선택지가 아니라 전제를 바꿨다

A. 단 system 이라는 선택지 자체를 없앤다. AI 가 B 를 추천한 유일한 근거가 "system 이 있으니 2택은 되돌아갈 수 없는 문"이었는데, system 이 사라지면서 그 근거가 통째로 무력화됐다.

A로 가는게 맞지 않나, 그리고 현재 OS단에 맞게 했는데, 그냥 OS단에서 따라간다는 ADR을 수정하고 기획서도 수정하는게 어떨까 앱내에서만 수정가능하게 설정하는게 관리하기도 쉬울꺼같아서 그래

→ Q6 ADR-008 §4 를 부분 supersede 하는 새 ADR 이 필요해진다

Q6

system 제거를 확정하나

얻는 것

system 은 값이 값을 가리키는 간접 상태다 — 화면이 어두운 이유가 저장값과 OS 둘로 갈린다. 없애면 상태 공간이 3 → 2 가 되고 nativeTheme.on('updated') 구독도 불필요해진다. 그리고 tokens.css 는 여전히 수정 0 이다 — themeSource 가 명시값이면 prefers-color-scheme 도 그 값으로 강제되므로 기존 미디어 쿼리가 그대로 맞는다.

치르는 대가

macOS·Windows 둘 다 일몰 자동 다크 전환 기능이 있다. 그걸 켜 둔 사용자는 낮에 다른 앱이 전부 밝아져도 이 앱만 선택한 채로 남는다. 이 대가를 명시적으로 수용하기로 했다.

안 바뀌는 것

고대비 모드(forced-colors: active)는 여전히 OS 가 이긴다. "앱 안에서만 결정"이 그것까지 뒤집으면 접근성 회귀다.

결정

저장값 light/dark, 기본 dark. 문서 5곳(adr-008 상태 줄 · tokens.md §9 · app-shell prd R42 재작성 + A34 삭제 · ux-spec §6.5 · adr-018 시딩 표)과 코드 2곳을 같은 PR 에서 고친다.

→ 계획서 작성 단계에서 발견: 기존 개발 DB 에 "system" 이 남는다. seed.ts 가 멱등이라 값을 안 덮으므로 읽을 때 정규화 + 되쓰기 경로가 필요하다

Q7

3 OS 중 어디까지 책임지나 검증

문제

PRODUCT.md 가 대상 OS 를 셋으로 확정했고 app-shell PRD A17 이 "Win·Linux 에서 창 컨트롤과 겹치지 않는다"를 인수 기준으로 걸었다. 그런데 개발 환경이 macOS 하나다.

Electron 43 타입 정의에서 확인한 것

titleBarOverlay 의 색 옵션은 @platform win32,linux — Linux 도 지원하고 Linux 는 symbolColor 생략 시 접근성 대비를 자동 계산한다. 그리고 이걸 켜면 Window Controls Overlay CSS 환경 변수가 활성화된다.

고민한 선택지
  • (가) 3 OS 코드 + macOS 만 검증 — 검증 안 된 코드가 "됐다"로 읽힌다
  • (나) macOS 만 구현 — Win·Linux 에서 컨트롤이 타이틀바 위에 겹쳐 못 쓰는 앱이 된다
  • (다) 3 OS 코드 + macOS 검증 + 미검증을 계획서에 명시 — (가)와 코드는 같고 기록만 다르다
결정

(다). A17 은 이번에 안 닫힌다를 계획서에 못박는다.

다로 가자

부수 성과

ux-spec §1.1 의 "창 컨트롤 폭은 플랫폼별 상수로 예약한다" 가 불필요해졌다. CSS 환경 변수가 실제 폭을 런타임에 알려주므로 하드코딩한 숫자가 OS 업데이트로 어긋날 일이 없다 — ux-spec 을 개선하는 방향의 정정이다.

Q8

토글의 모양과 스타일 소유 — 진단 원인 ③과 만나다

문제

"2택 토글"에 두 해석이 있었다. ① 단일 버튼이면 아이콘이 "현재 상태"인지 "누르면 될 것"인지가 정해져야 하는데 둘 다 관용적이고 둘 다 헷갈린다. 그리고 이 버튼을 어떻게 스타일링하느냐가 진단 원인 ③과 직결된다.

고민한 선택지 (스타일 소유)
  • (가) 이 버튼만 Tailwind 유틸 + 인라인 style — 방금 원인으로 지목한 것을 그대로 재생산
  • (나) .seg 하나만 global.css 로 이식 — 첫 이식 사례. 다음 컴포넌트가 따라올 자리가 생긴다
  • (다) 컨트롤 클래스 전량 이식 — 기존 컴포넌트 전부 재작성. 별도 계획서 감
결정

② 2세그먼트 + (나) .seg 만 이식. ②는 "지금"과 "누르면"이 동시에 읽혀 모호성이 사라지고, design-system ADR-006 §3 의 "선택 상태에 보더" 규칙(고대비에서 배경이 사라짐)을 이미 만족한다.

(나)로 가자

Q9

검증을 어떻게 하나 — E2E 도입 반전

문제

지금까지 계획서의 검증 기준이 전부 "동작한다"였고 그것이 진단한 원인의 구조적 뿌리였다. 여기에 더해 ADR-008 이 라이트 테마의 대비 판정 지점을 "타이틀바"로 지정하고 그 때문에 --ink-dim 알파를 0.60 → 0.65 로 올렸는데, 타이틀바가 없어서 그 판정을 한 번도 실측한 적이 없다. 이번 작업이 그 지점을 처음 만든다.

고민한 선택지
  • (가) 단위 테스트만 — "저장된다"까지만. 화면이 뒤집히는지는 못 본다
  • (나) 단위 + 수동 체크리스트 (AI 추천) — 낮은 비용. 대비 수치는 사람이 재야 한다
  • (다) 단위 + Electron E2E — 새 의존성·CI·실행시간을 감수
결정

(다) E2E 도입. AI 는 "테마 계획서가 감당할 크기가 아니다"라며 (나)를 추천했으나 기각됐다.

(다)로 하는게 맞는거 같아 이왕하는김에 e2e테스트 기능도 깔자

결과적으로 얻은 것

E2E 는 getComputedStyle 로 대비 수치를 자동 계산할 수 있다. ADR-008 이 계산으로만 통과시킨 4.97:1 을 기계가 실측하게 됐다 — 수동 체크리스트로는 불가능한 검증이다.

→ Q10 작업 덩어리가 셋(E2E 하네스 · 타이틀바 · 테마)이 된다

검증

DB 격리가 공짜라는 것을 확인 검증

Electron 이 Chromium 의 --user-data-dir 스위치를 존중하므로 app.getPath('userData') 가 임시 디렉토리를 가리킨다. main 코드를 한 줄도 안 고치고 매 테스트가 순정 첫 실행이 되고 개발 DB 도 오염되지 않는다. 이것이 "첫 실행이 다크인가" 케이스의 전제가 됐다.

Q10

계획서를 하나로 가나 나누나

문제

CONTRIBUTING.md 가 스쿼시 머지를 강제하므로 PR 제목 한 줄이 main 커밋이 된다. "Playwright 도입 + 프레임리스 창 + 테마"를 한 줄 Conventional Commits 로 쓸 방법이 없다 — feat: 인지 test: 인지부터 안 정해진다.

고민한 선택지
  • (가) 1개 — 리뷰 불가능한 diff
  • (나) 2개 — E2E 하네스 → 타이틀바+테마. E2E 가 먼저다
  • (다) 3개 — 과분할. 타이틀바 없이는 테마 버튼을 놓을 자리가 없고 창 컨트롤 색이 테마를 따라야 해서 둘은 분리 불가 — 쪼개면 중간 상태가 "빈 타이틀바"
결정

(나) 2개, E2E 가 선행. 하네스를 나중에 만들면 테마를 수동 검증한 뒤 다시 자동화하게 되어 같은 검증을 두 번 한다.

(나) ㄱㄱ

Q11

E2E 를 어디서 돌리나 검증

문제 — CI 를 열어 보고 발견

pnpm test 가 어디서도 자동 실행되지 않는다. CI 는 pr-language.yml(PR 언어 검사) 하나뿐이고, husky 는 pre-commit=lint-staged, pre-push=브랜치 보호, commit-msg=commitlint 가 전부다. 타입체크도 단위 테스트도 자동 실행 지점이 없다.

고민한 선택지
  • (가) 로컬 전용 — 안 돌리면 없는 것과 같다
  • (나) CI 에 E2E 만 추가 — 단위 테스트는 여전히 안 돈다. 지붕부터 얹는 격
  • (다) CI 파이프라인 신설 — typecheck · lint · format · test · build · e2e. (나)와 비용이 거의 같다
결정

(다). 함께: 스크린샷 회귀는 넣지 않는다 — 폰트 렌더링이 OS 마다 달라 macOS 로컬과 ubuntu CI 의 베이스라인이 일치하지 않고, 상시 실패하는 테스트는 곧 무시된다. 대신 스크린샷을 아티팩트로 올리고 비교는 사람이 한다.

다로 가자

계획서 작성 중 새로 나온 문제 3건

  • ① 기존 개발 DB 에 "system" 이 남는다 — seed.ts 가 멱등("키가 없을 때만")이라 기본값을 바꿔도 기존 DB 는 안 바뀌고, 그 값은 새 계약을 통과하지 못한다. 읽을 때 정규화 + 저장값 되쓰기를 태스크로
  • ② 색 값 4개가 CSS 밖으로 샌다 — main 은 CSS 변수를 못 읽는데 Win·Linux 창 컨트롤 색은 JS 로 줘야 한다. 한 파일에 가두고 tokens.css 를 직접 읽어 값 일치를 검사하는 테스트를 붙였다
  • ③ OS 오버레이 영역은 투명할 수 없다 — 앱 타이틀바는 광원 위에 투명하지만 OS 컨트롤 영역은 불투명이라 Win·Linux 에서 미세한 색 이음매가 보인다. 해결 방법이 없어 알려진 한계로 기록

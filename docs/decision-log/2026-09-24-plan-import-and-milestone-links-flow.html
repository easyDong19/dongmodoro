무엇부터 하나

디자인 정합성 점검 결과와 계획서 가져오기 아이디어가 한 요청에 같이 들어왔다.

선택지
  • 디자인 수정 먼저 — 범위가 작고 이미 원인까지 찾아 둔 상태
  • 계획서 기능 먼저 — 기획 절차(Phase 0)가 필요해 길다
결정

디자인 수정 먼저. PR #98 로 머지됐다.

일단 다른것부터 해보자 디자인 정합성 수정할꺼 수정부터 들어가자 스킬 계획한는건 나중에 해ㅏ자 계획가져오기 같은건
Q1

에이전트가 앱에 계획을 어떻게 넣나

문제

한 주를 계획하려면 Milestone·Sprint·요일·task·연결을 하나씩 눌러야 한다. 클릭이 수십 번이다.

선택지
  • 스킬이 DB 에 직접 쓴다 — 켜진 앱 캐시가 어긋나고 이월·워터마크 규칙이 있는 서비스 계층을 건너뜀
  • 스킬은 형식 맞는 텍스트(계획서)까지, 등록은 앱이 — 형식이 계약이라 Claude·Codex·일반 챗봇 모두 같다
  • 로컬 MCP 서버 — 지금은 과함. 같은 형식 위에 나중에 얹을 수 있다
결정

형식 계약 + 앱의 가져오기. 스킬은 두 에이전트가 함께 쓰는 한 폴더.

Q2 반전

입력 뷰를 어디에 띄우나 — 미결

문제

AI 가 먼저 에이전트부터 앱까지의 흐름 와이어프레임을 그렸다. 사용자는 입력 뷰 자체를 원했다. 다시 3안 × 상태 4개(비어 있음 / 붙여넣음 / 형식 오류 / 이미 Sprint 가 있는 주)로 그렸다.

선택지
  • C 계획 컬럼 위 비모달 시트 (AI 추천) — MONTH 오버레이와 같은 문법, 타이머를 막지 않음. 단 480px 는 타이머를 가려 360px 로 줄여야 함
  • B 가운데 모달, 좌우 분할 — 가장 넓지만 타이머를 막음 (PRD R10)
  • A WEEK 카드 안의 모드 — 새 표면이 없지만 360px 라 확인 화면으로 좁음
결정

아직 없음. 계획서 기능의 Phase 0 에서 정한다.

내가 원한건 흐름 와이어프레임이 아니라, input 넣는 뷰에 대한 와이어프레임이었어 확인해볼래?
Q3 재설명

계획서 형식 — YAML 인가 txt 인가

문제

앱에 AI 가 없으므로 어떤 형식이든 규칙대로 읽혀야 한다. 자유 txt 는 앱이 Sprint 와 task 를 확실히 구분할 수 없다.

선택지
  • YAML — 에이전트가 잘 쓰고, 줄 단위 오류를 낼 수 있음. 약점은 들여쓰기·값 오해석
  • Markdown 식 자체 문법 — 손으로 고치기 쉽지만 파서·오류 메시지를 직접 만들어야 함
  • JSON — 따옴표·괄호가 많아 사람이 훑기 어려움
결정

YAML. 값은 전부 문자열로 읽고, 확장자가 아니라 내용을 읽어 .txt 도 받는다.

yaml로 할꺼야? 일반사람들은 txt가 익숙할껀데 그렇게 한이유가있어? 바꾸라는소리는아님
음 yaml이 맞을꺼같다 어차피 AI가 작성해주니깐 ㅇㅇ

2 · 공존 — 기존 동작과 부딪히나

설계를 확정하기 전에 기존 동작이 깨지지 않는지부터 확인했다.

평가 검증

서브에이전트 3개 — 데이터·화면·도메인

설계 그대로면 막히는 곳 4건이 나왔다.

  1. 계획 단계 task 생성이 R12 "task 목록은 계획서가 아니라 누적 기록"과 충돌
  2. AI 가 쓴 예시 계획서의 Milestone 연결이 서비스에서 거부됨 — 9/28 주는 9월 주라 10월 Milestone 불가 (R14)
  3. 대상 주 제한이 화면에만 있음 — 지난 주로 가져오면 정산이 못 보는 Sprint 가 생김
  4. 480px 시트가 창 최소 폭에서 타이머를 약 96px 가림

Q4 반전

task 를 계획서로 미리 넣어도 되나

문제

R12 는 task 를 "해 온 일의 누적 기록"으로 정의하고, 첫 pull 이 첫 task 를 만든다.

선택지
  • v1 은 tasks 를 빼고 Sprint 만 (AI 추천) — 기존 정의를 지킴
  • R12 를 개정해 두 방식 공존 — 드로어가 task 0개·있음 두 상태를 이미 다 다뤄 새 코드가 거의 없음
결정

공존. tasks 는 선택 필드. 없으면 드로어에서 쪼개고, 있으면 + 오늘로 한 번에 다음 task 가 순서대로 들어온다.

기존 정의와 충돌해도 됨, 음 내가 원하는건 기존의 방식과 현재 방식이 공존했음 좋겠다는거임

3 · 규칙 — Milestone 연결을 단순화

다른 달 Milestone 연결을 풀어 보다가, 규칙 여섯 개가 한 개념에서 줄줄이 나온다는 것이 드러났다.

Q5 재설명 반전

다른 달 Milestone 에 연결할 수 있게 하나

문제

주는 월요일이 속한 달에 통째로 귀속된다(R18). 그래서 새 연결은 그 달만(R14), 이월은 예외(R15), 카드는 귀속될 때만 숫자(R20), 아니면 안내 문구(R23). 9/28–10/4 주에 10월 목표를 걸 수 없다.

선택지
  • (가) 지금 규칙 유지 — 코드 변경 0. 경계 주에 그 달 목표를 못 다는 게 어색
  • (나) 경계 주만 두 달 허용 (AI 첫 추천) — 규칙 6개 위에 예외를 하나 더 얹음
  • 단순화 — 규칙 6개 → 3개 — Milestone 은 한 달에 속한다 / Sprint 는 어느 달 Milestone 에나 연결 / 카드는 그 Milestone 에 연결된 이번 주 Sprint 의 시간. R18 은 정산·주간 합계용으로 유지
결정

단순화. 이월 예외와 안내 문구가 사라진다. AI 는 처음 이 안을 "월 경계가 사라진다"며 비추천했다가, 집계가 Milestone 기준이라 경계가 섞이지 않는다는 점을 정정하고 추천을 바꿨다.

검증 검증

규칙 변경 가능성 · 예상 버그 — 서브에이전트 2개

기존 버그 재현. 8월 Milestone 에 연결된 Sprint 를 9/7 주로 이월하고 9/8 에 25분 집중 → 저장소는 1500초를 세지만 8월 카드도 9월 카드도 숫자를 표시하지 않는다. A13 이 지켜지지 않고 있었다 (milestones.ts:89). 새 규칙 3이 곧 해결책이다.

  1. 구현 가능 — 저장소 rollup 은 이미 어떤 주든 받는다. 서비스 게이트 2곳 + 후보 쿼리 + 무효화 + 드로어 + 문서
  2. 새 규칙의 예상 버그 3건 — 자정 달 전환 시 낡은 후보, 한 달만 새로고침, 드로어에 달 표시 없음
  3. 기존 버그 추가 — 보내주기·계획 확정이 월 카드를 안 털고, 연결 실패가 조용함
Q6

지난 달 Milestone 에 새로 연결하는 것을 막나

문제

막으면 10/2 에 9/28 주 Sprint 를 9월 Milestone 에 못 걸고, 자정에 달이 바뀌는 순간 드로어 후보가 낡는 버그도 따로 막아야 한다.

선택지
  • (가) 막는다 — "지난 달은 읽기 전용"에 문자 그대로 맞음. 규칙과 버그가 하나씩 늘어남
  • (나) 막지 않는다 (AI 추천) — 연결은 Milestone 자체를 고치는 게 아니라 읽기 전용과 부딪히지 않음. 달 전환 버그가 사라짐
결정

(나). 규칙 2 = "Sprint 는 어느 Milestone 에나 연결할 수 있다". 드로어 후보는 이번 달 → 다음 달 → 그 뒤 → 지난 달, 달별로 묶는다.

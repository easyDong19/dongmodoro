# 플래너 확정의 동시성 약점

## 무엇을

플래너 확정을 "변경분만 보내고 서버가 확정 시점에 다시 조회하는" 방식으로 옮긴다
(정산이 이미 쓰는 방식 — [weekly-review PRD](../features/weekly-review/prd.md) R29).

## 왜

플래너 확정은 **선언형**이다 — 요청 목록을 그 주 Sprint 의 전체로 보고, 목록에 없는 기존
Sprint 는 폐기한다(`services/ports.ts` 의 확정 포트 주석, week-plan R23·R24·A30).
플래너를 연 뒤 다른 경로로 Sprint 가 생기면, 낡은 초안으로 확정할 때 그 Sprint 까지 폐기된다.

## 왜 아직 안 만들었나

M3a·M3b 모두 "생성 경로가 플래너뿐이라 아직 발생하지 않는다, 다른 경로가 생기면 옮긴다"며 미뤘다.
지금은 정산 이월도 다음 주에 Sprint 를 만들지만, 정산 패널과 플래너가 같은 WEEK 카드 자리를
써서 동시에 열 수 없으므로 실제로는 발생하지 않는다.

## 언제 해야 하나

논의 중인 "계획서 가져오기"([decision-log 2026-09-24](../decision-log/2026-09-24-plan-import-and-milestone-links.md)
Q1)가 들어오면 새 생성 경로가 되어 조건이 성립한다. **그 기능과 같은 PR 에서** 옮긴다.

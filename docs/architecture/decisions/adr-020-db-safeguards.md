# ADR-020: DB 안전장치 — WAL 인지 백업·보존 정책·복구 경로

- 상태: accepted (2026-08-05)
- 관계: [ADR-011](adr-011-schema-final.md) §7("마이그레이션 적용 전 백업 + 스키마 버전
  검사")의 **결정을 유지하고 실행 방법을 확정한다.** §7 의 PRAGMA 세트도 유효하다
  (단 `foreign_keys` 기본값에 관한 근거 문장은 [ADR-019](adr-019-constraint-implementation.md) §9 가 정정).
- 결정 근거 원장: [2026-08-05 DB 계층 착수 전 심사](../../decision-log/2026-08-05-db-layer-audit.md)
  §F2 · §R5 — 보존 개수와 복원 정책은 그쪽 "확신도가 낮은 결정" 표에 약한 지점이 적혀 있다

## Context

ADR-011 §7 은 데이터 파손을 막기 위해 **마이그레이션 적용 전에 DB 파일을 백업**하도록
정했다. weekly-review 기술 명세는 이 백업에 기대어 "확정은 앱 시작 시 DB 백업 이후에만
일어나므로 최악의 경우 그날의 백업으로 복구 가능하다"고 적었다.

착수 전 심사에서 **그 백업이 실제로는 복구에 쓸 수 없는 파일**임이 확인됐다.

### 1. WAL 모드에서 메인 파일만 복사하면 데이터가 없다

계획된 PRAGMA 세트(`journal_mode = WAL`, `synchronous = NORMAL`)를 그대로 켜고 200행을
커밋한 뒤 `copyFileSync` 로 복사한 결과:

```
원본 행수: 200
app.db 크기: 4,096 바이트   (헤더뿐)
app.db-wal 크기: 12,392 바이트   (커밋된 200행 전부)
백업 열기 결과: no such table: t
```

WAL 모드에서는 커밋된 데이터가 `-wal` 에 살고 메인 파일은 체크포인트 전까지 비어 있다.
`synchronous = NORMAL` 이라 체크포인트도 지연된다. 체크포인트를 먼저 돌리면 백업 행수가
200 으로 회복되므로, 문제는 복사 방식이 아니라 **복사 시점에 데이터가 그 파일에 없다**는
것이다.

백업이 없는 것보다 나쁘다 — 있다고 믿게 만든다.

### 2. DB 를 닫는 경로가 없다

현재 main 프로세스에는 종료 시 DB 를 닫거나 체크포인트하는 코드가 없다. [app-shell R23]
이 강제 종료를 명시적으로 허용하는 경로로 두고 있으므로, "체크포인트되지 않은 `-wal` 이
남아 있는 상태"가 예외가 아니라 기본값이 된다.

### 3. 백업이 앱 실행마다 쌓인다

백업 조건이 `existsSync(dbPath) && dbVersion > 0` 뿐이라 **적용할 마이그레이션이 없어도**
백업이 만들어진다. 지우는 코드도 없다. 하루 5번 켜면 1년에 1,800개가 사용자 데이터
디렉토리에 쌓인다. §1 을 고쳐 백업이 실제 크기를 갖게 되면 이 문제는 오히려 커진다.

### 4. 시작 실패가 조용하다

`app.whenReady().then(...)` 에 `.catch` 가 없다. 여기에 마이그레이션을 붙이면 실패가
**unhandled rejection** 이 되어 빈 창 또는 무반응으로 끝난다. 처리 대상으로 문서화된
시작 실패는 `DowngradeError` 하나뿐이고, DB 손상·마이그레이션 실패에 대한 경로는 없다.

## Decision

### 1. 백업은 WAL 을 포함한 일관 스냅샷으로 만든다

복사 전에 체크포인트를 수행한다.

```ts
sqlite.pragma('wal_checkpoint(TRUNCATE)')
copyFileSync(dbPath, backupPath)
```

better-sqlite3 의 온라인 백업 API 도 같은 보장을 주지만 비동기라 동기 부팅 흐름에
맞추기 번거롭다. 체크포인트 후 복사가 단순하고 검증도 쉽다.

파일명 생성에는 `path.basename()` 을 쓴다 — `dbPath.split('/')` 는 Windows 경로를
쪼개지 못해 경로 전체가 파일명이 된다([app-shell R1] 이 Windows 를 지원 대상으로 확정).

### 2. 백업은 **적용할 마이그레이션이 있을 때만** 만든다

```
if (dbVersion < appVersion) → 백업 후 마이그레이션
if (dbVersion == appVersion) → 백업하지 않는다 (할 일이 없다)
if (dbVersion > appVersion)  → DowngradeError (§4)
```

ADR-011 §7 의 문구는 "마이그레이션 적용 **전에** 백업"이다. 적용할 것이 있을 때 그
앞에서 뜨라는 뜻이며, 매 실행마다 뜨라는 뜻이 아니다.

### 3. 백업 보존은 최근 5개로 제한한다

백업을 만든 뒤 같은 디렉토리의 백업 파일을 최신순으로 정렬해 **5개를 넘는 것을 삭제**한다.
마이그레이션이 있을 때만 만들어지므로(§2) 5개면 최근 5번의 스키마 변경을 덮는다.

정리 실패는 앱 시작을 막지 않는다 — 로그만 남기고 진행한다. 백업 정리는 부팅의 필수
조건이 아니다.

### 4. 시작 시 실패를 세 갈래로 나누어 처리한다

| 상황 | 판정 | 동작 |
|---|---|---|
| DB 버전 > 앱 버전 | `DowngradeError` | 열지 않는다. 안내 후 종료 |
| 무결성 검사 실패 | `CorruptError` | 열지 않는다. 백업 위치를 안내한 뒤 종료 |
| 마이그레이션 실패 | `MigrationError` | 백업을 자동 복원하지 않는다. 백업 경로를 안내한 뒤 종료 |

- 무결성 검사는 마이그레이션 **전에** `PRAGMA integrity_check` 를 1회 수행한다.
- **자동 복원은 하지 않는다.** 마이그레이션 실패 시 Drizzle 이 각 단계를 트랜잭션으로
  감싸므로 DB 는 대개 이전 세대 상태로 온전하다 — 이때 백업으로 덮으면 오히려 멀쩡한
  파일을 과거로 되돌린다. 손상의 경우도 범위를 앱이 판단할 수 없는데 파일 전체를
  갈아치우는 것은 과하다. 판단은 사용자에게 남긴다.
- **다만 실행은 돕는다.** 안내 창에 **"백업 폴더 열기"** 버튼을 두어
  `shell.showItemInFolder(백업 경로)` 로 파일 관리자를 연다. 경로 문자열만 보여주고
  끝내면 사용자가 무엇을 해야 할지 모른다 — 결정권은 넘기되 도달 비용은 낮춘다.
  따라서 안내는 `dialog.showErrorBox` 가 아니라 버튼을 둘 수 있는
  `dialog.showMessageBox` 로 띄운다.
- 세 경우 모두 안내 후 `app.quit()` 한다. 창을 띄우지 않는다 — DB 없이 뜬 창은 기능이
  없는데 사용자는 앱이 정상이라고 오해한다.
- `app.whenReady()` 체인에 `.catch` 를 달아 **예상 못한 실패도 같은 경로로** 보낸다.
  조용한 unhandled rejection 을 남기지 않는다.

### 5. 종료 시 체크포인트하고 DB 를 닫는다

`before-quit` 에서 `PRAGMA wal_checkpoint(TRUNCATE)` 후 `sqlite.close()` 를 수행한다.
정상 종료 경로에서 `-wal` 이 비어 있으면 다음 시작이 빨라지고, 강제 종료로 남은 `-wal`
과 구분된다.

강제 종료를 막지는 않는다 — WAL 저널이 그 경우를 위해 존재하며, 다음 시작 시 SQLite 가
복구한다.

### 6. 스키마 버전은 마이그레이션 파일 개수로 센다

`user_version` 에 번들된 `.sql` 파일 개수를 기록한다. Drizzle 은 `__drizzle_migrations`
테이블로 이력을 관리하고 `user_version` 을 쓰지 않으므로, 이 값은 **앱이 자기 스키마
세대를 표시하기 위한 별도 표식**이다. 두 장부의 역할이 다르다는 것을 명시해 둔다.

파일 개수를 세는 방식은 무관한 `.sql` 이 섞이거나 파일이 사라지면 어긋난다. 마이그레이션
디렉토리에는 생성물 외에 아무것도 두지 않는다.

## Consequences

- (+) 백업이 실제로 복구에 쓸 수 있는 파일이 된다. weekly-review 명세의 "그날의 백업으로
  복구 가능하다"가 참이 된다.
- (+) 백업 파일이 무한히 쌓이지 않는다. 마이그레이션이 있을 때만, 최근 5개만 남는다.
- (+) 시작 실패가 조용히 빈 창으로 끝나지 않는다. 세 원인이 구분돼 안내된다.
- (−) 시작 경로에 `integrity_check` 가 추가된다. DB 가 커지면 시작이 느려질 수 있다 —
  현재 규모(5년치 약 7MB)에서는 무시할 수 있으나, 체감되면 주기적 검사로 옮기는 것을
  재검토한다.
- (−) 자동 복원을 하지 않으므로 **사용자가 직접 파일을 되돌려야 하는 상황**이 남는다.
  안내 문구에 백업 경로를 정확히 담는 것이 그래서 중요하다.
- (−) 종료 시 체크포인트가 종료를 약간 지연시킨다. 강제 종료는 여전히 가능하므로
  사용자를 붙잡지는 않는다.
- (−) 백업·복구 UX 를 화면으로 제공하지는 않는다. v1 은 파일과 안내 문구 수준이며,
  복원 UI 가 필요해지면 별도 결정으로 다룬다.

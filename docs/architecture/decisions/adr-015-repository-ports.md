# ADR-015: main DB 접근 — 리포지토리 포트 + Unit of Work (DIP)

- 상태: accepted (2026-08-04)
- 관계: [ADR-008](adr-008-code-structure.md) 의 main 3층 구조는 유지하되, "서비스 → DB 직행"
  부분을 정정한다. [architecture/overview.md](../overview.md) 확장성 절의 "리포지토리 추상화
  계층은 지금 만들지 않는다" 결정을 **뒤집는다**.

## Context

M1 스캐폴딩 계획 검토 중 두 가지가 확인됐다.

1. overview.md 의 "IPC 경계가 이미 그 추상화다"는 서술은 엄밀하지 않다 — IPC 경계는
   **renderer 를 위한 유스케이스 파사드**일 뿐이고, main 내부에서는 서비스가 Drizzle 에
   직접 의존한다. main 쪽 추상화의 존재 여부는 별도 결정이 필요했다.
2. 그 결정을 두 선택지로 비교했다 (도식: 세션 산출물 dip-comparison.html):

| 선택지 | 내용 | 판정 |
|---|---|---|
| A. 직접 호출 유지 | 서비스가 Drizzle 직접 호출. 테스트는 실제 인메모리 SQLite 단일 방식. 로직 격리는 순수 함수 계층이 담당 | 기각 |
| B. 리포지토리 포트 (DIP) | 서비스는 포트(인터페이스)에만 의존. Drizzle 구현체는 격리, 테스트 더블 교체 가능 | **채택** |

AI 검토는 A 를 권고했다 — 구현체가 영원히 1개면 인터페이스는 의식(ceremony)이고,
임베디드 SQLite 는 인메모리 실 DB 테스트가 목보다 정확하며, 로직 격리는 순수 함수로
충분하다는 근거였다. 사용자가 B 를 결정했다:

- **테스트 전략을 단일 DB 방식에 묶지 않는다.** 목·페이크·별도 테스트 DB 를 상황에 따라
  선택할 수 있어야 한다.
- **기획 변경·스택 변경 가능성에 대한 보험**은 코드가 0줄인 지금 지불하는 것이 가장 싸다.

## Decision

1. **포트는 서비스가 정의한다 (consumer-defined).** 포트 메서드는 유스케이스가 필요로
   하는 질의·명령 단위로만 만든다. 테이블 모양을 그대로 비추는 **범용 CRUD 리포지토리
   금지** — 그것은 인터페이스만 있는 직접 호출이다.
2. **Drizzle·better-sqlite3 import 허용 범위는 `src/main/db/` 하위가 유일하다.**
   구현체는 `src/main/db/repositories/` 에 둔다. 서비스·핸들러·순수 도메인 함수·renderer
   는 DB 라이브러리를 import 할 수 없다 (코드 리뷰 관찰 지점).
3. **트랜잭션은 Unit of Work 포트로 묶는다.** 유스케이스 = 트랜잭션 1개(ADR-007)를
   포트 세계에서 표현하는 장치다.

   ```ts
   interface UnitOfWork {
     run<T>(work: (repos: Repositories) => T): T
   }
   ```

   better-sqlite3 트랜잭션은 **동기**이므로 `work` 는 동기 함수여야 한다 — async 콜백을
   넘기면 트랜잭션이 커밋된 뒤에 본문이 실행되는 조용한 버그가 된다. 타입으로 `Promise`
   반환을 막는다.
4. **구현체마다 계약 테스트를 공유한다.** 포트별 계약 테스트 스위트 하나를 Drizzle
   구현체와 인메모리 페이크가 함께 통과해야 한다 — 페이크가 실 DB 와 다르게 행동하는
   순간(예: 롤백 의미론) 테스트가 잡는다.
5. **순수 도메인 함수 계층(ADR-008)은 그대로 유지한다.** 포트는 껍데기(서비스)의
   관심사이고, 규칙이 있는 로직은 여전히 DB 도 포트도 모르는 순수 함수로 뺀다.
   둘은 경쟁이 아니라 보완 관계다.

## Consequences

- (+) 테스트에서 저장소를 선택할 수 있다 — 빠른 단위 테스트는 페이크로, 제약·SQL 검증은
  인메모리 실 SQLite 로, 통합 검증은 파일 DB 로.
- (+) 스택 교체·동기화 엔진 추가 시 서비스 코드가 불변이다. 교체 범위가
  `db/repositories/` 로 닫힌다.
- (+) "Drizzle import 는 db/ 하위만" 규칙이 생겨 의존 방향을 리뷰로 검증할 수 있다.
- (−) 포트·구현체·페이크·계약 테스트로 파일 수가 늘어난다. 유스케이스마다 포트 메서드를
  설계하는 비용이 상시 발생한다.
- (−) 페이크가 실 DB 의 제약(CHECK, FK)을 재현하지 않으므로, 페이크만으로 통과한
  테스트는 제약 위반을 놓칠 수 있다 — 계약 테스트(결정 4)와 인메모리 실 DB 테스트를
  병행하는 이유다.
- (−) overview.md 확장성 절의 해당 서술은 이 ADR 기준으로 갱신된다. ADR-008 본문은
  수정하지 않고 상태 표기로 남긴다.

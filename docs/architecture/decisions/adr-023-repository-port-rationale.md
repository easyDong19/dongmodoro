# ADR-023: 리포지토리 포트의 근거 교체 — 페이크·계약 테스트 보류

- 상태: accepted (2026-08-06)
- 관계: [ADR-015](adr-015-repository-ports.md) 의 **도입 결정은 유지하고 근거를 교체한다.**
  - **살아 있다**: §1(consumer-defined 포트) · §2(DB import 격리) · §3(동기 UoW, 근거 보강) · §5(순수 함수 계층)
  - **보류한다**: §4(구현체 간 계약 테스트) — 두 번째 구현체가 실제로 필요해질 때까지
  - **철회한다**: 도입 근거 ②("기획 변경·스택 변경 가능성에 대한 보험")
  - ADR-015 본문은 수정하지 않고 상태 줄에만 표기한다 (docs/CLAUDE.md).
- 결정 근거: **격리 조사 3건** — ① 로컬 우선 데스크톱 앱 8종의 데이터 계층 코드 실측
  ② 리포지토리 패턴 찬반 문헌 ③ 동기화 솔루션 9종이 데이터 계층에 강제하는 것.
  세 조사 모두 사전 맥락 없이 독립 수행했다.

## Context

Task 5 착수 직전, "리포지토리 + UoW 를 손으로 구현하는 것이 이 맥락에서 정말 맞는가"를
검증했다. ADR-015 는 AI 검토의 반대 권고(선택지 A — 직접 호출 유지)를 사용자 판단으로
뒤집어 채택된 결정이었으므로, 근거의 실증 여부를 확인할 가치가 있었다.

### 1. 실제 오픈소스는 이 패턴을 쓰지 않는다

Electron/데스크톱 + 임베디드 DB 앱 8종의 데이터 계층 **코드를 직접 읽어** 집계했다
(Actual Budget · Joplin · Trilium · Bruno · Beekeeper Studio · Notesnook · AFFiNE · Zotero).

| 항목 | 결과 |
|---|---|
| 도메인 단위 리포지토리 **인터페이스** | 1 / 8 |
| **구현체가 하나뿐인데 인터페이스를 둔 사례** | **0 / 8** |
| **Unit of Work 추상화** | **0 / 8** |
| 테스트를 실제 SQLite 로 | 6 / 6 |
| 데이터 계층을 목·페이크로 대체 | **0** |

관통하는 규칙: **인터페이스는 구현체가 실제로 둘 이상일 때만 생겼고, 그 축은 언제나
도메인이 아니라 플랫폼/엔진이었다.** Joplin·Trilium 의 인터페이스는 DB 드라이버
레벨(better-sqlite3 / node-sqlite3 / WASM 실구현 3개), AFFiNE 은 저장 종류별 4개,
Notesnook 의 `DatabaseCollection` 은 IndexedDB → SQLite 이관 중 **두 백엔드를 실제로
동시에 굴려야 해서** 생겼다 (구 구현에 `@deprecated only kept here for migration
purposes` 명시).

우리와 가장 유사한 **Actual Budget**(Electron + better-sqlite3 + 로컬 우선 + 자체 CRDT
동기화)은 인터페이스가 하나도 없다. `server/db/index.ts` 한 파일(1037줄)에 함수 60여 개를
export 하고 서비스 40여 파일이 `import * as db` 로 쓴다. 추상화 투자는 포트가 아니라
**쿼리 표현력**(자체 쿼리 DSL `server/aql/`, 3232줄)으로 갔다.

**Trilium 은 리포지토리 계층을 걷어냈다** — `6fa68914`(2018-01-30) "created repository
object to access entities" 로 도입, 3년 운영 후 `8bd3e17a`(2021-05-17) "removed legacy
entities and repository" 로 제거(**+30 / −1431, 28개 파일**). 대체물은 ActiveRecord +
인메모리 엔티티 캐시였다.

### 2. 교체 보험은 실증이 반대다 — 그리고 우리 구조에서는 성립하지 않는다

동기화·원격 저장소 솔루션 9종의 공식 문서를 확인했다.

| | 개수 | 솔루션 |
|---|---|---|
| 쓰기 API 가 **비동기 강제** | 4 | PowerSync · Triplit · RxDB · Turso |
| **동기 유지 가능** | 3 | cr-sqlite · SQLite session 확장 · Actual 식 수제 CRDT |
| 중립 / 범위 밖 | 2 | ElectricSQL · Automerge |

결정적인 것은 "4개가 비동기"가 아니라 **그 4개가 전부 `better-sqlite3 + Drizzle` 자체를
버리게 만든다**는 점이다. PowerSync 는 SQLite 를 자기가 소유하고 사용자 테이블을 JSON
위의 **뷰**로 만들며 PK 를 `text id` 로 강제한다. Evolu 는 스키마 정의·쿼리 빌더·ID
포맷(21자 NanoID — **ADR-006 §1 의 UUID v7 과 호환되지 않는다**)까지 가져간다.
Triplit·RxDB 는 SQL 이 아니다.

즉 저 중 하나를 고르면 `schema.ts`·`ports.ts`·구현체를 **전부 다시 쓴다.** 포트가 있든
없든, UoW 가 동기든 비동기든 그 시점에 무관하다. 반대로 동기 호환 3종을 고르면 바꿀 것이
없다. **어느 쪽이든 포트는 교체 비용을 줄여주지 않는다.**

### 3. 우리 맥락에서 페이크의 존재 이유가 없다

일반 프로젝트가 페이크를 만드는 이유는 실 DB 가 느려서다 — 서버 프로세스·네트워크·컨테이너
부팅. **우리는 그것이 전부 없다.** 이 저장소에서 직접 측정했다:

```
우리 실제 스키마(CHECK 44개 포함)로 인메모리 DB 세우기 : 중앙값 0.54 ms, p95 0.97 ms
settings set+get 왕복 10,000회                        : 22.6 ms (2.26 µs/회)
```

테스트 1,000개가 각자 새 DB 를 세워도 0.54초다. **페이크가 아껴줄 시간이 없다.**

게다가 프로덕션 DB 와 테스트 DB 가 같은 엔진이므로, "SQLite 로 Postgres 를 흉내내다
사고난다"는 고전적 함정(EF Core InMemory provider 류)도 해당되지 않는다.

### 4. 페이크는 오히려 검증 수준을 끌어내린다

이 스키마의 방어는 **CHECK 44개 · FK 6개 · 부분 UNIQUE 인덱스**이며, ADR-019·021·022 세
문서가 그것을 만드는 데 쓰였다. `Map<string, string>` 페이크는 그중 **하나도 재현하지
못한다.**

계약 테스트는 정의상 "두 구현체가 같은 스위트를 통과"하는 것이므로, **페이크가 통과할 수
있는 만큼만 스위트를 쓰게 된다.** 우리가 공들여 만든 제약을 검증하는 테스트는 계약
스위트에 들어갈 수 없다. 방어를 늘리려는 장치가 방어를 깎는다.

문헌에도 같은 지적이 있다 — 인메모리 페이크는 트랜잭션 격리·락 의미론·유니크 제약을
재현하기 어렵고 *fake drift* 가 발생한다. 4Comprehension 의 채택 기준이 명확하다:
**"페이크를 어떻게 구현할지 즉시 자명하지 않다면 만들지 말라."**

### 5. 그럼에도 포트를 유지하는 이유는 남아 있다

위 넷은 전부 ADR-015 의 **근거 ②(교체 보험)와 §4(페이크)** 를 겨눈다. 다음 둘은 반박되지
않았다.

- **설계 규율.** 서비스가 아직 0개다. 포트를 먼저 정의하면 다음 코드가 "테이블에 뭐가
  있나"가 아니라 "이 유스케이스가 뭘 필요로 하나"에서 출발한다. Actual 의 `import * as db`
  가 잘 작동하는 것은 이미 다 만들어진 뒤이기 때문이다.
- **표현 경계.** eslint 의 `DB_IMPORT_PATTERN` 은 **import 만** 막는다. Drizzle 을 import
  하지 않고도 `snake_case` 컬럼명·DB nullability·JSON 문자열이 서비스 로직에 그대로 새어
  들어올 수 있다. 포트의 반환 타입이 그것을 막는다. 린트는 "누가 무엇을 import 하나"를,
  포트는 "무엇이 오가나"를 본다 — 다른 축이다.

그리고 **좁은 쓰기 경로 자체는 값어치가 확인됐다.** Actual 이 CRDT 동기화를 붙일 수 있었던
이유가 모든 변경이 `insert`/`update`/`delete` 세 함수를 통과했기 때문이다. 다만 이것은
"인터페이스"의 값어치가 아니라 "좁은 경로"의 값어치이며, 모듈로도 얻어진다.

## Decision

### 1. 포트와 UoW 는 유지하되, 근거를 교체한다

ADR-015 의 도입 근거 ②("스택 변경 보험")를 **철회**하고, §5 의 두 가지 —
**유스케이스 단위 설계 규율**과 **DB 표현이 서비스로 새는 것 차단** — 로 대체한다.

근거를 바로잡는 것이 계층을 지키는 길이다. 틀린 명분이 남아 있으면 그것이 무너질 때
맞는 근거까지 함께 폐기된다 — Trilium 의 1431줄 제거가 그 경로였을 가능성이 높다.

### 2. UoW 는 동기다 — ADR-015 §3 을 확인하고 근거를 보강한다

```ts
interface UnitOfWork {
  run<T>(work: (repos: Repositories) => T): T
}
```

Context §2 대로 **비동기로 미리 감싸는 것은 얻는 것이 0 이다.** 그리고 감쌀 수도 없다 —
`drizzle-orm#2275` 에 따르면 sqlite 드라이버 5종 중 better-sqlite3 를 포함한 4종이 async
트랜잭션 콜백을 지원하지 않으며, 넘기면 **트랜잭션이 커밋된 뒤에 본문이 실행된다.**
better-sqlite3 자체도 `Transaction function cannot return a promise` 를 던진다.

성능은 근거가 아니다 — 측정치는 동기 0.404 µs, Promise 로 감싼 것 0.458 µs (1.13배)로
무시할 수준이다. 실제 이유는 **함수 색깔 전파**이며, 그 전파가 필요해지는 시나리오는
Context §2 대로 이 계층 전체를 교체한다.

### 3. 인메모리 페이크와 계약 테스트를 만들지 않는다

`memory.ts` 를 만들지 않는다. 테스트 대역은 **인메모리 실 SQLite 하나**다.

대신 테스트 스위트를 `suite(name, make)` 형태의 함수로 감싸 둔다 — 두 번째 구현체가
생기는 날 호출 한 줄로 계약 테스트가 된다. 지금 페이크를 만드는 것과 그날 만드는 것의
비용 차이가 거의 없으므로 미리 만들 이유가 없다.

이로써 **실 DB 라서 쓸 수 있는 테스트**를 스위트에 넣는다 — `settings_value_json`,
`settings_updated_at_format` 같은 CHECK 검증은 페이크가 있었다면 계약 스위트에서 빠졌을
것들이다.

### 4. 재개 조건을 명시한다

다음 중 **하나라도 실제로 발생하면** 페이크와 계약 테스트를 도입한다. 그 전에는 하지 않는다.

- 실 DB 로는 만들 수 없는 테스트 상황이 필요해진다 (결정론적 시계, 실패 주입, 디스크 부족)
- 두 번째 저장 백엔드가 실제로 필요해진다 (Notesnook 이 인터페이스를 세운 조건)
- 인메모리 DB 준비 비용이 테스트 시간에서 유의미해진다 (현재 0.54 ms)

## Consequences

- (+) ADR-015 §4 와 코드 사이의 모순이 생기지 않는다. "미이행"이 아니라 **"근거를 갖춘
  보류"** 로 기록된다.
- (+) 계약 스위트에 **CHECK·FK 검증을 넣을 수 있다.** 페이크가 있었다면 두 구현체 공통분모
  밖이라 빠졌을 것들이다.
- (+) Task 5 산출물이 4개 → 3개로 줄고, 페이크의 롤백 흉내 로직이 사라진다.
- (+) 포트가 살아남을 근거가 실증에 기반한 것으로 바뀐다.
- (−) **인터페이스의 구현체가 하나뿐인 상태가 지속된다.** 조사에서 0/8 이었던 바로 그
  상태다. 이것은 설계 규율을 위해 의도적으로 지불하는 비용이며, 값어치를 못 한다는 판단이
  서면 걷어내는 것도 정당하다 — 그때는 이 ADR 을 정정하는 새 ADR 로 한다.
- (−) 테스트가 전부 실 DB 에 의존하므로, 마이그레이션이 깨지면 리포지토리 테스트도 전부
  깨진다. 실패 원인 판별이 한 단계 멀어진다.
- (−) 동기 UoW 는 무거운 집계 쿼리에서 **main 프로세스의 이벤트 루프를 막는다.** renderer 는
  별도 프로세스라 화면이 얼지는 않으나 IPC 응답이 지연된다. 현재 쿼리 규모(µs)에서는
  무해하지만, 통계·정산 화면에서 체감되면 별도 결정으로 다룬다.
- 지금 하지 않는 것 (같은 조사에서 나왔으나 이 ADR 의 범위 밖):
  - ~~**정렬 키의 fractional index 전환.**~~ **철회 (2026-08-06, 같은 날 정정).**
    조사 결과를 우리 요구사항과 대조하지 않고 옮긴 것이다. 정수 정렬 키가 LWW 에서
    깨진다는 것 자체는 사실이나(Actual 회고), **그 전제는 "사용자가 순서를 바꾼다"이며
    우리에게는 그 기능이 없다.** [milestones R10] 은 표시 순서를 생성 순으로 고정하고
    수동 순서 변경을 v1 비범위로 두었으며, `sort_order` 는 **생성 순의 안정적 tie-break
    로만** 쓰인다. [week-plan R10] 은 아예 정렬 컬럼을 만들지 않기로 했다.
    재정렬이 없으므로 ① N행 재작성이 없고 ② 같은 행의 `sort_order` 를 두 기기가 고칠 일이
    없다. 오프라인 동시 생성으로 값이 겹치는 경우는 R10 이 정한 "동일 시 행 id" tie-break
    가 처리하며, PK 가 UUID v7 이라 그 순서가 곧 시간순이다.
    **되살아나는 조건**: 사용자 재정렬 기능이 v1 범위로 들어올 때. 그때 목록 규모(현재
    월당 2~3건)와 동기화 도입 여부를 함께 보고 판단한다.
  - **관찰 지점: `milestones.sort_order` 컬럼의 존재 이유.** 생성 순 tie-break 로만 쓰인다면
    `created_at` 과 시간순 PK(UUID v7)가 이미 그 역할을 한다. 지금 지우면 마이그레이션이
    또 생기고 R10 이 명시적으로 요구한 컬럼이므로 건드리지 않는다. 재정렬 기능이 생겨
    이 컬럼을 다시 설계할 때 함께 판단한다.
  - **HLC·노드 ID·컬럼 단위 버전.** 실제 동기화 시스템들이 공통으로 갖는 메타데이터이나,
    소비자 없이 넣으면 검증되지 않은 채 잘못 채워지는 죽은 컬럼이 된다. 전부 나중에 추가
    가능하다.
  - `settings` 를 **키당 한 행**으로 둔 것은 조사 결과 옳았다 (JSON blob 이면 LWW 아래에서
    한쪽 기기의 변경이 다른 쪽을 통째로 덮는다). 변경 없음.

# ADR-006: 스키마 확장 보험 — UUID v7 PK + updated_at

- 상태: accepted (2026-08-03)

## Context

v1 은 로컬 단독 동작이지만, 이후 "로그인하면 어느 기기서든 todo 공유"(멀티기기
동기화)로 확장될 가능성이 있다. 아키텍처의 확장 지점(seam)은 IPC 경계에 이미
있으므로 renderer 는 손댈 필요가 없으나, **스키마에는 나중에 소급 불가능하거나
마이그레이션 비용이 최악인 결정이 두 개** 있다.

원칙: "확장에 열려 있되 미리 짓지 않는다." 동기화 엔진 선택, 리포지토리 추상화
계층 같은 '미리 짓기'는 하지 않고, 비용이 거의 0 인 '문 안 잠그기'만 지금 한다.

참고로 이 도메인은 우연이 아니라 PRD 원칙 8(집계값 저장 금지) 덕에 동기화
친화적이다: 동기화할 파생 상태가 없고, sessions 는 append-only(병합 = 합집합),
soft delete 가 이미 tombstone 역할을 한다. 1인 멀티기기 시나리오라 동시 편집
충돌이 드물어 last-write-wins 로 충분한 난이도다.

## Decision

1. **모든 테이블의 PK 는 UUID v7 (TEXT 저장).** PRD §2.2 의 autoincrement 정수에서
   의도적으로 벗어난다.
   - 정수 ID 는 두 기기가 오프라인에서 각자 행을 만들면 즉시 충돌하고, 사후
     전환은 FK 전체를 갈아엎는 최악의 마이그레이션이다. 지금 정하면 비용 ~0.
   - v4 가 아닌 **v7** 인 이유: 타임스탬프 프리픽스로 삽입이 순차적이고
     `ORDER BY id` 가 시간순 — 정수 PK 의 실질 장점을 보존한다.
   - 크기 비용은 이 규모(수만 행)에서 2MB 미만으로 무시 가능. BLOB(16) 저장은
     디버깅·Drizzle 사용성을 해치는 오버엔지니어링으로 기각.
2. **mutable 테이블(tasks, week_items, milestones, settings)에 `updated_at` 추가.**
   Drizzle `$onUpdate` 로 자동 갱신.
   - last-write-wins 병합의 재료. 컬럼 추가 자체는 나중에도 쉽지만 **과거 데이터의
     갱신 시각은 영영 복원 불가**하므로 지금 넣는다.
   - **sessions 는 제외** — append-only 라 같은 행의 두 버전이 존재할 수 없고,
     충돌이 구조적으로 불가능한 테이블에는 병합 재료가 필요 없다.

## Consequences

- (+) 멀티기기 동기화로 갈 때 스키마 마이그레이션 없이 병합 규칙만 얹으면 된다.
- (+) UUID v7 생성은 main 에서만 일어난다 (행 생성이 main 의 책임이므로).
- (−) 디버깅 시 `0198f3a2-…` 가 `42` 보다 읽기 불편하다 — 감수한다.
- (−) PRD 원천 스키마와 다른 두 번째 지점이다 (첫 번째는 ADR-002/005 의 상태관리).
  기능 문서의 technical-spec 은 이 ADR 를 따른다.
- 지금 하지 않는 것 (그때 가서 결정): 동기화 엔진/프로토콜 선택, 서버 스키마,
  리포지토리 인터페이스 추상화. IPC 경계가 이미 그 추상화다.

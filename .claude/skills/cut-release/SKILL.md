# cut-release — 판을 자르고 내보내는 순서를 지킨다

## 순서의 출처는 여기가 아니다

**절차와 그 근거는 [CONTRIBUTING.md](../../../CONTRIBUTING.md) §2 가 소유한다.** 이 스킬은
그것을 옮겨 적지 않는다 — 같은 절차가 두 곳에 있으면 한쪽만 고쳐지는 날이 오고, 그날
어느 쪽이 맞는지 알 수 없게 된다. **시작할 때 §2 를 연다.**

이 문서가 담는 것은 두 가지뿐이다. **실행 가능한 체크리스트**와, **손으로 하면 밟는
것들**이다. 뒤엣것은 전부 실제로 밟은 것이다.

## 먼저 정한다 — 마이너인가 패치인가

`git log --oneline vX.Y.Z..main` 으로 지난 태그 이후를 본다. 판정은 커밋 접두사가 아니라
**사용자 손에서 무엇이 달라지는가**로 한다.

**커밋 제목만 읽고 판정하지 않는다.** 마이그레이션은 제목에 안 나온다 — `feat:` 하나가
스키마를 바꾸고 있을 수 있다. 한 줄로 확인한다:

```bash
git diff --name-only vX.Y.Z..main -- drizzle/
```

여기에 `.sql` 이 나오면 그 파일을 열어 무엇을 하는지 본다. `DROP`·테이블 재생성이면
파괴적이고, 그 사실이 아래 표와 노트 양쪽을 동시에 정한다.

| 들어 있는 것 | 판정 |
|---|---|
| DB 마이그레이션 (특히 파괴적) | 마이너 이상. 패치에 스키마 변경을 섞지 않는다 |
| 기능 제거·이름 변경 | 마이너. 쓰던 사람에게는 고쳐진 게 아니라 없어진 것이다 |
| 새 화면·새 조작 | 마이너 |
| 버그 수정만 | 패치. `release/X.Y` 에 cherry-pick 하고 새 브랜치를 자르지 않는다 |

섞여 있으면 높은 쪽을 따른다. 판정이 갈리면 사용자에게 근거와 함께 묻는다.

## 체크리스트

**항목마다 todo 를 만든다.** 순서를 건너뛰면 되돌리는 비용이 앞으로 갈수록 커진다.

- [ ] **1. 지난 태그 이후 변경을 읽고 버전을 정한다** (위 표). 사용자 승인을 받는다.
- [ ] **2. 노트를 쓴다** — `release-notes` 스킬. **1번에서 파괴적 마이그레이션을 찾았다면
      `## 업그레이드 — 되돌릴 수 없다` 가 필수**이고, 그 안의 `### 시작하기 전에` ·
      `### 복귀선` · `### 마이그레이션이 실패하면` 셋도 함께 필수다
      ([ADR-032](../../../docs/architecture/decisions/adr-032-destructive-migration-safety.md)).
      복귀선이 노트에 도달하지 않은 판은 publish 하지 않는다.
- [ ] **3. 노트를 PR 로 main 에 머지한다.** 브랜치를 노트보다 먼저 자르지 않는다.
- [ ] **4. 리허설을 돌린다** — `gh workflow run release.yml --ref main` 후 `gh run watch`.
      태그를 밀기 전에 빌드가 서는지 보는 유일한 자리다.
- [ ] **5. main 에서 `release/X.Y` 를 자른다.** 노트가 이미 그 안에 있다 — cherry-pick 없음.
- [ ] **6. 그 브랜치에서만 `package.json` 을 범프한다.** main 에는 반영하지 않는다.
- [ ] **7. 태그를 만든다.** push 전에 **사용자 확인을 받는다** — push 가 배포 트리거다.
- [ ] **8. 워크플로가 만든 draft 를 확인한다** — 노트 본문, 자동 목록의 기준점, dmg 첨부.
- [ ] **9. 설치본으로 연다** — `install-release` 스킬. dev 로는 마이그레이션 경로가 안 밟힌다.
- [ ] **10. 사람이 publish 한다.** 여기까지 오기 전에는 바깥으로 나간 것이 없다.

## 손으로 하면 밟는 것들

| 함정 | 무슨 일이 나는가 | 피하는 법 |
|---|---|---|
| **리허설을 건너뜀** | 가장 흔한 누락이다. CONTRIBUTING 을 읽고도 4번만 빠뜨린다 — 앞뒤 단계가 전부 git 명령이라 워크플로 실행이 눈에 안 들어온다. 실패는 태그를 민 **뒤에** 드러나고, 그때는 이미 민 태그를 지우는 일부터 시작한다 | 4번을 체크리스트 항목으로 만들어 두고 넘어가지 않는다 |
| **`gh pr merge` 가 `fatal: 'main' is already used by worktree` 로 죽음** | main 이 다른 워크트리에 체크아웃돼 있으면 `gh` 의 로컬 브랜치 전환이 실패한다. **머지 자체는 이미 성공한 뒤다** — 실패 메시지만 보고 다시 머지하려 들면 안 된다 | `gh pr view <N> --json state,mergeCommit` 로 실제 상태를 먼저 확인한다 |
| **노트의 문서 링크가 태그에 없음** | 상대 경로나 `main` 고정 링크는 릴리스 페이지에서 깨진다. 태그 고정 링크도 그 태그에 파일이 없으면 404 다 | 태그를 만든 뒤 `git cat-file -e vX.Y.Z:docs/...` 로 전부 확인한다 |
| **범프가 마지막 커밋이라고 가정** | 보통은 맞다 — 그래서 확인 없이 넘어간다. 그런데 `v2.2.0` 은 범프 **뒤에** cherry-pick 된 CI 수정에 앉아 있다. 범프 후에도 수정이 붙을 수 있고, 그때 범프 커밋에 태그를 앉히면 그 수정이 빠진 판이 나간다 | 확인하고 앉힌다: `git log -1 --oneline` 로 HEAD 를 보고 태그는 **그 브랜치의 마지막 커밋**에 건다. 범프 커밋이 마지막이면 그게 맞는 것이고, 금지가 아니라 확인의 문제다 |
| **main 의 `package.json` 을 고치고 싶어짐** | main 은 지난 판 번호에 머물러 있고 그게 정상이다 (범프는 release 브랜치에만 있다). "틀렸다"고 보고 고치면 배포되지 않는 번호가 main 에 남는다 | 건드리지 않는다. 이상해 보이는 것이 설계다 |
| **draft 를 확인 없이 publish** | 자동 목록의 기준점이 엉뚱한 옛 태그면 이미 나간 PR 이 새 변경으로 다시 실린다 (`v2.2.0` 첫 draft 가 18개 중 11개를 그렇게 실었다) | 8번에서 기준점이 **직전 판**인지 눈으로 본다 |
| **노트 파일을 빠뜨림** | 워크플로가 빌드 전에 죽는다. 릴리스도 draft 도 안 만들어진다 | 이것은 함정이 아니라 안전장치다. 죽었으면 노트부터 쓴다 |

## 멈추는 자리 둘

- **태그 push 전** (7번). 배포 트리거이고, 민 태그를 옮기면 이미 받아 간 사람이 깨진다.
- **publish 전** (10번). 태그를 미는 것과 남에게 보이는 것 사이의 한 칸이 여기 있는 이유다.

두 곳 다 사용자 확인 없이 지나가지 않는다. 나머지 단계는 확인을 따로 받지 않아도 된다 —
전부 되돌릴 수 있다.

## 태그를 민 뒤에 잘못을 발견하면

**태그를 옮기지 않는다.** 릴리스 객체가 아예 안 만들어졌으면(노트 누락 등) 태그를 지우고
다시 자른다. 릴리스는 만들어졌고 앱 쪽이 잘못이면 `X.Y.Z+1` 로 앞으로 고친다.

## 이 스킬이 아닌 경우

- 노트 본문을 쓴다 → `release-notes` 스킬
- 나온 dmg 를 깔아 본다 → `install-release` 스킬
- 개발 중인 코드를 화면으로 본다 → `run-app` 스킬
- 이미 나간 판에 버그 수정만 넣는다 → [CONTRIBUTING §3](../../../CONTRIBUTING.md) 핫픽스

# plain-report — 사람이 읽는 보고

## 언제 쓰는가

- 작성한 문서·코드·설계를 사용자에게 **확인·승인받아야 할 때** (PR 요약, 태스크 완료 보고, 결정 사항 정리)
- 판단 기준: 보고를 읽는 사람이 "그래서 뭘 정했다는 거야?"라고 되물을 여지가 있으면 이 형식으로 다시 쓴다.

## 핵심 원칙

1. **도메인이 처음인 사람을 독자로 상정한다.** 이 대화에 계속 있었던 사람이 아니라,
   방금 합류한 동료에게 설명하듯 쓴다. 프로젝트 내부 용어·결정 번호(Q7, B4, S3 등)를
   설명 없이 쓰지 않는다 — 쓰려면 첫 등장에서 괄호로 풀어준다.
2. **개조식이되, 완전한 문장으로.** 불릿을 쓰지만 각 불릿은 주어·서술어가 있는
   읽히는 문장이다. `A → B → 실패` 같은 화살표 속기, 명사 나열, 축약어 금지.
3. **문제 → 결정 → 이유(실패 시나리오) 순서.** 결정만 나열하지 않는다.
   - 먼저 "무엇이 문제였나"를 말하고
   - "그래서 무엇으로 정했나"를 말하고
   - "안 그러면 어떻게 되나"를 **구체적 사례**로 보여준다.
     (좋음: "시간대를 바꾸는 순간 과거 기록 전체가 다른 날짜로 이사간다" /
     나쁨: "타임존 이슈가 있다")
4. **배경 섹션으로 시작한다.** 본론 전에 "이 앱/기능이 뭐고, 왜 이 결정이 중요한가"를
   2~4개 불릿으로 깐다. 독자가 지도 없이 세부에 떨어지지 않게 한다.
5. **한 줄 요약으로 닫는다.** 항목당 한 줄 요약 목록 + 다음 단계 한 문장.
   요약은 본문을 읽지 않은 사람도 결론을 가져갈 수 있어야 한다.

## 형식 뼈대

```markdown
# <무엇을 했는가 — 명사구 제목>

## 배경: 왜 이 작업이 필요한가
- (이 도메인/기능이 무엇인지 2~4불릿. 처음 보는 사람용)

## 1. <산출물/결정 이름>
- **문제**: (무엇이 비어 있었나, 무엇이 모순이었나)
- **결정: <굵게, 한 문장>**
  - (세부 사항은 하위 불릿으로)
- **왜 중요한가**: (안 했을 때의 구체적 실패 장면)

## 2. ...

## 한 줄 요약
- **<이름>**: <결론 한 줄>
- (다음 단계 한 문장)
```

## 금지

- 표만 던지고 설명을 생략하는 것 (표는 짧은 열거에만, 해석은 문장으로)
- "상세는 문서 참조"로 설명을 떠넘기는 것 — 보고 자체로 이해가 끝나야 한다
- 렌더되는 산출물이 아니어도 이모지 남용 금지 (프로젝트 규칙과 동일 기조)
- 이 형식을 이유로 내용을 부풀리는 것 — 항목 수는 실제 산출물 수를 따른다

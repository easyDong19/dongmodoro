# 의사결정 로그 작성 규칙

## 위치와 파일명

```
docs/decision-log/
├── YYYY-MM-DD-<topic>.md            # 필수. 전체 기록 (원장)
└── YYYY-MM-DD-<topic>-flow.html    # 권장. 시간순 플로우 시각화
```

- 날짜는 **실제 세션 날짜**. topic 은 kebab-case (예: `planning-session`, `sync-architecture`).
- `docs/origin/` 에는 절대 넣지 않는다 (permissions.deny 로 차단됨).
- 같은 주제의 후속 세션은 새 날짜로 새 파일을 만들고 서로 링크한다.
  기존 로그는 **추가 전용** — 오탈자 외에는 수정하지 않는다 (기록의 신뢰성).

## md (원장) 구조

레퍼런스 구현: [docs/decision-log/2026-08-04-planning-session.md](../../../docs/decision-log/2026-08-04-planning-session.md)

1. **헤더**: 세션의 목적 한 줄 + flow html 링크 + 진행 방식 요약
2. **주제별 섹션** (A, B, C…), 각 결정 항목은 이 형식:
   - `### Q<n>. <질문>`
   - **배경/문제**: 무엇이 비어 있었거나 모순이었나 (처음 보는 사람 기준으로)
   - **선택지**: 각각 한 줄 트레이드오프와 함께. 기각된 것도 반드시 남긴다
   - **결정**: 굵게. 무엇을 골랐고 그래서 무엇이 확정됐나
   - **이유**: 사용자가 말한 근거를 **원문 인용**으로. 요약·윤색하지 않는다
   - **파생**: 이 결정이 다른 결정에 미친 영향 (`→ Q<m>` 형식으로 링크)
3. **특기 사항**: AI 의 오판·정정·번복 기록. 결정만큼 중요하다 — 숨기지 않는다
4. **미결**: 이 세션에서 의도적으로 미룬 것과 미룬 이유

## flow html 구조

레퍼런스 구현: [docs/decision-log/2026-08-04-decision-flow.html](../../../docs/decision-log/2026-08-04-decision-flow.html)

- **처음 보는 사람이 md 없이도 이해할 수 있어야 한다.** 카드마다
  `문제 → 고민한 선택지(트레이드오프 포함, 선택된 것에 ● 표시) → 결정 → 이유(원문 인용)` 를 담는다.
- 시간순 세로 타임라인. 단계(phase)로 묶고 단계마다 한 줄 설명을 단다.
- 배지 3종으로 결정의 성격을 표시:
  - `반전` — AI 추천을 기각했거나 사용자가 선택을 번복한 지점
  - `재설명` — 결정 전에 상세 설명·분석을 요구한 지점
  - `검증` — 코드 실행·서브에이전트 등으로 사실을 확인한 지점
- 질문이 아닌 이벤트(검증 실행, 규칙 변경)는 점선 카드로 구분한다.
- 결정 간 의존은 카드 하단 점선 영역에 `→ Q<m>` / `← Q<m>` 로 적는다.
- 기술 제약: 외부 의존성 0 (CDN·폰트·이미지 금지, CSS 인라인),
  라이트/다크 테마 대응 (`prefers-color-scheme`), 레퍼런스 html 의 CSS 변수 팔레트를 재사용.

## 작성 원칙

1. **사용자 발언은 원문 인용.** 맞춤법 오류까지 그대로 두는 게 원칙이나,
   문장이 깨져 못 읽을 수준이면 최소한으로만 다듬고 의미는 절대 바꾸지 않는다.
2. **기각된 선택지가 본체다.** 결정만 적으면 나중에 "다른 건 고려 안 했나"가 된다.
   왜 그 길로 안 갔는지가 이 문서의 존재 이유.
3. **AI 오판을 기록한다.** 잘못된 지적, 철회한 주장, 정정된 사실을 특기 사항에 남긴다.
   이게 없으면 로그가 "처음부터 다 맞았던 것처럼" 왜곡된다.
4. **결정이 ADR 감이면 이중 기록한다.** decision-log 에는 과정을, ADR 에는 결론을.
   서로 링크한다. decision-log 가 ADR 을 대체하지 않는다.
5. 모든 문서는 한국어. 파일명·코드 식별자만 영문.
